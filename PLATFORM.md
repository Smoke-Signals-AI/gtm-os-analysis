## 1. Company & product landscape

**Smoke Signals AI** (smokesignals.ai, owner Nick Zeckets, nick@smokesignals.ai) is a
signal-based demand-generation agency that builds GTM operating systems for B2B companies.
The core thesis is the **"alpha signal" flywheel**: *signal → interactive app + original
content → social posts → inbound leads → sharpen the signal again.* Each product implements
a stage of that flywheel. Target ICP: B2B companies running HubSpot whose buyers are active
on LinkedIn (not agencies).

**How they connect:**
- The **Client Management Portal consumes SocialOS's integration API** (`Authorization: Bearer $SOCIALOS_INTEGRATION_KEY`, base `https://socialos.smokesignals.ai/api/integration/...`) for LinkedIn campaign/engagement data. Responses are `{ success, data }` envelopes (`lib/socialos.ts` unwraps them; `success: false` throws). Every count is people; pass `since` for windowed views and use no-`since` numbers only where a lifetime figure is labelled as such; never `Math.max` the two. Match rows to Portal campaigns by the linked source `externalId`, never by name. Use `acceptRate`/`replyRate` or `totalEngagements` for rates, never engagements / (invites + DMs). `lastEngagementAt` is always lifetime and drives Active/Previous against the classifier's own window. Every other LinkedIn reader (agent, narratives, weekly digest, huddle, portal chat) goes through `lib/metrics/linkedin-live.ts`: live SocialOS for the window it reports, snapshot LinkedIn only for campaigns with no live row. The snapshot LinkedIn columns only mirror live reads; Sync Now never writes its snapshot fallback back.
- *Throughline side:* **Throughline ↔ SocialOS cross-channel link** (`docs/socialos-integration.md`): a per-org OAuth connect in Settings → Integrations (NOT the all-org key). Launching a Throughline campaign with LinkedIn touchpoints auto-programs a single cross-channel orchestration into SocialOS's engine (LinkedIn ↔ email ↔ calls, branch-aware). ⚠️ **`planHasLinkedInTouchpoints` is the gate, so a campaign flow with NO LinkedIn actions is never programmed** — its emails just run as the Smartlead sequence and its branch/wait nodes never execute. The canvas draws the same picture either way, so anything that reports on a flow (the flow tool, the launch summary, the GTM Partner) must say which of the two it is rather than implying the graph runs. SocialOS runs it and calls Throughline back at `/api/socialos/send-email` for the campaign's emails; engagement on Throughline-published LinkedIn posts is harvested by SocialOS and reported to `/api/socialos/engagements`, where Throughline routes engagers (email-enroll new people; HubSpot follow-up task on the contact owner for already-emailed ones). Metrics flow back into the campaign report. ⚠️ **Every count on the engagements endpoints is PEOPLE, with or without `since`** (SocialOS contract from 2026-09-24; before that `connectionsSent` / `messagesSent` were ACTION counters that switched to people only when `since` was passed, `enrolled` included removed people, and `totalEngagements` counted a person who accepted and replied twice). `connectionsSent` / `connectionsAccepted` / `messagesSent` / `messagesReplied` / `totalEngagements` (distinct people who accepted OR replied) are narrowed by `since`; `enrolled` (removed excluded) and `completed` (people whose current pass finished) are not; `connectionsSentTotal` / `messagesSentTotal` are lifetime ACTION counters, for volume only and never a rate denominator; `prospectsInvited` ... `prospectsReplied` and `acceptRate` / `replyRate` stay the LIFETIME per-person funnel whatever window was asked for (rates null when nothing was sent, NOT 0). So a WINDOWED view (the board report, the campaign report's SocialOS card, which now passes its 7/30/90-day window as `since`) reads the windowed people counts and computes its rates from them (capped at 1, since a window's accepts can include earlier invites), and never quotes SocialOS's lifetime rates or `enrolled` beside them; a lifetime view (the partner's `get_campaign_linkedin_performance`) quotes SocialOS's rates. `lastEngagementAt` is always lifetime and includes email replies. The board report counts each person once per campaign row (accepts under Engaged, LinkedIn and email repliers under Responses, deduplicated) and its headline lead total is distinct people across forms, events, email repliers, LinkedIn accepts/replies and social conversations, matched on email and LinkedIn URL. The loop is **bidirectional** — email activity flows the other way too: a Smartlead webhook (`/api/webhooks/smartlead/<orgToken>`) reports open/click/reply, which posts reply/click notes to the HubSpot timeline and forwards to SocialOS so the graph can branch (`email_opened`/`email_replied` decision nodes) — a reply auto-exits the prospect from LinkedIn touches (see the Smartlead webhook notes below). **Zero-config for these two first-party products** — connect works with no env setup (trust = redirect_uri allowlist + per-org consent; `SOCIALOS_BASE_URL` defaults to prod; `SOCIALOS_CLIENT_ID/SECRET` are optional hardening). Per-org tokens live on `Organization.socialos*`. ⚠️ `send_email` graph nodes need a Smartlead campaign — the programmer provisions one at launch. ⚠️ **The enrollment payload is everything SocialOS will ever know about those contacts** — nothing enriches them on the far side — so `resolveSocialosContacts` sends the whole identity (name, first/last, email, company, `title` → SocialOS's Headline column, `hubspotContactId`, and the audience's own extra HubSpot columns as `customProperties`); anything it drops shows up over there as a grid of "Unknown / — / —". `socialosAudienceName(campaign)` names the container program SocialOS files them under — `Throughline: <HubSpot list / CSV name>`, falling back to the campaign name — so each audience is its own program instead of one org-wide "Throughline Import" pile; the always-on watcher passes the same name so top-ups land in it. Enrollment is ONE-SHOT (guarded on `socialosCampaignId`), so a payload fix never reaches an already-programmed campaign on its own: the **Re-program** card on the Launch stage is the backfill. ⚠️ **SocialOS dedupes `POST /api/integration/campaigns` on `throughlineCampaignId` and answers a repeat with the campaign that key already made (`reused: true`, meaning NOTHING was created)**, so re-programming under the bare campaign id got the old, paused campaign back with its old graph. Each re-program records a revision (the replaced SocialOS campaign id) on `outboundRefs.socialosProgramRevision` and `socialosProgramKey` keys on `<campaignId>:<revision>`; the revision is persisted so a launch retrying a failed re-program resumes it rather than falling back to the first key, and the route refuses (re-pauses, 502) if SocialOS still hands back the campaign it replaced. ⚠️ **The enroll endpoint answers in COUNTS** (`{ requested, resolved, program, result: { enrolled, reenrolled, skipped, skippedActiveElsewhere, skippedContactedRecently } }`), not per contact, so the always-on watcher tags a contact with the `socialos` ledger channel (which the board report's LinkedIn attribution reads) only when the counts prove the whole batch is on the campaign; a partial batch is recorded as handled with no channel and a warning carrying SocialOS's counts. ⚠️ **SocialOS keeps ONE engagement monitor per (org, post URN)** and a re-registration replaces its match list and ref, so `registerPublishedPostForMonitoring` registers each post once with the union of every programmed campaign's audience (ref `atomization:<id>`, or the campaign id when there is only one), and `/api/socialos/engagements` resolves the post back to all of its campaigns (`campaignsForPost`) and routes each engager to every campaign whose audience has them. SocialOS matches engagers after only trim/lowercase/strip-one-trailing-slash, so the match list carries each URL as typed plus its canonical form with and without `www.` (`matchListVariants`, `src/lib/linkedin-match.ts`), and routing keys back on a protocol/www/query-insensitive form (`linkedinMatchKey`). The strategy engine's **engagement handoff** (`src/lib/audience/engagement-handoff.ts`) reuses the same primitives for a different motion: the audience research's engagement plan enrolls its amplification targets into a comment-only campaign (`find_recent_post` → `comment_on_post`, twice, with waits — never `send_connection`/`send_dm`/`send_email`), sender matched to the strategy's voice by normalized profile URL (the comment-gate pattern from `strategy/publish.ts` — the two products key accounts differently and there is no stored mapping), pointer kept on `AudienceStudy.engagementCampaignId` (one-shot; redo pauses the old run first and keys the new campaign on `strategy-engagement:<strategyId>:<replaced campaign id>`, for the same `reused` reason as the re-program hatch), replies swept back by the hourly `strategy-conversations` cron alongside campaign DMs. **Operator-side linking + the cross-system board report** (added 2026-09-10, `docs/board-report.md`): an admin who runs both products can link a customer's SocialOS account from admin → org → Integrations, three ways: admin-driven OAuth (`?orgId=` on the authorize route, nonce stamped on the TARGET org and the callback resolving the org BY the nonce, so the token binds to the customer rather than to whoever clicked), a verified token paste, or a REPORTING-ONLY bind of the customer's SocialOS org id against the all-org `SOCIALOS_INTEGRATION_KEY`. The reporting bind sets `socialosStatus = "reporting"`, which no orchestration path treats as connected (`isSocialosConnected` still demands `"connected"` + a token), mirroring SocialOS's own split: the operator key is accepted on GET (`requireIntegrationAuth`) and refused on every write (`requireLinkedOrg`). That key is what lets `/dashboard/insights/board` cover campaigns SocialOS ran NATIVELY (`GET /api/integration/campaigns/engagements?orgId=`) instead of only the ones Throughline programmed; a SocialOS campaign matched on `Campaign.socialosCampaignId` merges into its Throughline row rather than double counting. The report resolves every campaign across both products to leads/meetings/opportunities/pipeline/revenue, names the attribution basis per channel (any-touch inbound, contacted-audience match outbound, activity-only otherwise), shows the CRM's own totals beside the attributed slice so the unattributed remainder stays visible, and carries a human `BoardNarrative` (per org per window, AI-draftable but only ever saved by a person) into a print-CSS PDF and a server-built editable `.pptx`.
- *SocialOS side:* **Throughline ↔ SocialOS cross-channel link** (OAuth, per-org tokens — NOT the all-org key): launching a Throughline campaign with LinkedIn touchpoints programs a single cross-channel graph into SocialOS's engine (LinkedIn ↔ email ↔ calls). SocialOS runs the orchestration; a new `send_email` node calls Throughline back to send the campaign's emails (Throughline owns email); engagement on Throughline-published posts is harvested here and reported back for routing. See `docs/integration-api.md` (Partner write API) and the `partner_links` / `engagement_monitors` tables.
  - ⚠️ **The enrollment payload is the ONLY thing SocialOS knows about a partner-sent contact.** `POST /api/integration/campaigns/[id]/enroll` writes what it's given — nothing enriches those prospects afterwards — so a payload of bare LinkedIn URLs produces a prospect grid of "Unknown / — / —" rows and reads to the customer as a broken integration. Accept and write through every identity field, incl. `title`/`headline`/`jobTitle` → `linkedin_headline` and an open `customProperties` bag; write only the fields present so a later, thinner enrollment can't blank an earlier one; clamp to the varchar widths (Postgres rejects rather than truncates, and one long company name used to drop that contact from the whole import). Contacts land under a container `listening_programs` row named `Throughline: <audienceName>` (`src/lib/import-program-name.ts`) — per audience, not one org-wide "Throughline Import" pile; a prospect whose only provenance is a previous Throughline import is re-pointed at the new run, one a real listening program discovered is not. Enrollment is one-shot per campaign on the Throughline side, so fixes to the payload only reach already-programmed campaigns via its **Re-program** action.
  - **Reverse leg (email events → graph):** the loop is bidirectional. When a campaign email is opened/clicked/replied (Throughline receives the Smartlead/HubSpot webhook), it calls `POST /api/integration/campaigns/[id]/email-events` (`requireLinkedOrg`, body `{ email, eventType, at? }` → `recordEmailEvent`). We stamp `campaign_enrollments.email_{sent,opened,clicked,replied}_at` (first-occurrence only, so retries are idempotent). Two decision nodes branch on it — `email_opened` ("opened/clicked/replied? → warm the LinkedIn touch") and `email_replied` — and a REPLY is an **exit criterion** (`exit_reason=email_reply`), so downstream LinkedIn comms become no-ops just like a LinkedIn reply/accept. These conditions read stored enrollment state only (no Unipile call, so they're NOT in `SENDER_REQUIRED_STEP_TYPES`).
- **Three products write customer telemetry into Smoke Signals' own HubSpot portal** via private-app tokens: DealOS (`OWN_HUBSPOT_ACCESS_TOKEN`, `lib/crm-tracker.js` for customer lifecycle + `lib/prospect-tracker.js` for the prospect-assessment sales flow), SocialOS (`SOCIALOS_HUBSPOT_ACCESS_TOKEN`), ContentOS/Throughline (`SMOKESIGNALS_HUBSPOT_TOKEN`, `src/lib/analytics-hubspot.ts` — onboarding telemetry + free-AEO-report leads with timeline notes; ALSO renewal deals in a dedicated "Renewals" pipeline via `src/lib/renewal-deals.ts` [pure lifecycle] + `src/lib/renewal-deals-sync.ts` [own-portal deal writer], driven by the Stripe billing webhook — feeds GTM plan Phase 11 via `dealtype=existingbusiness`; see `docs/stripe-renewal-deals.md`). ⚠️ Private apps expose NO notes/engagement scope — docs and API error messages reference `crm.objects.notes.*`, but it isn't selectable; engagement writes (notes v3) ride `crm.objects.contacts.write` (verified via HubSpot community, 2026-07). Note the env-var name differs per repo — follow the local convention; all are fire-and-forget and must never block customer flows.
- **DealOS prospect-assessment flow** (`dealos.smokesignals.ai/assess`): a NON-customer sales flow. Entry is either the public self-serve landing page (`GET /assess` → `POST /assess/start`) or an admin-minted per-prospect link (`POST /admin/api/prospects`). The prospect connects HubSpot via the existing scorecard OAuth app (the OAuth `state` carries the prospect token, persisted in the `prospect_assessments` table — NOT `installations`, so prospects stay out of the customer table and cron sweeps). The callback branches on that state BEFORE the paid-install path (no billing, no property install into their portal), fires a background assessment (`services/prospect-assessment.js` — reuses the methodology recommender with top-3 per-methodology reasoning, a rolling next-two-quarter forecast, the rep-activity rollup, and a "% of open deals with a pending task" metric), and writes results + a drafted follow-up email as `dealos_pa_*` properties into OUR portal. The assessment takes ~30s–5min depending on portal size (HubSpot search rate limits dominate), so the prospect is NOT shown a live report: the report page (`/assess/:token/report`) is gated until the prospect books a meeting. Unlock is driven by a "meeting booked" HubSpot workflow that sets the `dealos_pa_meeting_booked` contact property (read back by the report page) and sends the drafted follow-up email; `POST /admin/api/prospects/:id/unlock` is a manual fallback. The public funnel is qualified on the intake form: a **work email** is required (`lib/eligibility.js` blocks free providers) and a **self-reported salesperson count** must be ≥ `ASSESSMENT_MIN_SALESPEOPLE` (default 3) — below that the lead is captured as status `ineligible` and never connects. Each **HubSpot portal is assessed at most once** (a re-connect under another link short-circuits to status `duplicate`). `ASSESSMENT_MEETING_URL` is the scheduling link shown on the pages. ⚠️ **The assessment runs against portals we have never sized, so every read is bounded** — the methodology recommender samples the **100 most recent closed-won + 100 most recent closed-lost within 12 months** (`RECOMMENDER_DEAL_SAMPLE` / `RECOMMENDER_HISTORY_MONTHS`, two single-page searches, `hs_is_closed_won` split so a lopsided year can't fill the sample with losses), and the pending-activity metric samples the **500 most recently created open deals** (`PENDING_ACTIVITY_DEAL_CAP` — each deal costs association + task-batch round-trips downstream). Ratios computed off a capped sample must use the search response's `total`, not the sample size: the recommender's win rate reads the true 12-month won/lost counts, otherwise a big portal reports a flat 50%.
- **GTM OS** writes lead grades into our own portal (`gtmos_*` contact properties) and pings Slack `#sales` for C+ leads.
- Call transcripts (AskElephant/Fathom/Grain) reach ContentOS via inbound webhooks and reach the Portal indirectly inside HubSpot notes.

### Stack conventions (fleet-wide)

- **Hosting: Railway** everywhere (some PRDs still say Vercel — trust the code, not the PRD). Postgres on Railway; Redis only in GTM OS.
- **Frameworks:** Next.js App Router (ContentOS 16, SocialOS 16, Portal 14) or plain Express (DealOS, GTM OS). ORMs: Prisma (ContentOS 7, SocialOS 6), Drizzle (Portal), raw `pg` (DealOS).
- **Background work:** Postgres-table-as-queue + worker dyno (ContentOS `docs/worker-tier.md`, DealOS `lib/job-queue.js`) or Railway cron hitting `Authorization: Bearer $CRON_SECRET` endpoints (Portal). **In-process schedulers have burned us** (silent failures when the web process wasn't alive at the tick — Portal removed theirs); if you must run one, split roles like DealOS `DEALOS_ROLE=web|worker`.
- **Auth:** NextAuth magic-link (Portal v5 beta, ContentOS v4), custom JWT (SocialOS), HubSpot OAuth identity (DealOS).
- ⚠️ **Prisma migration discipline (ContentOS & SocialOS):** the start command runs `prisma migrate deploy`, which applies migration *files* only — editing `schema.prisma` without a migration file in the same commit takes production down with `P2022` on every query. Write `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` for idempotency. SocialOS: `prisma/migrations/` **is committed** (the `.gitignore` has an explicit "never gitignore migrations" note after a stray rule caused production drift on 2026-04-27) — commit new migrations normally, no `git add -f` needed (older copies of this file said the folder was gitignored and new migrations needed `git add -f` — no longer true); first `migrate deploy` after a `db push` needs baselining (`scripts/db-sync.sh` handles P3005).
- ⚠️ **ContentOS deploys to production on push to ANY branch** (Railway setting). Treat every push there as a prod deploy.

## 3. Anthropic Claude — our core AI provider

Every product calls Claude. The mature reference implementations are
**ContentOS `src/lib/anthropic.ts`** (instrumentation + fallback chains + caching) and
**SocialOS `src/lib/anthropic.ts`** (`callAnthropic` shared transport).

### Model tiering (route by stakes and volume)

| Tier | Model | Fleet usage |
|---|---|---|
| Premium / customer-facing prose | `claude-opus-4-8` | GTM OS reports for HubSpot-running prospects; DealOS follow-up emails; Portal agent default |
| Heavy synthesis | `claude-opus-4-7` / `claude-opus-4-6` | ContentOS heavy tier; Portal narratives |
| Default workhorse | `claude-sonnet-4-6` (alias) / `claude-sonnet-5` | Most generation, chat, complex scoring passes |
| High-volume / cheap | `claude-haiku-4-5` | Extraction, classification, ICP grading, per-deal scoring |

Rules we follow:
- **Centralize model IDs in one module** (`ai-models.ts` / `anthropic-models.ts`) — a deprecation is then one diff, not seven. SocialOS learned this when a pinned `claude-sonnet-4-20250514` snapshot was retired and started 4xx-ing, breaking a user-facing feature.
- **Prefer aliases over dated snapshots** for anything long-lived; pin snapshots only when output stability matters more than longevity.
- **Implement model fallback**: Portal catches 404/400 (retired model) → retries with a fallback model; ContentOS steps down a chain (opus-4-7 → opus-4-6 → sonnet-4-6 → haiku) **only on 529 overload**, never on other errors, and never restarts a stream after the first token shipped.
- ContentOS supports runtime re-tiering via `AI_MODEL_TIERS` env JSON (no deploy needed).

### Call patterns that work

- **`temperature: 0` for scoring/classification** — deterministic, stable across runs, fewer malformed responses (DealOS).
- **Anything published under a real person's name needs a deterministic anti-slop check, not just a prompt rule.** "No em dashes, sound human" lowers the rate; it does not eliminate it, and a partner's LinkedIn DM has no margin for it. SocialOS pairs two things (`src/lib/ai-slop.ts`): (1) **verbatim exemplars** — carry a handful of the person's REAL messages into the prompt, not just a distilled description of their voice; a description leaves room for the model's register to seep back, specimens don't. (2) **a post-generation gate** — mechanical tells (em/en dashes, "hope this finds you well") are fixed by rule, and judgement-requiring ones (`genuinely`, `truly`, "it's not X, it's Y", "not just X but Y", buzzwords, stock transitions/closers) trigger ONE repair call that names the exact offending strings. Naming them beats "make it more human", which returns a different draft with different tells. Keep the rule list conservative — a false positive burns a round-trip and flattens real voice (we dropped `foster`: common surname).
- **Prompt caching**: mark the static system prompt with `cache_control: { type: 'ephemeral' }`; keep it byte-stable across requests so the prefix cache hits (GTM OS, Portal, ContentOS — ContentOS caps at ONE breakpoint per request, under the 4-breakpoint max, and skips thinking blocks). Traps that each cost us real money:
  - **A block is matched byte-for-byte and all-or-nothing.** ONE per-item value inside a "shared" block partitions the cache and every switch pays a full 1.25× write of the whole prefix behind it. Throughline's per-recipient personalization shipped a seniority-derived block inside the cached half; on any real mixed-seniority list that thrashed. Assert the invariance, not just the presence of `cache_control` — a test that only checks "block 0 has a breakpoint" passes while the cache never hits.
  - **Order matters more than the breakpoint.** Caching is a strict PREFIX match, so per-item content placed FIRST makes the message uncacheable no matter where a breakpoint goes (Throughline's social-design prompt led with the post and ended with the org-invariant brand context). Put invariant content first, ideally in `system`.
  - **A cache that misses is worse than no cache.** Before adding a breakpoint, check the block can actually be byte-stable AND clears the model's minimum (1024 Sonnet / 2048 Opus / 4096 Haiku). Throughline's memory-consolidation context embeds per-entry counters (`salience`, `mentionCount`, `lastSeenAt`) that mutate every run, so a breakpoint there would miss on nearly every call and pay the write premium for nothing — it is deliberately NOT cached, with the reasoning in the code.
  - **Placement is the whole game — audit it before assuming caching is "on".** The cache covers a PREFIX (tools → system → messages), so invariant content sitting in the *user* message is uncacheable no matter what you mark. SocialOS's per-prospect ICP judge had the ICP definition and outreach context — byte-identical across every prospect for a filter — in the user message, behind the varying prospect block; moving them into the cached system block was the actual fix (`judgeIcpFit`, `engine.ts`).
  - **Check the model's cacheable minimum before counting on it.** Haiku 4.5 won't cache a prefix under 4,096 tokens: the marker is silently ignored (`cache_creation_input_tokens: 0`). SocialOS's noise pre-filter (`src/server/services/noise-prefilter.ts`) marks its ~600-token system prompt anyway, but `CREDIT_COSTS.NOISE_PREFILTER` is priced without any caching discount. Price small Haiku classifiers the same way until `usage.cache_read_input_tokens` shows otherwise.
  - **Batch inside the TTL.** The default TTL is 5 minutes: a per-item call in a slow serial loop can expire the entry between items and never hit. Concurrency and caching reinforce each other — parallelizing the enrichment batch is what brought a run inside the window.
- **Cold-start a fan-out deliberately.** A cache entry exists only after the first request *completes*, so N concurrent workers all miss and all pay the write premium. Run the first item alone to warm the prefix, then fan out the rest (Throughline: event agendas at concurrency 10, personalization batches, the Smartlead preview).
- **Streaming for anything long**: SSE to the browser survives edge-proxy timeouts (Portal task-gen lesson). Pass an `AbortController` wired to client disconnect so you stop paying for tokens nobody reads (GTM OS).
- **Structured output via forced tool use**: `tool_choice: { type: "tool", name: "submit_analysis" }` beats prose-JSON prompting (SocialOS engine).
- **Server-side `web_search` tool** (`web_search_20250305`, name `web_search`, `max_uses`) for research features (ContentOS GEO/research, SocialOS VoC chat + web-tech).
- **Message Batches API for latency-tolerant bulk work**: 50% token cost + massive parallelism (DealOS nightly scoring). Access defensively (`client.messages.batches || client.beta.messages.batches`), poll with a timeout, and always keep a live per-item fallback path. Refresh downstream OAuth tokens (e.g. HubSpot) *after* the batch returns — batch turnaround can outlive an access token. **Throughline's shared wrapper is `src/lib/anthropic-batch.ts`** (`runBatchWithLiveFallback`): unique-`custom_id` enforcement, results matched by `custom_id` (they arrive in ANY order — a positional match writes one item's answer onto another's row), a per-item outcome for an item the results stream never mentions, a poll timeout that does NOT cancel the batch (a later run can still use it), and automatic degradation to live calls when the batch is disabled, unavailable in the installed SDK, below the size floor, or fails to submit. Kill switch `ANTHROPIC_BATCH_DISABLED`. **Latency tolerance is the whole test** — batch a nightly repair pass (Throughline: `repairMissingSentiment`), never anything a user or a polling UI is waiting on: campaign personalization, attendee agendas and chat turns all stay live because a 24h turnaround would visibly stall them.
- **Timeouts & retries**: SDK `timeout` 180s / `maxRetries: 3`, or manual retry on 429/529/5xx with exponential backoff capped ~16s. **Classify errors**: transient (429/529/5xx/"overloaded") → retry/user-facing "high demand"; 4xx → log loudly as a bug and do NOT retry (GTM OS shipped a hard 400 hidden behind a "high demand" message for days). ⚠️ **That 180s is not one budget — it means two different things depending on `stream`.** See gotcha 7: it is a TOTAL-DURATION cap on `messages.create` and only a TIME-TO-FIRST-BYTE cap on `messages.stream`.

### Hard-won gotchas

1. **Lone UTF-16 surrogates crash the API with a 400** ("no low surrogate in string"). LinkedIn posts and scraped copy are full of emoji; fixed-length `.slice()` truncation splits surrogate pairs. **Sanitize every text field** before sending (`stripLoneSurrogates` in GTM OS `server/utils/validation.js`; `sanitizeAnthropicBody` in SocialOS). SocialOS originally patched 2 of 8 call sites and left 6 broken — which is why **every repo must route all Claude calls through ONE shared transport function**.
2. **LLM JSON needs a repair ladder**: strip code fences and commentary, escape literal control chars, drop trailing commas, close unbalanced braces, extract the outermost `{...}` — then if parsing still fails, **re-request the whole call** (DealOS `lib/llm-json.js`, the best implementation). Never silently zero-out a result on parse failure.
3. **Check `stop_reason === 'max_tokens'`** — truncation is not fixable by re-parsing; size `max_tokens` per task.
4. **Cost instrumentation**: wrap `.create`/`.stream` to log tokens, cache reads/writes, estimated USD, and a caller tag per call (ContentOS logs `anthropic.usage`; DealOS writes per-portal rows to Postgres). Measured tokens are the source of truth for margin math — hardcoded per-feature cost guesses drift badly (ContentOS credits audit found real margins far below the claimed 90% because non-LLM vendors weren't metered).
5. **Cost guardrails for volume features**: per-org daily ceilings and a kill-switch that degrades to a deterministic template (SocialOS personalization: `CAMPAIGN_AI_MAX_PERSONALIZATIONS_PER_ORG_PER_DAY`, default 5000).
6. Keep methodology/internal vocabulary out of customer-facing generated text (DealOS email generator maintains an explicit "BANNED" list). GTM OS's prompt has a house-style banned-words list to avoid AI slop (no em dashes, no "leverage/unlock/seamless", no "not A, but B" hooks) — reuse it for any customer-facing prose.
7. ⚠️ **An explicit client `timeout` silently caps how many output tokens a NON-STREAMING call can ever produce — and the retry policy then multiplies the wait by four.** The SDK arms its abort timer around `fetch`, and `fetch` resolves when the response HEADERS arrive. So the same `timeout: 180_000` is a **total-duration** budget for `messages.create` and only a **time-to-first-byte** budget for `messages.stream` (a stream may then run for ten minutes untouched). Worse, setting `timeout` at all suppresses the SDK's own protection: `messages.create` computes a generous non-streaming timeout from `max_tokens` — and refuses outright, telling you to stream, past ~10 minutes of expected work — but ONLY when `_options.timeout == null`. Pass a timeout and that guard never runs. Then "retry on request timeout" fires `maxRetries` more times, so a call that could never fit burns `(maxRetries + 1) × timeout` before failing. **Throughline lived this**: the social-strategy calendar generator was a `messages.create` at `max_tokens: 16000` (~4–5 minutes of emission) against the 180s client timeout. It timed out, was retried 3×, and failed after **`latencyMs: 723128` — 12 minutes — having written nothing**, every single time, for every customer. The rule: **above roughly 8,000 `max_tokens`, the call must stream**, even when nobody is watching the tokens. Throughline's `createMessageStreamed` (`src/lib/anthropic.ts`) is the batch-shaped wrapper — streaming transport, same overload-fallback ladder, returns the finished message — so a long generation does not have to become an SSE route to be correct. Do NOT fix this by raising the shared timeout: it is also what stops a wedged CHAT request hanging a user.
8. **Chunk a long generation, and persist each chunk as it lands.** Once a run is several model calls (Throughline plans a 12-week × 13-slot calendar in week ranges), accumulating everything and writing once at the end means the last call's failure destroys work that already succeeded and was already paid for. Write per chunk, make the write idempotent per cell, stop at the first failure rather than burning money on calls likely to fail the same way, and charge only for the calls that actually ran. Retrying then costs the remainder, not the whole program.
9. ⚠️ **Chunking silently destroys coherence unless the chunks share a PLAN — and feeding each chunk the previous one's output is not that.** The obvious fix (hand chunk N what chunks 1..N-1 produced) only ever looks BACKWARD, so chunk 1 is written with no idea that chunks 2 and 3 exist. Anything whose value is a progression — a narrative arc, a curriculum, an escalating argument, a migration in stages — comes out as N locally-good, globally-flat segments, and nobody notices because each chunk reads fine on its own. It is also lossy backward: a rolling "last N items" window stops reaching the start of a long run exactly when the global constraint (a category mix, a budget, a coverage requirement) most needs the full count. **Do a cheap PLANNING pass first**, over the whole scope, that emits one line of intent per unit; then give EVERY chunk the entire plan with its own slice marked, so it knows whether it is writing the setup or the payoff. Throughline's `planProgramArc` (`src/lib/strategy/arc.ts`) is ~2k output tokens against ~10k per content chunk, so it rides inside the existing price. Three rules make it hold: **persist the plan** (a resumed run must serve the same plan its first half served, or the seam lands exactly where the failure did); **degrade to no plan, never to no output** (the planning call failing must not become a new way for the whole run to fail); and keep a **complete aggregate** of what is done alongside the truncated recent tail, since the aggregate is what global constraints are judged against.
10. **A model reply is not always the artifact — auto-publish paths MUST detect refusals and meta-commentary.** Any prompt a customer can edit will eventually read as an instruction to an assistant ("write a GTM Engineering comment... and don't write a bullshit comment"). When the source material doesn't fit that brief, Claude does the *conversationally* correct thing: declines, explains why, and asks a clarifying question. If nothing sits between the response and the wire, that refusal gets published under the customer's real name. SocialOS shipped exactly this as a public LinkedIn comment ("This post isn't about GTM Engineering, so I can't write a relevant comment... Would you like me to..."). Three fixes, all needed:
   - **Tell the model there is no operator.** State in the system prompt that the reply is published verbatim, that it must never refuse/ask/explain, and — critically — that the user prompt is *a brief, not a contract*: if the requested angle doesn't fit the source, drop the angle and write something grounded, rather than commenting on the mismatch. Without that last clause the model has no in-character escape hatch and refusing stays its most reasonable move.
   - **Detect it deterministically** (`detectAssistantMetaCommentary` in SocialOS `campaigns.ts`): tier-1 patterns that are never valid copy (first-person refusals, "would you like me to...", "the instructions say", "as an AI", `Here's the comment:` preambles) block on one hit; weaker "describing the task" tells ("off-topic", "unrelated to", "writing a comment") need two. Tune for recall — a false positive skips one step, a miss is a public artifact.
   - **Gate at the publish boundary, not just after generation.** The stored text can predate the validator, come from a regenerate endpoint, or be hand-edited. Check it in the executor immediately before the vendor call, before charging credits.
   - **Then sweep every auto-send path in the repo — there is never only one.** SocialOS fixed the campaign comment, then found three more surfaces with identical exposure: referral partner DMs, referral invite DMs, and partner posts published to a real feed. All were cron-driven with no human in the loop. The detector belongs in the shared slop module (`src/lib/ai-slop.ts`), not next to whichever caller found the bug first — same reasoning as routing all Claude calls through one transport.
   - **Watch where user-supplied text sits in the prompt.** SocialOS's partner DM prompt appends partner-written voice feedback framed as "if it conflicts with anything above, this feedback wins". A partner writing "only send this if it's really a good fit" is then *licensed* to trigger a refusal. Order the guard AFTER any such block and say it outranks it — and lock the ordering with a test, since it's invisible in review.
   - **Discard, don't repair.** Route meta-commentary to the "no draft" path before any slop-repair round-trip. Repairing it just launders the commentary into cleaner prose and lets it through.
11. **A writer cannot grade its own output — put a second reader, with the FULL source, at the publish boundary.** Regex gates catch text that is *never* valid copy; they cannot tell that a grammatical, on-brand comment answers the first sentence of a post rather than its point, staples a "we wrote about this" link onto a post that is only adjacent to the piece, or lands a tip under a layoff announcement. SocialOS's campaign comments had all three, and the writer was the wrong place to fix it: it is optimising for a brief it has already committed to, and in sender-post mode it is deliberately handed a 50-character topic hint so it has nothing to misquote. The fix (`src/lib/comment-review.ts`, run from `executeCommentOnPost`) is a separate call whose only job is to read the WHOLE post plus the draft and return one of `keep` / `edit` / `stop` via forced tool use, with a required `post_summary` field first so it has to state what the post is about before ruling. Rules that made it safe: (a) the reviewer runs *after* the deterministic gates and its edit must pass them again — meta-commentary, foreign URLs (`findForeignUrls` against the draft + our matched content), the fabrication check — and a failed edit is **withheld, not replaced by the draft** the reviewer just said shouldn't ship; (b) fail-open on infrastructure (unreachable / malformed → publish unreviewed, logged) so an outage doesn't switch every comment campaign off, fail-closed on judgement; (c) bias stated in the prompt: torn between keep and edit → keep, torn between edit and stop → stop; (d) persist verdict + reason + both drafts on the row (`CampaignEnrollment.commentReview`) so the owner can tune the writer from the diff, and put the outcome in step history (`comment_withheld: <reason>`); (e) kill switch (`CAMPAIGN_AI_COMMENT_REVIEW_DISABLED`); (f) `temperature: 0`, static system prompt under `cache_control` — the volatile case goes in the user message. Not billed to the customer: it is QA on our output. Apply the same shape to any other auto-publish surface.

12. **Retrieved material in a message addressed to a named person needs an explicit attribution guard — and the better your retrieval, the more it needs one.** RAG excerpts dropped into an outbound prompt get woven in as though the RECIPIENT had said them: SocialOS shipped "though 47% of teams are moving that direction" to a recipient whose reply was, in effect, "what 47%?". The first fix was to withhold the knowledge base from any prompt grounded in the prospect's own post — which, in an engagement-monitoring product where every prospect arrives *because* they posted, switched the knowledge base off for essentially all outbound. The real fix is a framing header that keeps the material and forbids the misattribution outright (`KnowledgeBaseFraming: "outreach"` in `knowledge-base.ts`; the same rules restated in `relevant-content.ts` for the `find_relevant_content` node). Non-obvious consequences:
   - **Topic-matched retrieval makes this MORE likely, not less.** The `find_relevant_content` node selects excerpts precisely because they resemble the recipient's post, so the two are as similar as they ever get. Any feature that improves retrieval precision raises the misattribution risk in lockstep — carry the guard forward, never assume better matching made it unnecessary.
   - **Pin the exact title and URL in the prompt and forbid inventing them.** Told only "reference our content", the model produces a plausible-looking link that 404s. The point of a retrieval node is that the citation is a known string, so hand it over verbatim.
   - **Cap the citations and say the material is droppable.** "Cite at most one unless asked" plus "if none of it fits, ignore this section" — otherwise a helpful note turns into a link list that reads as marketing.
   - **Never stack two retrieval blocks in one prompt.** When a vetted, thresholded block is present it must REPLACE the ambient one, not append to it: two sets of excerpts with nothing marking which links are safe to cite is worse than either alone.

## 4. HubSpot — the central CRM

Deepest integrations: DealOS (`server/src/lib/hubspot.js`), ContentOS (`src/lib/hubspot.ts`, 110KB), Portal (`lib/crm/*`), SocialOS (`src/server/services/hubspot.ts`), GTM OS (`server/services/hubspot.js`).

### Auth modes we use
1. **OAuth 2.0 public apps** (customer portals): authorize at `https://app.hubspot.com/oauth/authorize`, token at `https://api.hubapi.com/oauth/v1/token`. 2. **Private-app tokens** (`pat-*`) for our own portal (telemetry sinks, GTM OS lead writing).

The batch publish path already sequenced the writeback first; the per-registrant path now carries the link itself. ⚠️ **`POST /crm/v3/objects/contacts/batch/update` keyed by `idProperty: email` is ALL OR NOTHING**: one input email with no contact and HubSpot refuses the whole batch (`Failed to find objects with unique property`, the missing ones listed under `context.missingObjectPropertyValueCoordinates` as `<portalId>:0-1:email:<email>`). Live (GRTW, Ariox portal, found from Railway logs): an event mixing 14 self-serve registrants with 13 imported names never in the CRM wrote ZERO agenda URLs on every publish for months, while `pushAgendaUrlsToHubspot` logged "wrote agenda URLs" with a `failed` count nobody read. `batchUpdateContacts` now parses those coordinates (`missingEmailsFromBatchUpdateError`), drops exactly the missing emails, and re-sends the rest once; the missing stay counted as failed and are never created (an imported audience is not the customer's CRM). (3) Partner logos on a door: the panel UPLOADS into the brand-logo asset store (served publicly at `/api/assets/brand-logo/<key>`, deliberately no `BrandLogo` row so `pickOrgLogoForBackground` never picks a partner's mark as the customer's own), and the template build PROBES an http(s) logo URL (`probeLogoUrl`, headers only, SSRF-guarded): a 4xx/5xx or a non-image content type renders the partner's name instead of a broken-image icon (a pasted share-page URL shipped one at the top of every registrant's agenda, live); an unverifiable URL is left alone. Ink for the header band is read from storage for uploaded SVGs (`inkColorsForLogoUrl`). (2) `createEventDeliveryEmailDraft` refuses to mint a twin: when the door's selected email already has the same subject AND its body carries the same agenda token (readback), the existing id is returned — a looped confirmation card double-approved a create and put two identical drafts in a customer's portal a minute apart.
- The transactional single-send API (`POST /marketing/transactional/2026-03/single-email/send`, scope `transactional-email`, paid add-on) sends by `emailId` with `customProperties` merged as `{{ custom.* }}`. ⚠️ The "mark this email for single-send" toggle and publish step have NO public API — a draft created via the API must be reviewed, set to single-send, and published in HubSpot's UI before the send endpoint accepts it. Surface that step to the user; a created-but-unpublished email fails the send with a portal-specific error.

### ⚠️ Which tenant does a finished OAuth grant belong to? (cross-tenant CRM wiring)
Found in SocialOS 2026-08-29: a workflow's "fallback owner" picker in one account listed user seats from other companies. The picker was scoped correctly (session org → that org's connection → that portal's owners). The break was in **how the connection got attached to the org**:
- The connect route put the initiating org id in `state`; the callback **ignored `state` and used `session.orgId`**. The session is one cookie shared by every tab and rewritten on every account switch, so switching accounts (or having a second tab) between "Connect" and HubSpot's redirect landed the grant on the wrong tenant. That org then read the other tenant's contacts and owner seats and wrote tasks/notes into their CRM — no error, no signal, in an app where agency staff switch accounts constantly.
- Nothing stopped **one portal from backing two organizations**, so the mis-wiring survived next to the legitimate connection.

Rules for every OAuth callback in the fleet:
1. **Take the target tenant from a signed `state`, never from the live session/cookie.** Sign it (we use the JWT secret, `aud` = a per-flow constant, ~15 min TTL) so the id can be trusted; also carry the initiating user and require the same user to finish the flow, which doubles as CSRF protection. An unverifiable `state` must **refuse the connection** — falling back to the session's org is the bug.
2. **Re-check the user still has access to that tenant** before storing (membership can change during the handshake).
3. **Require an identifiable portal** (`hub_id` from introspection) and **refuse a portal already connected to a different org** — one portal, one account. Only live connections should block: an org whose tokens were cleared keeps a stale `hubspotPortalId` and must not block a reconnect elsewhere.
4. **Show the connected portal id next to any UI that lists portal-wide data** (owner/seat pickers especially). A correct-but-mis-wired connection is visually indistinguishable from a data leak otherwise.
5. Audit existing rows for portals claimed by more than one org (SocialOS `scripts/audit-hubspot-portals.ts`) — the guard only prevents new mis-wirings.

### Rate limits (the #1 operational issue)
- The **CRM search API has a strict ~4–5 req/s per-portal "secondly" limit** that parallel fan-outs trip instantly. Pace searches with a **client-side token bucket before the wire** (DealOS `lib/rate-limiter.js`, `HUBSPOT_SEARCH_RPS=3`); treat 429-retry as fallback, not flow control.
- General limit ~100 req/10s: batch associations in small concurrent groups with inter-batch delays (Portal uses concurrency 2 + 300ms).
- Always honor `Retry-After` on 429 with exponential backoff + jitter (jitter matters — concurrent callers otherwise resynchronize and stampede again).
- **Batch endpoints**: read/update in chunks of ≤100 IDs; fetch engagements via one association call + one batch read, never N+1.
- **A cap without a sort is not a sample.** Truncating a paged search keeps whatever order HubSpot returns (roughly oldest-first), which is the opposite of what "the last N deals" means — pass `sorts: [{propertyName, direction:'DESCENDING'}]` whenever the ceiling is deliberate (DealOS `searchDeals`/`searchAllDeals` both take it). Where a bounded sample will do, prefer one 100-row page per slice over paginating: it's a single request, and the response's `total` gives the true match count for free so ratios stay honest.

### Scope gotchas (bit us repeatedly)
- **OAuth scopes are frozen at consent.** Adding a *required* scope invalidates/403s every existing install until customers reauthorize. Prefer HubSpot **optional / conditionally-required** scopes for post-launch additions, detect missing grants at runtime, and show an actionable prompt (Throughline `docs/hubspot-scope-migration.md`, Portal social scope). ⚠️ **The corollary that cost a full day live (GRTW, 2026-09-02): an optional scope added post-launch does NOT reach existing installs on reconnect.** HubSpot's changelog: "Changes to the auth settings will not affect existing installs or existing OAuth refresh tokens." Optional permissions are selected at INSTALL (pre-checked boxes on the consent screen), and re-authorizing an existing install re-uses that selection, so four reconnects by a partner admin on a Marketing Hub Pro portal, with `automation` declared Optional on the right app and requested in `optional_scope`, returned a byte-identical scope list every time while the two optional scopes that predated the install kept granting. The fix is a NEW install: the customer uninstalls the app in HubSpot (Settings, Integrations, Connected apps) and reconnects. Any "reconnect to grant X" prompt for an OPTIONAL scope must say uninstall-then-reconnect; and the authoritative test for a grant is the API call itself (`buildEventDeliveryWorkflow` probes the action-types endpoint and surfaces HubSpot's verbatim `MISSING_SCOPES` body, whose `errors[].context.requiredScopes` names the exact scope), never the scope list on the stored row or the token-info endpoint.
- ⚠️ **Scope mismatch is BIDIRECTIONAL, and it breaks every connect — including reconnects.**
  `Authorization failed because there is a mismatch between the scopes in the install URL and the
  app's configured scopes` fires in BOTH directions:
  1. a scope in the install URL (`scope` **or** `optional_scope`) that the app does not declare, and
  2. a scope the app marks **Required** that the URL does not request in the required `scope` union.
  Direction 2 is the trap: adding a new scope to the app as *Required* while the code requests it via
  `optional_scope` breaks connects **more** thoroughly than not adding it at all, and it looks like
  the fix didn't work. An `optional: true` entry in `hubspot-scopes.ts` therefore needs the scope
  declared on the app as *Optional* / *Conditionally required* — **never** Required.
  Adding a scope is a TWO-PLACE change: the manifest in `src/lib/hubspot-scopes.ts` AND the app's
  scope list in the developer portal. Nothing in CI can catch the second half, because the app config
  isn't in the repo — so the code change and the portal change ship together or connects break.
  Cost the first time: `crm.objects.owners.read` (added `optional: true`, never declared on the app)
  and `e-commerce` (same, latent for ten days before anyone tried to reconnect) took every connect
  down while the existing tokens kept working, so nothing looked wrong until a customer reconnected.
  Debug it by reading the ACTUAL install URL's `scope`/`optional_scope` params off the error page and
  diffing both directions against the app's three buckets — not by reasoning about the code, which is
  usually correct.
- The `oauth` scope is not always echoed in a token's granted-scope list — exclude it from scope-audit diffs (DealOS).
- Keep the canonical scope list in exactly ONE module and sync app manifests to it.
- Free/Starter portals are plan-gated for some APIs — check granted scopes after OAuth and refuse politely with guidance (SocialOS requires Marketing Hub Pro+).

### Identity: matching a person to a contact (the wrong-contact class of bug)
Every product here resolves "which contact is this human?" and it is the most dangerous
code in the integration: a wrong answer attaches tasks, notes and property writes to a
stranger, silently. SocialOS shipped all of these; the rules are general.
- **Never accept a name-only match.** A single live portal has **84 contacts named Smith,
  45 Johnson, 43 Brown**. A same-surname search with `limit: 10` and a fuzzy first name is
  a coin flip, not a lookup. Require an owned identifier (LinkedIn URL / email), or an
  exact first+last **plus** a company match. SocialOS had a branch that returned a contact
  whose first name did not match *at all* on the strength of surname + overlapping company
  text — that is how "Sally Smith's post" produced "a task on Jimmy Smith".
- **Refuse on ambiguity, and refuse on truncation.** If two candidates tie, or `total >
  results.length` (the surname is more common than one page), return null. Picking from an
  arbitrary slice is worse than missing.
- **`EQ` on a text property is ANALYZED, not literal.** `lastname EQ "Smith"` genuinely
  returns contacts stored as `"Smith, MBA"` and `"Smith, CTS, DSCE"`. Always re-verify the
  match client-side; never treat an EQ filter as an exact match.
- **Verify a URL match by slug, not by string.** Stored values drift every way possible —
  www/no-www, trailing slash, query strings, and (seen live) `HTTPS://` in caps. A
  `CONTAINS_TOKEN` slug filter is a useful recall net but returns other people
  (`garoutte` also lives inside `garoutte-smith-99`), so **compare the `/in/<slug>` of the
  result against the one you asked for** and never return `results[0]` on faith. Two
  contacts with the same slug are duplicates of one human — that case is safe.
- **Two tiers, and only one may write.** Record HOW a contact was matched next to the id
  (SocialOS: `hubspot_match_method` on `prospects` and `campaign_enrollments`). A match on
  an owned identifier may have properties written to it; a name match may only be
  associated with. Writing properties on a name match is what **fuses two people into one
  record** — a live portal holds "Jason Smith, MBA" over `jason.deshefy@veloxis.com` and
  `/in/jason-deshefy-a6728b96`, ~10% of one bulk-created cohort. The association is
  recoverable; the overwrite destroyed the original values.
- **A stored id is not evidence.** Re-verify ids you already have by reading the contact
  and checking it still carries that person's URL/email (one batch read per 100). This is
  what promotes legacy ids so they keep syncing, and what *detects* an id already pointing
  at someone else before the next write deepens the damage.
- **Split names before writing them.** `name.split(" ")` keeps credentials, pronouns and
  flair, producing last names like `"Smith, MBA"` — which then never match the `"Smith"`
  on the person's real contact, pushing every later lookup into the fuzzy path. One live
  portal has **44 contacts whose last name is literally "PMP"** and 33 that are `"S."`.
- **Say so in the artifact.** When a match is unverified, put that on the task/note body.
  Silence means a rep acts on a misattributed signal and never finds out; refusing to
  write loses a real signal. The human is the only one who can settle it.

### Data & API quirks
- ⚠️ **Batch endpoints return 207 Multi-Status on partial success — and `response.ok` is
  true for it.** `results` then holds ONLY the records that succeeded, with the rest in a
  separate `errors` array, and **ordering is not guaranteed** in any case. So **never pair
  a batch response to its inputs by array index.** SocialOS's `batchCreateContacts` did
  (`created.set(batch[j].key, data.results[j])`): one rejected input shifted every later
  prospect onto the previous prospect's contact id, those ids were persisted, and the next
  sync wrote one person's name onto another person's contact. Match results back by an
  identifier you actually sent (email / LinkedIn slug); create records that have no unique
  identifier one at a time; if a result can't be attributed, log it and leave it unpaired —
  re-resolving next run is cheap, a wrong pairing is not.
- ⚠️ **`batch/read` with `idProperty` only works for a property HubSpot treats as a UNIQUE identifier — and it fails SILENTLY when it isn't.** SocialOS resolved contacts in bulk with `POST /crm/v3/objects/contacts/batch/read` + `idProperty: "hs_linkedin_url"`. That property is an ordinary shared one, so the call returned **200 with an empty `results`** on every real portal — indistinguishable from "none of these contacts exist". The bulk pass therefore resolved 0/N forever, silently fell through to the per-URL search fallback (`[hubspot] Batch read resolved 0/50, searching 50 individually`), and 429-stormed the search endpoint — while those very same individual searches went on to match nearly every contact. **Bulk-match on a non-unique property with `search` + an `IN` filter instead** (`filterGroups[0].filters[0] = { propertyName, operator: "IN", values }`, ≤100 values, `limit` 100): one request per 100 values rather than one per record. Two rules the fix depends on: send **every URL variant** (www / no-www / no trailing slash — portals store all of them, and the stored form is routinely not the one you asked for) and match the response back **by slug identity, never by position**; and **let the first result win per input**, because portals genuinely hold duplicate contacts for one profile and picking the last would make a prospect's contact id flap between syncs, re-writing properties and re-attaching notes on every flap. Generalize: **a bulk read that returns "0 resolved" and a working per-record fallback is a silent outage, not a slow path** — alert on the ratio, because the fallback hides it behind nothing worse than a rate-limit warning.
- ⚠️ **Containment is not repair: a wrong id you refuse to act on is still a wrong id.** The `batchCreateContacts` index-pairing bug above persisted mispaired `hubspot_contact_id`s onto prospects. `verifyStoredContactMatches` was added to catch them — it re-reads each stored contact and demotes the match when the contact carries somebody else's LinkedIn profile — and it worked: no more overwrites. But it only ever *declined*. The bad id stayed on the row, so every subsequent sync re-read it, re-logged an error, and left it for the next one; ~56 rows in one portal did this indefinitely. Verification has to distinguish **contradicted** (the contact carries a profile and it belongs to someone else, or the contact is gone from the portal → clear the stored id so the resolver re-runs) from **unverifiable** (no URL on the contact, no email on either side → keep it; absent evidence is not counter-evidence, and clearing on it would re-resolve a quiet portal forever). Only the first clears. **Any guard that writes "refusing to act on this" to the log on every pass needs a repair path, or it becomes permanent load with a paper trail nobody reads** — the same failure mode as `lastRefreshError`.
- **Don't re-resolve an identity you were handed.** A prospect discovered by scanning a HubSpot list member's posts **is** that contact — the run started from it. SocialOS still wrote the prospect with no contact id and let the campaign engine search the portal for it later by LinkedIn URL, which is the search pass that storms. Stamp the id at ingest (`AuthorContactHint` → `Prospect.hubspotContactId`) and seed it onto the campaign enrollment at creation, so the CRM is read once. Carry the **method** with it and be honest about the tier: when the contact had no LinkedIn URL and the run guessed one by name search, the contact is certainly right but the profile attached to it is only as good as that guess, so it travels as *unverified* and may not overwrite properties.
- **Deals in our own portal (SocialOS Trigify migration, `socialos-hubspot-deals.ts`)**: don't hardcode pipeline/stage ids; read `GET /crm/v3/pipelines/deals` at runtime (prefer id `default`, first stage by `displayOrder`) with env overrides. CRM search is eventually consistent, so a deal created seconds ago may not be found by search yet: **store the new id immediately after create**, and only fall back to search (by an external-id property) when no id is stored. v4 `PUT /crm/v4/objects/deals/{id}/associations/default/{type}/{toId}` is idempotent, so re-associating on every retry is safe. A contact create that races another writer returns 409 with `Existing ID: <id>` in the body.
- **Custom properties**: provision idempotently on install (create group + properties, tolerate 409s). ⚠️ **HubSpot reserves archived property names forever** — a deleted property's name can never be recreated (GTM OS lost `gtmos_linkedin_url` this way). Property values cap at 65,536 chars — truncate.
- **A portal admin can delete/retype your properties at any time.** GTM OS's `writeDroppingInvalidProps()` pattern: parse which property names the 400 flags invalid, drop just those, retry, and log loudly — one broken property must cost one field, not the whole lead.
- **Include error response bodies in thrown errors** — a bare "HubSpot API error: 400" let a rejected payload go unnoticed for days.
- Never write object-valued fields into properties (400: "Cannot deserialize value of type java.lang.String") — flatten/normalize enrichment payloads first.
- Never blank a shared standard property (e.g. `hs_linkedin_url`) — only write when you have a value; other integrations share it.
- ⚠️ **Marketing emails resolve company tokens through the contact's PRIMARY ASSOCIATED COMPANY — creating both records is not enough.** A contact created via `POST /crm/v3/objects/contacts` has no company association unless you write one, and portal-level domain auto-association is a setting you cannot rely on. Every company-level token then renders blank in a contact email while the properties themselves look perfectly written, so it fails silently and only in the delivered email. Associate explicitly with `PUT /crm/v4/objects/contacts/{contactId}/associations/default/companies/{companyId}` (idempotent, safe to repeat), and **write the association before any workflow enrollment trigger property**, or a contact can enroll before HubSpot can resolve its tokens. DealOS `lib/prospect-tracker.js` (`associateContactToCompany`) is the reference; the whole prospect nurture depended on it and it was missing.
- Association writes can answer **204 with an empty body** — a transport that unconditionally calls `res.json()` throws on success. Read the body as text and parse only when non-empty.
- **Webhooks**: v3 signature = HMAC-SHA256 over `method + url + rawBody + timestamp` with the client secret, base64, 5-min replay window, `timingSafeEqual`. Capture the raw body via `express.json({ verify })`. **Respond 200 within 5 seconds, process async**, and **debounce** engagement-triggered work through a durable queue (engagements land in bursts). Raise the JSON body limit (default 100kb 413s at scale).
- **Lists v3 (active lists / segments)**: `POST /crm/v3/lists` with `objectTypeId: "0-1"`, `processingType: "DYNAMIC"` and a `filterBranch` whose root is an `OR` branch holding `AND` branches (both need `filterBranchType` + `filterBranchOperator`). Property operations: bool `{operationType: "BOOL", operator: "IS_EQUAL_TO", value: true}`, enum `{operationType: "ENUMERATION", operator: "IS_ANY_OF", values: [...]}`, "more than N days ago" `{operationType: "TIME_POINT", operator: "IS_BEFORE", timePoint: {timeType: "INDEXED", indexReference: {referenceType: "TODAY"}, offset: {days: -N}, timezoneSource, zoneId}}`. Find a list by name first (`GET /crm/v3/lists/object-type-id/0-1/name/{name}`, 404 when absent) so a bootstrap stays idempotent. SocialOS: `LIFECYCLE_LISTS` in `socialos-hubspot-contacts.ts`.
- `date` properties take `YYYY-MM-DD` (midnight UTC); `datetime` takes ISO. Note-to-contact association type id is 202 (`HUBSPOT_DEFINED`).
- **No pipeline-config webhook exists for public apps** — cache pipelines with a short TTL (30s) + a manual "Resync" button.
- Some portals don't support association filters in search — keep a fetch-all-then-filter fallback.
- **`propertiesWithHistory`** (per-property version history, e.g. every `dealstage` a deal ever entered) needs no extra scope — `crm.objects.deals.read` covers it. Gotchas: it drops the list endpoint's max page size from 100 to **50** (`GET /crm/v3/objects/deals?limit=50&propertiesWithHistory=dealstage`), and `POST .../batch/read` accepts a `propertiesWithHistory: [...]` body field with the same 50-input cap. Versions arrive most-recent-first — reverse before replaying chronologically (DealOS stage-transition backfill, `lib/hubspot.js` + `lib/stage-transitions.js`).
- **Enriching contacts with their company's firmographics** (headcount/industry/revenue a contact record doesn't hold): resolve the association in ONE v4 `POST /crm/v4/associations/contacts/companies/batch/read` (≤100 ids/chunk), take the first (primary) company per contact, then ONE `crm/v3/objects/companies/batch/read` for the unique company ids — never an N+1 per contact. Bound the input (Throughline `getCompanyPropertiesForContacts`, cap `MAX_CONTACT_COMPANY_ENRICH=1000`) since it fans out to two batched reads; it's a read for segment insight, not a send, so a bounded sample is fine. Best-effort: a failed chunk drops those contacts from the map rather than throwing.
- Trust `hs_is_closed` but ALSO check stage categories: customers create custom closed stages ("Churned") without the closed flag.
- **Deal → product attribution via line items**: a deal's products aren't a deal property — resolve them through line items in TWO batched passes, never N+1: v4 `POST /crm/v4/associations/deals/line_items/batch/read` (≤100 deal ids/chunk) to get each deal's line-item ids, then v3 `POST /crm/v3/objects/line_items/batch/read` for each line item's `hs_product_id`. Needs the **`e-commerce`** scope (a.k.a. `crm.objects.line_items.read`), which is an OPTIONAL post-launch add: request it via the OAuth **`optional_scope`** param — NOT the required `scope` union — so it can't 403 existing installs whose tokens predate it (frozen-consent rule above); HubSpot silently skips an optional scope A PORTAL can't grant — but that is the only thing it forgives. **Every scope in the install URL, `optional_scope` included, must be declared on the APP**, and every scope the app marks *Required* must appear in the required `scope` union. See the bidirectional-mismatch rule below. Detect the grant at runtime (`hasScopeFor(scopes, "deal-line-items")`, scopes from `Organization.hubspotScopes`) and on a 403 degrade to org-level attribution with a "reconnect HubSpot" prompt rather than erroring. Throughline: `getDealLineItems()` in `src/lib/hubspot.ts`, used by the GTM Planning funnel baseline (`src/lib/gtm-plan/funnel-baseline.ts`); the optional scope is declared in `src/lib/hubspot-scopes.ts` (`optional: true`) and flows into `optional_scope` via `allOptionalScopes()`.
- **Broadcast/Social API** (`/broadcast/v1/broadcasts`) is deprecated but the ONLY per-post social-metrics source; needs the optional `social` scope; metrics retained ~30 days → snapshot daily and merge with a `GREATEST` high-water-mark so totals never regress (Portal `docs/social-reporting.md`).
- HubSpot CMS export: `POST /cms/v3/pages/site-pages` creates DRAFT pages (needs `content` scope).
- Tenant isolation: key every cache row by `portalId`/`orgId` as a *required* argument — this physically prevents cross-tenant leaks (DealOS).
- Detecting "does this company run HubSpot" from their website: naive substring scans false-positive on blog posts about HubSpot and false-negative on bot-blocked sites — check actual tracking-script hosts, and follow GTM containers (`googletagmanager.com/gtm.js?id=...`) since HubSpot is often loaded via tag manager (GTM OS).

### Custom workflow actions (DealOS Phase 2.2)

Admin-authored HubSpot workflows can call our server as custom actions. DealOS ships five DEAL-scoped actions (re-score, coach-on-breach, deal-score-branch, escalate-to-manager, draft-next-step) under `/workflow-actions/*` on `https://dealos.smokesignals.ai`.

- **Definition = an app-project `hsmeta` file, not the v4 REST API.** Each action is a `"type": "workflow-action"` hsmeta under `meddpicc-scorecard/src/app/workflow-actions/*-hsmeta.json` (deployed with `hs project upload`, same as cards). Config shape: `actionUrl`, `isPublished`, `supportedClients:[{client:"WORKFLOWS"}]`, `inputFields` (typeDefinition + `supportedValueTypes` + `isRequired`), `objectRequestOptions.properties` (props HubSpot sends in the payload), typed `outputFields` (`typeDefinition{name,type,fieldType}` — `bool`/`booleancheckbox`, `number`/`number`, `string`/`text`), `labels.en`, and `objectTypes:["DEAL"]`. The TargetOS repo's `src/app/workflow-actions/*.json` is the canonical shape reference.
- **Signature is v3 HMAC over the FULL URL — the correction vs webhooks.** Same scheme as webhooks (`base64(HMAC-SHA256(secret, METHOD + URL + rawBody + timestamp))`, `timingSafeEqual`, 5-min past / 60s future window) BUT the workflow-action callback signs the **absolute URL including scheme + host** (`https://dealos.smokesignals.ai` + `req.originalUrl`), not just the path our webhook verifier uses. Signing only the path fails every request. The secret is the **marketplace DealOS app's client secret** (`config.hubspot.scorecardClientSecret`), NOT the legacy "main" app's `clientSecret`. Reject with 401 on failure; capture `rawBody` via the global `express.json({ verify })`. Lives in `server/src/lib/workflow-action-auth.js`, separate from `webhooks.js`.
- **Sync vs async response contract.** Sync actions (e.g. deal-score-branch, coach-on-breach) respond `200 { outputFields: { ...outputs, hs_execution_state: "SUCCESS" } }`. Actions that do slow work (rescore enqueues; draft-next-step calls Opus) fire-and-forget and respond SUCCESS immediately (`{ queued:true }` / `{ drafted:true }`) rather than blocking the workflow. On a **handled** error respond `200 { outputFields: { hs_execution_state: "FAIL_CONTINUE" } }` and log — never wedge the customer's workflow. Only signature/auth failures return non-200 (401). **Human-in-the-loop is structural**: actions only write reviewable deal properties/tasks (the `[DealOS]` task prefix is load-bearing — `compliance.js` excludes it from rep-follow-up detection); they never change a deal stage autonomously.
- **Static-hsmeta / runtime-framework tension.** DealOS is framework-agnostic (15 methodologies; property prefix `ss_<frameworkId>_*` resolved per-portal via `getPropertyPrefix(getFramework(fwId))`). But hsmeta files are **static** — `objectRequestOptions.properties` and `outputFieldLabels` can only list ONE framework's names, so they hardcode the `ss_meddpicc_*` defaults. This is cosmetic only: the SERVER re-resolves the caller's actual framework from `installation.config.framework` at request time and reads/writes that prefix's properties. A non-MEDDPICC portal's action still works; the workflow's property picker just shows MEDDPICC-named request props. (A future per-framework hsmeta generation step could remove the mismatch.)
- **Scope: `automation`, added as OPTIONAL not required.** Added to `optionalScopes` in `app-hsmeta.json` (NOT to `config/scopes.js` REQUIRED_SCOPES). Existing installs stay valid and are not flagged missing-scope; only portals that enable a workflow action get a consent prompt for `automation`.
- **Platform-version caveat (deploy-blocking, unresolved as of 2026-07-18).** DealOS's project is `platformVersion 2025.2`; the `workflow-action` hsmeta type is only _confirmed_ on `2026.03`. Do NOT bump `platformVersion` casually (it can invalidate other project components). Run `cd meddpicc-scorecard && hs project validate` and read whether 2025.2 accepts the type before deploying; if it rejects, the type needs a platform bump that is a separate, orchestrated decision. See the Phase 2.2 build notes for the current `hs project validate` result.

### DealOS Context API (Phase 3.2)

Provider-neutral, read-only HTTP surface (`/context/v1/*` on `https://dealos.smokesignals.ai`, `server/src/routes/context.js`) that returns a deal's DealOS-derived context — scores, transcript-grounded evidence, stage-compliance verdict, stage progression, org-hierarchy placement — or a portal summary, so **DealOS's OWN agents consume it on the Anthropic SDK. NO HubSpot Breeze anywhere** (hard rule; "we write our own agents"). Full spec + reference client: `docs/CONTEXT_API.md`.

- **Auth = per-portal API key**, `Authorization: Bearer dk_<key>` (`lib/api-keys.js`): key format `dk_` + base64url(32 random bytes); only `sha256(key)` is stored (no bcrypt — keys are high-entropy), plaintext shown ONCE at creation; validate with `crypto.timingSafeEqual` (constant-time, no unknown-vs-revoked oracle). Staff mint/list/revoke via `POST|GET|DELETE /admin/api/customer/:portalId/api-keys` behind `requireAdmin`. This is a NEW auth mechanism — DealOS previously had no per-portal API key (only admin magic-link, workflow HMAC, `CRON_SECRET`, card JWT).
- **Cross-portal invariant (the load-bearing guarantee):** a key resolves EXACTLY ONE `portalId` (attached as `req.apiPortalId`); every Postgres read is `WHERE portal_id = <that portal>` and the single `hubspot.getDeal` uses that portal's token (HubSpot scopes it). A key can NEVER read another portal's deal; a deal not in the key's portal → `404 { error: "deal_not_found" }` (never leak existence).
- **Mounted OUTSIDE `EXTENSION_FACING_PREFIXES`** (like `/workflow-actions`, `/admin`) so the CRM-card JWT middleware and billing gate do NOT apply — the Bearer key is the credential. The `/context/v1` health/version endpoint needs no auth.
- **Framework-agnostic + one HubSpot call:** deal facts + evidence + compliance + transitions + hierarchy are Postgres; the ONLY HubSpot read is a single `getDeal` for the `ss_<frameworkId>_*` score props (built from `getFramework(installation.config.framework).elements`, never hardcoded MEDDPICC). Response `framework.elements` tells agents the element keys to read. Metered via `usage-tracker.trackFeatureUsage(portalId, "context_api_deal" | "context_api_portal")`.
- **PII/egress:** the bundle is the customer's own CRM-derived data; keys are secrets, portal-scoped — rotate (issue-new-then-revoke) on leak.

### Salesforce — second CRM (Throughline; read-mostly + activity write-back)

Unlike HubSpot (marketing email, workflows, campaign execution), Salesforce is a **system of record**: Throughline reads it and logs activities back, but never executes campaigns through it. Build plan + phases: `docs/salesforce-crm-integration-plan.md`. Client: `src/lib/salesforce*.ts`; routes: `src/app/api/integrations/salesforce/*`.

- **Auth: OAuth 2.0 Web Server flow + PKCE**, per customer, against an **External Client App** — NOT a legacy Connected App (Connected-App *creation* is restricted as of Spring '26; Salesforce steers new integrations to ECAs). Authorize `{login}/services/oauth2/authorize`, token `{login}/services/oauth2/token`; `{login}` = `https://login.salesforce.com` (prod + Developer orgs) or `https://test.salesforce.com` (sandboxes), overridable via `SALESFORCE_LOGIN_URL`. PKCE is enforced org-wide: send `code_challenge`/`code_challenge_method=S256` on authorize and replay `code_verifier` **plus** the client secret at token exchange.
- **Instance URL, not a fixed host.** The token response carries `instance_url` — every subsequent API call targets `{instance_url}/services/data/vXX.0/…`. Store it per org (`Organization.salesforceInstanceUrl`). Current REST API version: **v67.0** (Summer '26); pin it (`SALESFORCE_API_VERSION`).
- **No `expires_in`.** Salesforce token responses omit it — access-token lifetime is the org's session-timeout setting (unknown to us). So DON'T rely on a precise proactive-refresh clock: treat a **401 `INVALID_SESSION_ID` as the authoritative refresh trigger** (refresh once, retry) and use a conservative `issued_at`+assumed-TTL hint only to avoid an obvious round-trip. (`salesforceRequest` in `src/lib/salesforce.ts` does exactly this.)
- **Refresh-token ROTATION.** When the app/org enforces rotation (our Dev org does), each refresh returns a NEW `refresh_token` that MUST be persisted every time — dropping it silently disconnects the customer on the *next* refresh. Also an **idle-expiry cap** (Dev-org max 30 days; customer orgs may set less): a lapsed/rotated-away/revoked refresh → clear stored state → reconnect banner (a keep-warm sync cron keeps active orgs from lapsing). Scopes are **frozen at consent** (like HubSpot) — adding a required scope later forces reconnect (`docs/salesforce-scope-migration.md`).
- **Scopes (least privilege):** `api` (all reads + the write-back), `refresh_token`/`offline_access` (long-lived refresh), `id` (identity URL → org id + granted scopes). NOT `full`.
- **Objects:** Contact, Lead, Opportunity (closed-won = `IsWon = true`), Campaign + CampaignMember, **Task/Event** (Activities — engagement history AND the write-back target: log an executed activity as a `Task` on the matched Contact/Lead `WhoId`), ListView (results via the list-view REST resource). Query via SOQL (`/services/data/vXX.0/query`, paginate `nextRecordsUrl`).
- **Rate limits:** per-org DAILY API request allocation (403 `REQUEST_LIMIT_EXCEEDED` = a HARD WALL — pause the endpoint, don't retry) + concurrency limits (429 = back off, honor `Retry-After`; `src/lib/salesforce-fetch.ts`). Read a local mirror on hot paths; meter live calls.
- **Revenue plane is provider-agnostic.** Closed-won + open Opportunities sync into the SAME `HubspotConversion` table as HubSpot, tagged `provider` (`src/lib/salesforce-conversion-sync.ts`, cron `sync-salesforce-conversions`); campaign revenue/attribution (`getCampaignAnalytics`) reads it with no consumer changes. A customer runs one CRM, so "read all rows for the org" is exactly their CRM — no double-count. Each provider's open-deal prune is provider-scoped so the two syncs never delete each other's rows. The Salesforce sync also writes closed-LOST rows (`kind: "lost_deal"`) — read ONLY by the GTM funnel baseline's win rate, never by the revenue plane (`getStoredConversions` buckets kinds explicitly), with won ids reconciled out of the lost bucket so a reopened-then-won opp stops counting as a loss. GTM funnel-baseline (`funnel-baseline.ts`): HubSpot reads live; a Salesforce org reads this mirror (window clamped to `MIRROR_WINDOW_MONTHS` = what the 180-day mirror actually holds; lead/meeting stages fall to priors, win rate + deal size + renewal split derive from real rows).
- **The gated `set_campaign_audience` partner tool resolves Salesforce too** (no new tool; the approve loop is inherited): HubSpot lists keep precedence when HubSpot is connected; otherwise it resolves a Salesforce Campaign (members) or Contact/Lead List View by name (exact-then-substring, candidates on miss) and pins the id into the `ActionBinding`, mirroring `resolveHubSpotList`.
- **The memory layer mines Salesforce activities** (`MemorySourceKind.SALESFORCE_ACTIVITY`): Task/Event `Description` bodies (call/meeting notes) ingest via `getSalesforceRecentActivityNotes` → `src/lib/memory/salesforce-activities.ts`, substantiality-gated and capped like the HubSpot notes/calls sources, so a Salesforce org's engagement grounds positioning/briefs/coaching. Same prospect-org exclusion as the other sources.
- **Personalization reads fall back to Salesforce.** The personalized-page READ path (`/api/contacts/lookup`, `/api/content/[id]/personalize`) resolves the visitor via HubSpot when connected, else Salesforce (Contact, else unconverted Lead) mapped to the same identity property names (`salesforce-personalization.ts`) — identity fields only; there is no custom-property catalog on the Salesforce path, so HubSpot-specific `{{tokens}}` fall back to their `||default`. The personalization WRITE path now works on Salesforce too (owner directive 2026-07-25): the per-recipient URL push writes a custom Contact/Lead field via the field-write surface below, matched by email — the field is created + FLS-granted on first push, and a connecting user without "Customize Application" gets an actionable error rather than a silent no-op.
- **Prospect studies connect Salesforce too** (`/api/study/<token>/connect?provider=salesforce`): the shared Salesforce callback has a PUBLIC `sfstudy:<token>:<nonce>` state branch mirroring HubSpot's `study:` branch — token routes to the study, the FULL state must equal the one-time `salesforceConnectNonce` on the study's isolated `isProspect` org (PKCE verifier replayed from the same row), tokens only ever land on that shell, then a ONE-OFF `syncOrgSalesforceConversions` hydrates the mirror (the evidence engine reads `provider="salesforce"` deal/lost_deal rows — the hourly cron hasn't seen a brand-new prospect org yet) before `startProspectStudyRun`. `ProspectStudy.crmConnectedAt`/`crmProvider` are the provider-neutral stamps (HubSpot stamps both old + new fields). Salesforce mirror rows carry NO loss reason (no standard field) — the diagnosis clusters those losses reason-less, like a HubSpot portal that never codes `closed_lost_reason`.
- **Analytics display flag is CRM-agnostic.** The report objects (`OrgAnalytics`, `CampaignAnalytics`, `ItemAnalytics`, `AiSearchAttribution`, `DashboardMetrics`, the GTM-plan report) expose `crmConnected` — true when EITHER CRM token is present — and every conversion tile / AI coach line / partner performance note gates on it, so a Salesforce-only org sees its mirrored pipeline instead of "N/A / Connect HubSpot". Do NOT gate a conversion-display surface on `hubspotAccessToken` alone; that flag is only for genuinely HubSpot-specific features (nurture channel, list push, the HubSpot campaign-object link, request-path conversion freshen).
- **Consent-screen verification:** an unverified/Local ECA shows customers an orange "Security Warning" banner on consent. Fine for dev/pilot; **publish/verify the app (packaged distribution) before broad rollout**. Minor: a brand-new ECA can briefly 400 `invalid_client_id` until it propagates; reading/writing Campaigns needs the connecting user's "Marketing User" permission.
- **The write surface (owner directive 2026-07-25: full HubSpot-parity writes).** Three writes, nothing else: (a) **activity Tasks** (below), (b) **custom-field creation** on Contact/Lead via the Tooling API, and (c) **field-value updates** on existing Contact/Lead records matched by email — both via `src/lib/salesforce-fields.ts`. Still NEVER create or delete records (Contacts/Leads/Opportunities), and the GTM Partner still has no write tool. Field mechanics learned building it: a custom field is `name__c` created with `FullName: "Object.name__c"` + a Metadata payload, and it is **invisible to everyone until FLS is granted** — the module upserts a "Throughline Integration" PermissionSet, assigns it to the connected user, and adds a FieldPermissions row; skipping this makes every later read/write of the field silently fail. Bulk value updates go through sObject Collections (`PATCH /composite/sobjects`, ≤200 records, `allOrNone:false`) so one bad row never fails the batch; email matching is Contact-first, else unconverted Lead, match-or-skip.
- **Content data sources are CRM-agnostic** (`src/lib/content-data-source.ts` owns the one validated shape; picker `src/components/crm/crm-source-form.tsx`, CRM tab `src/components/content/crm-settings.tsx`). A content piece's narratives fuel is either a HubSpot list selection (`type: "hubspot"`, lists + properties) or a Salesforce audience (`type: "salesforce"`, a Campaign or a saved Contact/Lead List View + field API names). The Salesforce reader (`getSalesforceDatasetRows`) projects the CALLER's field list, unlike the fixed-identity audience readers: a **list view** keeps its own describe query from `FROM` onward with only the SELECT spliced (the filter IS the membership — dropping it would silently widen the audience to every Contact in the org), and a **campaign** resolves member ids from `CampaignMember` then projects the base object by id in ≤200-id chunks (CampaignMember denormalizes only a few identity fields, so it can't honor an arbitrary selection). ⚠️ **Always intersect a stored field selection against `describe` before building SOQL** — one unknown or FLS-hidden field 400s the WHOLE query, so a stale selection would take the entire snapshot down instead of losing one column; and drop compound `address`/`location` parents so no dataset cell holds an object. Snapshot failures surface to the writer, so the Salesforce path reports its own reason (`content-dataset-snapshot.ts` bypasses the swallow-everything read path) rather than the generic "zero rows".
- **Personalized-URL distribution runs on either CRM, and BOTH auto-pickup** (`/api/content/[id]/distribute`; sweeper `/api/cron/sync-personalized-urls`, one service, two passes): HubSpot writes a contact property on a static list's members; Salesforce writes a `…__c` Url field on a campaign / list view's Contacts and Leads via the field-write surface, matched by email. New people in either audience get a URL with no user action. The **cadence differs because the change probe does**: HubSpot has a cached `hs_list_size`, so it's cheap every 5 minutes; Salesforce's cheapest equivalent is an aggregate `SELECT COUNT()` over the audience (`getSalesforceAudienceMemberCount` — for a list view, the view's describe query with ORDER BY **and any trailing LIMIT stripped**, or a `LIMIT 25` view would report 25 members forever and the sweep would never see a newcomer), so a Salesforce piece is swept at most DAILY. That gate lives in the CODE (`SALESFORCE_URL_SYNC_MIN_INTERVAL_MS`, 20h, stamped in `personalizedLayout.salesforceUrlSyncedAt`) rather than in a second cron schedule: same trigger, different cadence, and a cron service nobody provisions in the Railway dashboard is a feature that silently never runs. A `null` count means "unknown" and reads the audience anyway — treating it as "unchanged" would strand newcomers — and an unreadable audience is deliberately NOT stamped so it retries next tick instead of waiting a day. Both providers share ONE slug map (`personalizedLayout.contactSlugs`, assigned by `assignPersonalizedSlugs`), so a URL already emailed keeps resolving even if the piece is redistributed through the other CRM. HubSpot Forms lead-capture and static-list linking remain HubSpot-only by nature (no Salesforce analog).
- **Events use Salesforce as an audience source + agenda-URL target.** `EventSalesforceSource` (the `EventHubspotList` analog) attaches a Campaign or Contact/Lead List View; import/auto-sync/removal reuse the shared `event-audience.ts` helpers (source id stored in `EventAttendee.sourceListIds`, `planSegmentRemoval` treats SALESFORCE like HubSpot). On publish, `pushAgendaUrlsToSalesforce` writes each attendee's live page URL to a Contact/Lead field (`{slug}_agenda_url__c`, created + FLS-granted on first push) matched by email — the elegant equivalent of the HubSpot agenda-URL property, using the field-write surface above.
- **Activity write-back** (`src/lib/salesforce-writeback-queue.ts`, cron `process-salesforce-activity-queue`): activities Throughline executes for a specific person (Smartlead email sent, sequence enrollment, LinkedIn-engagement follow-up) — plus the inbound-engagement leg (a prospect's REPLY or link CLICK from the Smartlead webhook; opens are skipped as noise, and sends are logged by the hourly sync with exact copy, not the webhook) — are logged as a Salesforce **Task** on the matched Contact (else unconverted Lead). Three rules learned building it: (1) **`POST /sobjects/Task` is NOT idempotent** and the shared transport retries 429s/network errors, so idempotency must be claimed BEFORE the call — a unique `(organizationId, dedupeKey)` index makes enqueue the claim and a duplicate enqueue is a P2002 meaning "already logged", never a second Task; (2) **match-or-skip** — never create records in a customer's CRM, so no match is a terminal SKIPPED, not a failure; (3) a **Lead must be filtered `IsConverted = false`** — a Task on a converted Lead is invisible. Set `OwnerId` from the record's owner so the activity lands with the rep who owns the relationship, and `WhatId` from the Contact's `AccountId` (a Lead has none). Opt-IN per org (`Organization.salesforceActivityWriteback`, default false) because it writes into the customer's system of record. It is a SYSTEM sync behind an explicit user action — deliberately **no GTM Partner tool** (AGENTS.md hard limit).
- **Tokens plaintext at rest** on `Organization.salesforce*`, consistent with `hubspotAccessToken` (the known fleet encrypt-at-rest gap — don't regress it).

## 5. LinkedIn data & actions — Anysite, Unipile, HeyReach

We deliberately split LinkedIn work across **anonymous scraping (Anysite)** — no customer
session at risk — and **authenticated actions (Unipile)** — the customer's own account.
**Prefer Anysite for all reads/enrichment**; only use Unipile when the action must come from
the customer's identity (invites, DMs, posting, "is *my* account connected to X").

### Anysite (`api.anysite.io`) — anonymous LinkedIn/Reddit scraping
- Auth: `ANYSITE_API_KEY` in an **`access-token` header** (not Bearer). All endpoints POST. Management endpoints additionally need `ANYSITE_ACCOUNT_ID`.
- ⚠️ **Token-management endpoints are at the host root, not under `/api`** (confirmed by Anysite, 2026-09-25): `GET https://api.anysite.io/token/requests` and `/token/requests/count`, header `access-token`. SocialOS appended them to `ANYSITE_BASE_URL` (`…/api`) and hit `/api/token/requests` (404) from early August until the fix; use `anysiteTokenOrigin()`.
- ⚠️ **Domain → company is `POST /api/linkedin/google/company` with `{"keywords": ["acme.com"], "count": N}`**, not `/google/company` and not `{domain}`. It matches the keyword as a substring of the company website and sorts by headcount, so always check the result's website is the domain before using the match (DealOS used the wrong path and body until 2026-09-25).
- Reference clients: SocialOS `src/lib/anysite.ts` (~1500 lines, most complete), GTM OS `server/services/anysite.js`.
- Key endpoints: `/api/linkedin/{user,company,post}`, `/user/posts`, `/company/posts`, `/post/{comments,reactions,reposts}`, `/search/{posts,people,companies,jobs,users}`, `/linkedin/email/user` (email→person), `/sn_search/users` (Sales Navigator), `/company/employees`, `/linkedin/google/company` (domain→company, `keywords` array; see below — other copies list this as `/google/company`). Usage feed: `GET /token/requests`, `/token/statistic`.
- **Billing is per CREDIT, not per call** — endpoints vary wildly (comments=63 credits, post search=9, user=3, most=1; ≈$0.001/credit on the Enterprise plan). Don't model cost per-request; SocialOS `docs/cost-analysis.md` is the source of truth.
- **Post engagement counters are NOT contractually guaranteed** and their field names drift across versions and between the user/company post endpoints (`reaction_counter` / `reactions_count` / `num_likes` / `likes` / nested `social_counts.numLikes`, and the comment/repost equivalents). Read across every spelling defensively — Throughline `postEngagement()` in `src/lib/account-voice.ts`. **Distinguish "no counter in the payload" from "measured zero":** return `null`, never `0`, when nothing is present. Ranking a mostly-null list would silently put arbitrary posts at the "top" while the consumer claims they performed best; Throughline's voice extraction falls back to recency below a minimum measured-post count for exactly this reason.
- **The `/search/*` endpoints bill per RESULT — "1 credit per 10 results" — and that makes some of them cheaper than the lookup they replace.** `/linkedin/search/sql/companies` takes a **`urn` array** (plus `count`, max 1,000) and returns the same fields as `/linkedin/company`, at 0.1 credits per company against ~4. Resolving 600 employers: 60 credits, not 2,400. It's cheaper even for ONE company, and chunk size doesn't matter to price — so chunk small (SocialOS uses 100) and fail small. **Before assuming an endpoint can't be batched, check whether a search endpoint returns the same shape**; the lookup/search split is about addressing, not about data.
- **Never compare LinkedIn URNs as raw strings.** The same entity arrives as `urn:li:member:123`, `urn:li:fsd_company:123`, a bare `123`, or any of those wrapped as `{type, value}` — and which one you get depends on the endpoint, not the entity. Every cross-source match must go through one shared rule (SocialOS `urnKey`/`urnParts` in `lib/linkedin-cache-keys.ts`). Two non-obvious requirements it encodes:
  - **Send the provider's casing, compare case-folded.** Member ids (`ACoAA…`) are case-SENSITIVE, so a lowercased id in a request body is a lookup that cannot succeed; but sources disagree on case, so an exact comparison misses real matches. One helper, two fields — `value` to send, `key` to match.
  - **Reject non-ids instead of coercing them.** A naive prefix-stripper turns `https://…/company/acme` into `//…/company/acme` and a URN with an empty id (`urn:li:fsd_company:`) into itself — both become junk request payloads that can only miss. Null means "unaddressable", which callers already handle.
  These failures are always silent and always look like something else: a batch lookup that "missed" and re-buys, a DM thread that never attaches so a warm note drafts as a cold intro, a contact the customer already knows that isn't suppressed. Audit for them by source pair, not by call site — same-source comparisons (a DB `IN` filter then a `Set.has` on the same column) are exact by construction and fine.
- **Bulk support is per-endpoint, not a platform property.** `/linkedin/user` and `/linkedin/company` take a single string and genuinely cannot be batched — profile enrichment, the dominant cost of any wholesale screen, is stuck at one call per person. `/company/employees` takes `companies[]`; `/user/email` batches 10.
- **412 gotchas** (all documented in code):
  - `company`/`current_companies` filters must be **arrays of URNs**, not bare strings.
  - Company lookups 412 on bare company names / vanity slugs — resolve a URN or LinkedIn company URL first; convert `fsd_company:{id}` → `company:{id}` for job/employee search.
  - Some encoded URNs 412 on `/user/posts` — soft-fail to fallbacks.
- **Response shapes drift across versions**: URNs arrive as string-or-object, display fields nested — normalize defensively (`urnString()`, `textOrName()`, depth-limited key search). An object leaking into a HubSpot property 400s the create.
- **A person's INDUSTRY and COMPANY SIZE are not on the person.** `LinkedinUser` (returned by `/search/sql/users` and `/linkedin/user`) has no `industry` and no `employee_range` field at all — check the schema at `https://api.anysite.io/openapi.json`, not the field list you expect. Both live on `experience[].company`, and the readable industry is on **`industry_full.name`**; the sibling `industry` there is a bare URN (`urn:li:industry:96`) that is useless in a report. Read them off the CURRENT role (the entry with no `end_date`), not `experience[0]` — most-recent-first is not the same as current for someone between jobs. **A depth-limited key hunt will NOT save you here**: it finds the `industry` key, cannot coerce the URN object to a string, and returns null — which is exactly how Throughline shipped an audience report reading "Industry: Not stated, 1000 of 1000" for a thousand people who all have employers. Company size worked only by accident of the same traversal (`employee_range` IS a plain string on that object). When a whole column comes back empty for every row, suspect the field name before you suspect the data. Throughline `companyFirmographics()` in `src/lib/audience/anysite-people.ts`.
- `experience[].company` is an **object**, not a string — the employer name is `company.name`, and the role title is `position` (not `title`). A `pickString(entry, ["company"])` returns null and silently empties the employer out of any job-description corpus built from it.
- ⚠️ **An alias chain ending in `?? 0` cannot tell "absent" from "zero", and for a COUNT those mean opposite things.** SocialOS resolved post like/comment/repost totals through `raw.likeCount ?? raw.like_count ?? … ?? 0`. When `/linkedin/search/posts` returned counts under a key not in the chain, every post stored 0 — and a VoC run whose posts demonstrably had engagement (the fan-out over those same reactions found 64 engagers) rendered an "Engagement by Theme" chart reading 0 for every theme. Nothing logged, because a genuine zero looks exactly like a failed read. Fix (`pickCount` in `lib/anysite.ts`): resolve through a path list that returns `{ value, matched }`, and when NOTHING matched, warn with the payload's **shape** — key names plus one level of nesting, values omitted since posts carry author names and body text — tagged with the endpoint and bounded per process so a 50-post batch can't flood the log. The same helper coerces numeric strings: some endpoints return counts as strings, and a string reaching Prisma's `Int` column throws at write time. Generalize this: **any defaulted numeric field read from a drifting vendor shape needs a matched/unmatched signal**, or the failure is permanently invisible. Same reasoning as the `...CheckedAt` stamp in the Unipile section — a zero is only trustworthy when you know you looked.
- ⚠️ **`/linkedin/search/posts` has no pagination: `count` is the only coverage lever, and `date_posted` decides what fills it.** Found 2026-09-21: a 3-keyword SocialOS topic search over 7 days returned exactly 75 posts (3 x a hardcoded `count: 25`) while LinkedIn's own search showed more for the same term in 24 hours. The call sent no `date_posted`, so Anysite returned the 25 all-time most recent matches and the lookback was applied client-side afterwards, which can only shrink the page. Fix (`runTopicSearch`, `engine.ts`): send the tightest `date_posted` enum (`past-24h` / `past-week` / `past-month`) that covers the lookback so every slot lands inside the window, raise `count` to `TOPIC_SEARCH_POSTS_PER_KEYWORD` (100, shared with the credit forecast), dedupe posts across keywords by activity id (overlapping keywords like `unbound` / `unbound26` were counted and fanned out twice), and log when a keyword fills the ceiling. The ceiling is still a ceiling: a busy event term can exceed it in a week, and there is no second page to ask for. Narrower keywords or a shorter lookback are the only ways to see more.
- ⚠️ **Post engagement counts: `reactions` is an ARRAY, and `/linkedin/search/posts` carries no counts at all.** Verified live 2026-08-05 against production credentials. `/linkedin/user/posts` returns `comment_count` and `share_count` as scalars, but reactions as one entry per TYPE — `[{"@type":"@linkedin_reaction","type":"like","count":6},{"type":"empathy","count":1}]` — so no scalar alias can resolve a like count from it and every post silently stored 0 likes. Sum ALL types (`sumReactions`, `lib/anysite.ts`), not just `like`: LinkedIn splits one audience action across like/empathy/praise/interest, so counting only `like` undercounts a well-received post by most of its reactions. Separately, **`/linkedin/search/posts` returns `comment_count: null`, `share_count: null`, `reactions: null`** — the fields are present, the values are always null. A VoC `topic_search` run therefore cannot produce engagement figures from search results alone. **There is no batch escape hatch here** — unlike the companies case, `/linkedin/search/sql/posts`, `/linkedin/sql/posts` and `/linkedin/posts` all 404 (probed 2026-08-06), so hydration is necessarily one `/linkedin/post` call per post. That endpoint *does* return the figures. SocialOS buys them back in `hydratePostMetrics` (`engine.ts`), gated to VoC runs, charged at `CREDIT_COSTS.FETCH_POST_METRICS`, bounded by `MAX_POST_METRIC_HYDRATIONS_PER_RUN`, and — critically — **only for posts whose counts are genuinely absent**, which is what `LinkedInPost.hasEngagementCounts` exists to tell you. Without that flag you either re-buy figures you already had (every user-posts run) or you never buy the ones you need. Never render a null-derived 0 as a measured zero: that is what made "Engagement by Theme" read 0 across every theme for a run that had found 64 engagers.
- **Rate limiting**: provider cap ~200/min. SocialOS runs a per-process token bucket (180/min) *with a serialization chain* (so `Promise.all` bursts can't all pass the check) PLUS a Postgres-backed cross-replica limiter, since the key is shared.
- **Distinguish per-minute vs daily 429s**: parse the stated reset (`Retry-After` header, "try again in N seconds" body, `retry_after` field). Wait > ~2 min ⇒ daily fair-use cap: **pause that endpoint until reset and fail fast** — blind retries fire thousands of doomed calls.
- ⚠️ **Charge-then-call must refund when the provider fails, and a key outage must stop the run.** 2026-09-24/25: our key started returning `401 {"detail":"Token expired"}`. Every SocialOS lookup site charged credits BEFORE the call, caught the throw, logged and moved on, so every run in every org paid for lookups that returned nothing (a 4-keyword topic search: 40 credits, 0 posts). Fix: every paid lookup goes through `chargeThenCall` (`server/services/provider-charge.ts`), which refunds the exact charge against the same run when `isProviderFailure(err)` (`lib/anysite.ts`: 401/402/403 and quota bodies = "outage", 5xx / 429 / 412-circuit-open / timeouts after the client's retries = "transient"; 404 / 400 / 422 / a plain provider 412 are answers and keep their charge). An outage also trips a per-run breaker (no further calls; run recorded failed with a plain message, rescheduled, never auto-paused) and the per-process health (`markProviderAuthFailure` / `providerAuthDownSince`, cleared on the next 2xx), which skips new runs and holds campaign steps for 15 minutes after the last failure, without charging. One-off settlement for the outage window: `scripts/refund-provider-outage.ts`.
- **Per-endpoint circuit breaker** for 412 storms: 10 failures/60s opens for a 60s cooldown, half-open probe after (SocialOS `anysite-circuit.ts`).
- **Caching**: cache successes (24h) and genuine misses (short negative-cache, ~10 min) — but **never cache failures**: caching a transient `[]` strips that data from every report for a day.
- **Global profile/company cache (SocialOS `linkedin_profile_cache`, `linkedin_company_cache`)**: the same public profile was being re-fetched by every program, every re-score, and every customer independently. These tables key the PUBLIC payload by the **person/company, not the customer**, so we pay once per TTL window fleet-wide (profiles 60d, companies 90d — companies drift slower). Read-through via `server/services/linkedin-profile-store.ts`; one canonical fetch flag-set is used for every write so any cached row satisfies any caller (a row written with fewer `with_*` flags would starve a later caller needing more).
  - **Content rule**: raw public payload ONLY — identity, role, employer, location, about, experience, education, company attributes. **Never** ICP grades, fit reasoning, talking points, or engagement. Sharing the payload across orgs is safe because it's the same bytes Anysite returns to anyone; sharing a judgment would leak a customer's targeting strategy.
  - **Erasure**: `linkedin_profile_forget` is checked before every fetch. A "forget" deletes the cached payload, scrubs the org-scoped rows (`prospects`, `referral_partner_contacts`), and blocks future fetches — without the block, the next sweep just re-scrapes them. Admin console: `/super-admin/dashboard/linkedin-cache`.
  - Prefer this over calling `getUserProfile`/`getCompanyProfile` directly in any new enrichment path. Wired into all four bulk paths: the listening engine, referral scoring, connection enrichment, and the re-enrichment backfill. Call sites with their own candidate/error semantics pass a `fetch` callback (errors propagate untouched); `forceRefresh` skips the read but still writes, for jobs whose purpose is to refresh stale data.
  - **Never write a partial payload.** The invariant is "one canonical fetch shape, so any cached row satisfies any caller". A site that fetches with `with_*` flags off (e.g. identity resolution, which only needs URL+URN) must use `lookupCachedProfile` READ-ONLY — writing its thin payload would hand the enrichment pipeline a profile with no experience to grade.
  - Deliberately NOT cached: the account holder's own profile (voice/identity UI, where a 60-day row could show stale self-data) and one-off user-initiated imports, where freshness is the expectation. Identity resolution stays uncached too — it runs per row during list imports and must not take a DB dependency.
- **Timeouts**: 10s (GTM OS — fail fast into fallbacks; 30s let serial enrichment stack to minutes) to 5 min (SocialOS bulk). Pick per use-case.
- De-dupe provider alert emails (1-hour cooldown per error category) — a run hitting 100 401s must not send 100 emails.
- Cost attribution with a shared key: match Anysite's per-request usage feed to your own call log by (endpoint, ~timestamp) nearest-neighbor (SocialOS `anysite-usage.ts`).

### Unipile — authenticated LinkedIn account management
- Auth: `UNIPILE_API_KEY` in **`X-API-KEY`**; base `https://{UNIPILE_DSN}/api/v1` where the DSN is **per-tenant** (e.g. `api31.unipile.com:16102`). Billing: flat ~$5/mo per connected account, not per call — disconnect accounts when done with them to recycle slots.
- Endpoints: `POST /hosted/accounts/link` (hosted-auth connect wizard; link expires 1h — carry a nonce to prevent forged account attach), `/users/invite`, `/users/relations`, `/chats` + `/chats/{id}/messages`, `POST /posts` (multipart/form-data — let fetch set the boundary), `GET /posts/{url_id}` (retrieve — the id space differs from the two below; see the post-id bullet), `POST /posts/{social_id}/comments`, `POST /posts/reaction` (older copies summarise these as `/posts/{id}/{reactions,comments}`), `GET /users/{id}` (**generates a real "viewed your profile" footprint**).
- **`GET /users/relations` has no published schema and drifts**: the id arrives as `provider_id` / `member_id` / `id` depending on account type and API version, and a headline/employer often rides along for free (read it: paying for a profile scrape to learn what the feed already handed you is pure waste). Normalize defensively and keep the row when only a weaker id survives: a relation you cannot DM is still one you can count and match on. Throughline `normalizeRelation` / `listRelations` in `src/lib/unipile.ts`.
- **`DELETE /accounts/{id}` is cost control, not cleanup.** Any flow that connects an account for a single sitting owes it a delete, and the delete must clear the stored account id EVEN WHEN IT FAILS: keeping the id so a sweep can retry leaves a send path holding an account you told the user you had released. A 404 counts as success. Reference: Throughline's guest-list page (`docs/guest-list-insights.md`, `releaseSession`), SocialOS `releasePartnerAccounts`.
- ⚠️ **Reactions and comments do NOT share a URL shape, and the asymmetry is a trap.** Commenting is `POST /posts/{social_id}/comments`; reacting is `POST /posts/reaction` with **`post_id` in the BODY** (`{account_id, post_id, reaction_type}`, plus optional `comment_id` to react to a comment). SocialOS posted reactions to `/posts/{id}/reactions` by symmetry with the comment route, and **every `engage_post` campaign step 404'd for weeks**. The give-away is in the error body, not the status: `"Cannot POST /api/v1/posts/urn:li:activity:…/reactions"` is an Express **route miss**, while a bad post id on a route that exists comes back `422 errors/invalid_post "Post cannot be found"` — which is exactly what the sibling comment call returned for the same ids. **One of the two paths being real is what made the wrong one look plausible; read the 404 body before assuming the id is at fault.** Also: `reaction_type` is **lowercase** (`like`, `celebrate`, `support`, `love`, `insightful`, `funny`) — the SCREAMING_CASE forms LinkedIn itself uses are rejected, and a reaction read off a scraped post needs mapping, not lowercasing (LinkedIn's `empathy` → `support`, `praise` → `celebrate`).
- ⚠️ **A LinkedIn post has several ids, and Unipile's post routes are split across two of them (verified against the docs 2026-09-01).** `GET /posts/{post_id}` takes the id **visible in the URL** — for an activity URL the **bare numeric** ("if the URL contains activity, use the numeric id … `-activity-7332661864792854528-` => `7332661864792854528`"), and `urn:li:ugcPost:<id>` / `urn:li:share:<id>` for the other post types. The **action** routes (`POST /posts/reaction` body `post_id`, and `POST /posts/{post_id}/comments`) take the retrieved post's **`social_id`**: "The post id visible in url will not work in all case", and Unipile's guidance is to use social_id "on all action interaction to be 100% reliable". So **the only way from a post URL to an actionable id is a retrieve call** — `social_id` is a different id space (an activity URL routinely resolves to a `urn:li:ugcPost:` social id), and no local parsing can produce it. SocialOS sent `urn:li:activity:<numeric>` to both action routes: the URL id in URN clothing, wrong for the action routes *and* for the retrieve route, so `engage_post` and `comment_on_post` had never once succeeded. Two lessons beyond the endpoint list. **Fixing the route alone converts a 404 into a 422** that reads "Post cannot be found" — blaming the post for an id you chose; if a fix moves the error rather than clearing it, the second defect was always there. And **cache the resolution, misses included** (`unipile.resolvePostSocialId`): a comment campaign points every enrollment at one post, so an uncached resolver spends one authenticated read per prospect on a constant, and one deleted post becomes hundreds of pointless reads on the customer's own session.
- **A sender that cannot send is DEAD, not busy — give the deferral an exit.** A `LinkedinAccount` with no `unipileAccountId` made SocialOS's sender lookup return null, and the campaign engine pushed its enrollments forward an hour at a time, every 5-minute tick, forever: 12–45 rows per tick, an error line each time, campaigns still reading "active", and nothing ever escalating. Route the unusable-sender case into the same health path as a webhook disconnect (`markLinkedinAccountNeedsReauth`) so the account flips to `needs_reauth`, the campaigns it stranded auto-pause, and the owner/admins get the one-shot reconnect email. **An infinite retry with a log line is indistinguishable from working, and strictly worse than failing.**
- Webhooks: Unipile doesn't natively sign — verify HMAC only if you proxy-sign, and rely on DB validation of the account-name payload. **Normalize event-name casing and accept synonyms** (`RECONNECTED` vs `RECONNECT_SUCCESS`) — matching only one left accounts stuck "Disconnected". When one product attaches more than one account type per person, give each its own name prefix (`referral::` vs `referral-gmail::`) so the handler routes to the right column.
- **Never trust the connect webhook alone**: a missed hosted-auth notify stranded rows on "Connecting…" forever. Reconcile pending connects against `GET /api/v1/accounts` (match by the `name` set on the hosted link) when serving account state — Throughline `src/lib/unipile-reconcile.ts`; clear pending rows older than 2h that Unipile doesn't have (links expire at 1h).
- **Post-metric field names also drift** (`impression_counter`/`impressions`/`view_counter`, `reaction_counter`/`likes`, …) — read defensively and return `null` on failure so reporting degrades instead of throwing (`getPostMetrics`, `src/lib/unipile.ts`).
- **Never read post metrics on render.** Metrics used to be fanned out per post on every campaign-report view and then discarded — expensive and un-learnable. **Sweep on a schedule, persist, and read the snapshot**: Throughline measures each post at ~24h and ~7d after publish, stores it on `ScheduledPost`, and goes terminal (`src/lib/social-metrics.ts`). Own-post metric reads are NOT `GET /users/{id}` profile reads, so they leave no "viewed your profile" footprint and don't count against the profile-read ceiling below — but they still belong on a cron, not a page load.
- **Don't publish a batch in one loop.** LinkedIn's feed now derives a popularity percentile from a post's first-hour engagement and feeds it into RETRIEVAL, so two posts from one account in the same hour split the audience that would have engaged with either and both rank lower than either alone. Stagger per account (Throughline `src/lib/social-cadence.ts`, ≥3h apart, inside a configured window, forward-jittered). This also satisfies the business-hours + jitter rule below.
- **Which field carries the event name depends on the SOURCE, not the version.** The `account_status` source puts it in `payload.status`; the `messaging` and `users` sources put it in `payload.event` (some versions `type`). Read `event ?? type ?? status` everywhere — including in the log lines. SocialOS's webhook routed on the full chain but *logged* `status` alone while calling it "event", so every messaging and relation webhook (the bulk of traffic) printed `event=undefined`, and the "unhandled event" line printed `undefined` for exactly the payload you'd need it to name. Log the field the label came from (`event=new_relation(event)`) so a future shape change is visible instead of silently landing back on `undefined`, and dump `Object.keys(payload)` when nothing matched.
- **Not every Unipile account has a first-class row on our side, so "no row" is not a fault.** Referral partners connect via token-scoped hosted auth and deliberately have no `linkedin_accounts` row (their `unipileAccountId` lives on `referral_partners`, plus `gmailUnipileAccountId` for the mailbox). Both the message and connection handlers logged that expected case and a genuinely orphaned account id in identical words, on **every event** — eight-plus connected partners produced thousands of lines that read like a broken mapping and buried any real one. Classify before logging (`classifyUnmappedUnipileAccount`): a known partner gets one quiet line naming the partner and which of their two accounts it was; an id belonging to nothing gets a `console.warn`. Suppress per account id per process so a steady-state condition costs one line, not one per event, and let a deploy re-report in case the mapping changed. Same failure shape as the `unipile_read_budget` gap below: **anything keyed off `linkedin_accounts` needs an explicit answer for accounts that legitimately have no row.**
- **Mailboxes (Gmail) ride the same hosted auth** — `providers: ["GOOGLE"]` (the resulting account `type` is `GOOGLE_OAUTH`). This is the reason to route mail through Unipile rather than our own Google app: reading a user's mail needs Google's **restricted** `gmail.readonly` scope, which for external users (e.g. referral partners, who aren't our users at all) means a CASA security assessment plus app verification before you can ship. Unipile already carries that.
- **Mail endpoints.** `GET /emails` → `{ object: "EmailList", items: [...], cursor: string|null }`. Query: `account_id`, `limit` (1–250), `cursor`, `after`/`before` (ISO 8601 UTC **with ms**, exclusive), `role`, `folder`, `from`, `to`, `any_email`, `search`, `meta_only`, `include_headers`. `POST /emails` is **multipart/form-data** (`account_id`, `body`, `subject`, and `to`/`cc`/`bcc` as **JSON-stringified arrays of `{identifier, display_name?}`**) → `{ object: "EmailSent", tracking_id }`. The API reference renders that body as a flat field list, which reads like JSON — it isn't; Unipile's own SDK (`EmailResource.send`) uses FormData. Let fetch set the boundary, as with `POST /posts`.
- ⚠️ **`role` on a mail is a FOLDER role, not a direction flag** — `inbox | sent | archive | drafts | trash | spam | all | important | starred | unknown`. Only `sent` and `inbox` answer "did this mailbox send it"; every other folder is silent and needs a from-address vs mailbox-address comparison. Assuming a `sender`/`recipient` vocabulary here silently corrupts anything built on direction (whose writing you sample, one-way vs two-way correspondence).
- ⚠️ **The same list endpoint returns three different shapes, tagged by `kind`.** `0_ref` is envelope metadata only — **no attendees, no subject, no body**. `1_meta` adds attendees + subject but `body`/`body_plain` are literally `""`. `2_full` has real bodies. `meta_only: true` downgrades results to `1_meta`, so anything needing bodies must not set it — and anything reading bodies must tolerate `""`. Conversely, **do** set it when you only need envelopes: it's cheaper and content you don't need never crosses the wire. `thread_id` is optional (absent on `0_ref`) — fall back to `id`. Attendees are `{ identifier, identifier_type, display_name?, profile_picture? }`; `identifier` is the address, and there is no `email`/`name` alias. Read all of it through normalizers (SocialOS `mailAttendeeAddress` / `mailAttendeeName` / `mailThreadId` / `mailDate` / `mailIsFromMailbox`, `src/lib/unipile.ts`). Bound reads by page count as well as `after`, so a tenant ignoring `after` still hits a ceiling.
- The **mailbox address** lives at `connection_params.mail.username` for Google and Microsoft, `connection_params.mail.imap_user` for IMAP (SocialOS `unipileMailboxAddress`). Source of truth for all of the above is `github.com/unipile/unipile-node-sdk` (`src/mails/*`, `src/attendees/attendees.types.ts`, `src/accounts/ressource.types.ts`) — their published typebox schemas are more precise than the rendered reference docs.
- **Billing footgun: a mailbox is a SECOND ~$5/mo connected account on the same person.** A concurrency cap that counts *partners* undercounts *accounts* by up to 2× once mail is in play.
- ⚠️ **"Access ended" is a billing event for Unipile, and it has more shapes than you think.** Flat per-connected-account pricing means a churned tenant keeps costing money until someone hands the accounts back — and the trigger for that is not one condition. SocialOS disconnected on admin *suspension* only, so the four other ways an org loses access (30-day trial elapsing, beta window closing, subscription cancelled, comp flag removed) each left every sender **and** every referral partner connected indefinitely, unusable and billing. Three lessons. **Derive the "access is over" predicate ONCE** (`hasOrgAccessEnded`) — SocialOS had `isAccountLocked` returning `false` for any org with a beta end date (beta is governed by its own expiry, checked separately in `deductCredits`), so the obvious-looking lock check silently answers "no" for a lapsed beta org: the union of every refusal is a different function from any one of them. **Split the triggers by whether an event exists**: release inline for suspension/cancellation/toggle (the cost stops at the transition), and sweep for the endings that are pure timestamps — nothing fires when a trial elapses, so a cron pass is the only thing that can ever notice. And **gate re-connection on the same predicate**, or the revocation is a treadmill: SocialOS's connect/reconnect gate checked suspension alone, so a lapsed org could re-establish a $5/mo session from the integrations page (and its `/reconcile` route would re-adopt any account whose remote delete had failed, flipping the row back to `active`) the moment the sweep let go.
- **Release accounts inline at the moment the work finishes, not on a sweep.** When you've promised someone you'll drop your access as soon as their sends are done, a cron sweep makes that promise only as tight as the interval. SocialOS revokes both accounts in the same call as the final send (`sendNextPartnerIntro` → `releasePartnerAccounts`), keeping `disconnectCompletedPartners` purely as a retry/backstop. Clear the stored account id regardless of what `deleteAccount` returned: a lingering account in Unipile costs us money, a lingering id is a live credential.
- **Never persist mail content you only needed to read.** SocialOS derives a referral partner's email writing voice by reading a recent window in memory, cutting the quoted chain (`stripQuotedReply`) so only their own prose reaches the model, and storing *only* the distilled style guide — never a body, subject, or quote. Contact addresses come solely from the user's own correspondence, never guessed from a company domain (a guessed address bounces from *their* mailbox and damages *their* sending reputation).
- **Distinguish "we looked and found nothing" from "we haven't looked".** A per-row `...CheckedAt` stamp alongside a score is what makes a zero unambiguous — and it's what lets a scan run again for rows that appeared later without re-scanning the ones already done. Crucially, only stamp after a read that actually **succeeded**: stamping on a transient API failure permanently records "no history" for everyone.

### ⚠️ LinkedIn account safety (SocialOS `docs/linkedin-safety-plan.md` — built after a customer account got restricted)
Any project doing authenticated LinkedIn automation MUST follow these:
1. **Cap profile reads per account per day** (~80, under Unipile's ~100 guidance) with an atomic claim counter; global rate limits are not enough. **Meter by the Unipile account id, and make the "no matching row" case METER rather than fail open.** SocialOS keyed the counter off `linkedin_accounts`, so referral partners — who connect via token-scoped hosted auth and deliberately have no account row — hit the missing-row branch and were exempt from the ceiling entirely; the control protected customers and silently skipped the accounts that belonged to people who'd merely volunteered to make intros. Fixed with a second ledger (`unipile_read_budget`) keyed by account id alone, so any connected account is metered whether or not it maps to a first-class row.
2. **Business-hours window + ±30% jitter** on all **authenticated** reads/sends — fixed-interval cron sweeps read as automation. **Scope this to Unipile, not to enrichment in general.** The control exists because a previously-quiet *account* emitting a 3am burst of profile views looks like a bot; anonymous Anysite scraping uses no one's session, so there is no account for a wall-clock pattern to look suspicious on and windowing it costs ~37% of the day for nothing. SocialOS had the whole referral enrichment sweep windowed + jittered to protect a single Unipile fallback, while the per-account budget that should have covered that fallback failed open — heavy pacing on the safe path, no metering on the risky one. Fix: drop the fallback so the path is fully anonymous, run it unwindowed, and keep read-pacing on the sweeps that genuinely call `viewProfile`.
3. **Warm up new/dormant accounts**: ramp 2→4→7→12→20→34→40 sends/day, advancing only on healthy days; heavy senders can start near historical volume.
4. **Auto-throttle/freeze on restriction signals** (disconnect, 422 `cannot_resend_yet`); re-warm from the floor on reconnect.
5. Alert owners pre-emptively at 80% of read ceiling / 90% of send cap.
6. Prefer webhooks over polling; prefer Anysite (anonymous) over Unipile (authenticated) for enrichment.
7. Ops: pin per-account proxy country in the Unipile dashboard (impossible-travel flags can't be prevented in code).

### ⚠️ Unipile is NOT a cheaper substitute for Anysite (checked 2026-07-26)
Unipile bills flat per connected account, so its calls look free next to Anysite's
per-credit metering. They are not: **every LinkedIn read through Unipile is capped
per account per day, and some are visible to the person read.**

| Read | Unipile limit | Footprint | Use |
|---|---|---|---|
| `GET /users/relations` | first page only, "a few times a day at randomly spaced intervals of several hours"; **avoid fixed-interval polling** | none | **Unipile only** — nothing else can list someone's connections |
| `GET /users/{id}` (profile) | **~100/day/account** | **Visible "Profile Visit"** | **Anysite.** 10K connections would take 100 days AND burn the partner's footprint |
| Posts / reactions / comments / company | **100/day/account** ("limit each action to 100 per day per account") | none stated | **Anysite** for anything bulk |
| Invitations | 80–100/day, ~200/week (paid) | — | Unipile (must be the customer's identity) |
| Search results | 1,000/day standard, 2,500 Sales Nav | — | — |

The rule: **Unipile for things that must BE the account (send, invite, list my
relations, read my own DMs). Anysite for volume.** Anysite is not an over-reliance,
it is the only tool that can screen a 10,000-person network at all.

The real waste isn't vendor choice — it's **discarding free data from a Unipile call
we already make.** `mapRelationToContact` kept only urn/name/url and threw away the
headline the relations feed often carries, and we then paid Anysite to re-learn the
person's role. Capture it and use it to ORDER the paid queue (`lib/referral-triage.ts`).
Never to exclude: a headline is not a title (people write value-prop headlines with no
role), which is why the paid AI title read exists.

**A connection graph is a durable asset; the session that fetched it is not.**
`listRelations` needs the person's live account, but its OUTPUT stays true for months —
people do not un-connect. So the expensive, scary thing (holding someone's LinkedIn
session, at ~$5/mo and standing liability) should last one pull, while the valuable
thing (who they know) persists. SocialOS's referral *listening* campaigns are built on
exactly this: pull the book once, `deleteAccount` in the same pass, and from then on
answer "which of our partners knows this prospect?" from stored rows. That is what lets
you ask a favour of someone who is not your user and has no ongoing relationship with
your product.

Two implementation notes, both learned the hard way:
- **Store the join key normalized, at write time.** Provider identifiers are useless as
  a join: the same person arrives as `urn:li:fsd_profile:ABC` from Unipile and a bare
  `ABC` from Anysite, with URLs differing by scheme and trailing slash. Bulk flows get
  away with normalizing in memory; a per-prospect reverse lookup against every contact
  in the org does not. Normalize through the *same* function the in-memory matcher uses
  (`urnKey` / `normalizeProfileSlug`) into indexed columns — a second set of rules that
  almost agrees produces a lookup that silently finds nobody.
- **Release inline, not in a sweep.** "We pull your connections once and disconnect" is
  the promise that gets a non-user to connect at all. A promise kept minutes later by a
  cron job is a weaker promise; keep the sweep only as a backstop for when the inline
  release throws.

## 6. Web research, scraping & AI-search measurement — Parallel.ai, Firecrawl, Jina, direct fetch, GEO engines, search consoles

**Scrape chain convention** (Throughline `scrapeWebpage`, `src/lib/knowledge.ts`): Firecrawl → Jina Reader → SSRF-safe direct fetch. Prefer Parallel.ai `/v1/extract` where configured. Consumers: knowledge ingest, and Product-registry seeding (`src/lib/products/seed.ts` — landing-page scrape + one optional `/v1/search` for competitor context, metered `resourceType: "product_seed"`, charged to the org as the `usage_product_seed` credit at enqueue).

### Parallel.ai (`api.parallel.ai`) — AI-native web research (ContentOS `src/lib/parallel.ts`)
- Auth: `PARALLEL_API_KEY` via **`x-api-key`**. Endpoints: `POST /v1/search`, `POST /v1/tasks/runs` + `GET /v1/tasks/runs/{id}/result` (long-poll), `POST /v1/extract` (≤20 URLs), `POST /v1/monitors`. Task processors `lite|base|core|pro|ultra` ($0.005→$0.30/run); search $0.005; extract $0.001/URL.
- **The metering pattern to copy everywhere:** every paid wrapper *requires* a meter object naming the org the spend belongs to — there is no way to call a paid endpoint without attribution. A `UsageEvent` with real vendor COGS is written the moment the call succeeds. Free status/result GETs are not metered. Budget expectation ≈ $150/customer/mo, reconciled in an admin spend rollup.
- **Outbound personalization research** (`src/lib/campaign-enrichment.ts`): opt-in per campaign (`plan.outbound.enrichResearch`). Uses `/v1/search` (fast enough for the synchronous SocialOS enrollment send; a polled task run would stall it) + a cheap Haiku synthesis into honest insight lines fed to the 1:1 rewrite. Results are cached in `ContactResearchCache` keyed by (org, company-domain | person-linkedin/email) so a company is researched **once** and reused across its contacts and campaigns (TTL 45d) — spend scales with #companies+#people, not #contacts. Billed as the `outboundResearch` credit on a cache MISS only; a cache hit (including a cached-empty "found nothing") is free.
- **Attendee identity fallback** (`findLinkedInUrlByWebSearch`, `src/lib/anysite.ts`): the last rung of the event-attendee resolution ladder. Anysite resolves people from INSIDE LinkedIn (profile URL → reverse email → name+employer search); a self-serve registrant with a personal address, no profile URL and an employer we can only infer from their email domain falls through all of it — and that is most of a public form's traffic, whose agendas then generate against an empty profile and come out identical to each other. One `/v1/search` scoped to `linkedin.com` proposes a `/in/` URL, which is fed back into the normal Anysite lookup so caching/posts/company are unchanged. **The candidate is never trusted:** the resolved profile's real name must pass `personNamesMatch` against the attendee's, because a name search always returns SOMEBODY and a stranger's profile produces a confident, specific, wrong agenda — strictly worse than no profile at all. Requires an `organizationId` (no attribution, no call).

⚠️ **Every imprecise rung of the enrichment ladder now corroborates the EMPLOYER, and initials are not a name.** Live (GRTW, Ariox): a company-filtered people search for "Greg Williams" at an insurance broker returned a clinician in Wales as its first hit and the ladder took it (`findUserByName` accepted `filtered[0]` blind); a form filled in as "CF"/"ET" was searched as a name and matched a French gérant; one-token addresses (`murphya@`, `elliottj@`, `amiller@`) derived no name, so the ladder stopped and those registrants got a company guessed from the domain and nothing else. ### Firecrawl (`api.firecrawl.dev`) — JS-rendered scraping
- Auth: `FIRECRAWL_API_KEY` Bearer. Endpoints: `POST /v1/scrape`, `/v1/map`, `/v1/search`.
- **Format selection matters**: request `rawHtml`/`html` when you need script/iframe tags (tech detection — markdown strips them; `onlyMainContent: true` strips the head/footer where tracking scripts live). Leave JS rendering off unless needed (halves cost). `waitFor: 2500` for JS modals.
- **The rendered DOM lies about parameterized SPA views.** A JS-app listing at `?page=N` can render its DEFAULT page regardless of the param (client router resets state at hydration), so rendered markdown of every pagination page comes back as the same grid — observed live on a Nuxt conference agenda: 60 rendered pages deduped to a quarter of the catalog. The `rawHtml` format carries the truth: the server-embedded state payload (`__NUXT_DATA__` devalue / `__NEXT_DATA__` JSON) holds that page's real items with exact ISO datetimes plus the listing's own pagination metadata (`total`, `pages`, `current_page`). The event scraper decodes it in `extractEmbeddedListing` (`src/lib/event-scrape.ts`) — reuse that, don't re-render harder.
- Contract: **never throws** — returns a structured `{ok, status}` outcome; a Firecrawl failure degrades to the next scraper in the chain. Self-disables when the key is unset.
- Response shapes drift (links as `string[]` vs `[{url}]`; search results under `data`/`data.web`/bare) — coerce defensively. Rate-limit with your own token bucket (60/min) — batch tech-detection runs 429-storm otherwise.
- Timeouts 30–60s. Log `err.cause` to get the real TLS/network error code.

## 7. Voice — Deepgram + ElevenLabs

Two halves, don't confuse them: **STT is always Deepgram**; **TTS is Deepgram (budget) or ElevenLabs (premium)** — auto-prefer ElevenLabs when its key is present, allow `TTS_PROVIDER` override (Portal `lib/agent/voice.ts`).

### Deepgram
- Auth: `Authorization: Token $DEEPGRAM_API_KEY`.
- STT: `POST https://api.deepgram.com/v1/listen?model=nova-2&smart_format=true&punctuate=true` (recorded clips) or streaming from the browser.
- **Browser streaming pattern**: mint a short-lived (60s TTL) browser token via `POST /v1/auth/grant` so mic audio streams direct from the browser and the long-lived key never ships to the client (ContentOS voice routes).
- TTS: `POST /v1/speak?model=aura-asteria-en&encoding=mp3`.
- Degrade to typed-only mode when unconfigured (return a `voice_not_configured` signal, not a 500).

### ElevenLabs
- Auth: **`xi-api-key` header**, always server-side proxied — never expose the key to the browser.
- Endpoint: `POST https://api.elevenlabs.io/v1/text-to-speech/{voiceId}[/stream]`, `model_id: "eleven_turbo_v2_5"`, `voice_settings: { stability: 0.4–0.45, similarity_boost: 0.7 }`, `Accept: audio/mpeg`.
- House voices: **Rachel `21m00Tcm4TlvDq8ikWAM`** (default/partner/female), **Adam `pNInz6obpgDQGcFmaJgB`** (male). Override via `ELEVENLABS_VOICE_ID*` env vars.
- Cap input text (2000–5000 chars); strip code fences and spell out acronyms before speaking; `Cache-Control: no-store` on audio responses.

### Browser audio on iOS (the silent-assistant gotcha)
⚠️ **Mobile Safari grants audio playback per HTMLAudioElement, and only from inside a user gesture.** A `new Audio(url)` per sentence therefore creates a fresh, never-gestured element whose `.play()` rejects every time — the partner transcribes, streams and fetches TTS perfectly and produces no sound, with no error anywhere. The fix is a SINGLETON element played (silently) inside the tap and reused for every clip (Throughline `src/lib/voice/audio-unlock.ts`). Three rules that go with it:
- **Unlock synchronously, as the first line of the tap handler.** The gesture is gone after the first `await`, so unlocking behind the token fetch is the same bug in a different place.
- **Set `playsinline`**, or iOS takes the element fullscreen and the reply hijacks the whole screen.
- **Share ONE AudioContext** between the unlock and the mic. A context constructed outside the gesture starts `suspended` and silently drops every captured frame; hand the unlocked one to the capture code rather than letting it build its own, and never let the capture code close a context it did not create.
- **Half-duplex on speakerphone.** The assistant's own reply goes back into the mic, gets transcribed, and the partner answers itself. Mute while thinking and speaking — but mute by sending ZEROED frames, not by closing the socket (Deepgram drops a stream that goes quiet, and the reconnect costs the utterance in progress), and unmute the instant the reply ends so a spoken approval still reaches the gate.

## 8. Voyage AI — embeddings

- Auth: `VOYAGE_API_KEY` Bearer → `POST https://api.voyageai.com/v1/embeddings`.
- Models in use: **`voyage-3-lite` @ 512 dims** (ContentOS + SocialOS knowledge bases), **`voyage-3.5` @ 1024 dims** (formerly Portal Emily memory; retired). **The dimension MUST match the pgvector column** (`VECTOR(512)` vs `VECTOR(1024)`) — validate returned dimensions.
- Set `input_type: "document"` for indexing and `"query"` for search — they embed differently.
- **Batch up to 128 texts per request** and **sort results by the echoed `index`** (order is not guaranteed). Chunking that works: ~800 tokens, 100 overlap, truncate inputs ~16k chars.
- Retry 429/5xx/network with delays [0, 1s, 3s, 8s]; other 4xx fail immediately; 30s timeout. Optional at boot — a missing key only disables indexing.
- Memory-layer principle (ContentOS `docs/memory-layer.md`): **don't vectorize raw transcripts** — raw volume is unbounded; map-reduce overnight into bounded distinct insights, embed those.
- ⚠️ **Similarity thresholds are a property of the MODEL, not of the app — pin them next to a note naming the model.** SocialOS's `find_relevant_content` node exposes High/Moderate/Low, which are cosine floors (0.60 / 0.48 / 0.35) tuned against `voyage-3-lite` @ 512 dims. Swapping the embedding model silently redefines every one of those user-facing settings: the same "High" would surface a different set, and nothing errors. They live in `src/lib/relevant-content.ts` with the model named in the comment; re-tune them in the same PR that changes `VOYAGE_MODEL`.
- **Chunk-level search and document-level search are different queries — don't reuse one for the other.** Retrieving top-N *chunks* is right for stuffing a prompt (more passages is just more context, and three chunks of one page are fine). It is wrong wherever results are presented as *things we published*: three chunks of one blog post is one recommendation repeated three times, and a caller asking for 3 results gets a single asset. SocialOS keeps both — `searchKnowledgeBase` (chunks) and `searchKnowledgeBaseDocuments` (`DISTINCT ON (d.id)`, keeping each document's best chunk as the excerpt). **Apply the similarity floor inside the query, before the LIMIT** — filtering after it, which the older `getKnowledgeBaseContext` does, can return nothing while qualifying documents sit just outside the window.
- **A retrieval threshold alone can't say _why_ something matched, and some consumers need that.** A HubSpot note reading "here's what we've published on their topic" is only useful with the connection stated. SocialOS pairs the vector floor (deterministic, the actual branch decision) with one cheap Haiku pass that confirms each hit and writes a one-sentence rationale. Order matters: **the AI pass may only ever reject, never resurrect**, and when it fails the vector matches stand un-annotated — otherwise an Anthropic outage silently switches a campaign branch off.

### Slack
- Two auth modes: per-workspace **OAuth v2 bot tokens** (multi-tenant products) or a static `SLACK_BOT_TOKEN` (internal single-workspace). Minimal scopes: `chat:write` (+ `chat:write.public`, `channels:read`, `groups:read`; add history/users scopes only when reading).
- Inbound (Events API): verify `SLACK_SIGNING_SECRET` HMAC (`v0:{timestamp}:{rawBody}`, SHA-256, `timingSafeEqual`, 5-min replay window); answer `url_verification` challenges; **ack 200 fast, process async**; ignore your own bot's posts; **de-dupe on `event_id`** and set the seen-flag only *after* a successful write so Slack's retry recovers failures (GTM OS `server/routes/chat.js` is the reference).
- Sending: on `not_in_channel`, auto-`conversations.join` and retry once; chunk to ≤48 blocks/message (limit is 50) with pauses; `unfurl_links/unfurl_media: false`; map `ok:false error:'ratelimited'` to a 429 and honor `Retry-After`.
- **Always send `text` alongside `blocks`.** Blocks don't reach the push notification, the sidebar preview or the notification email — `text` is what those render, so a blocks-only message shows up on a phone as "SocialOS sent a message". Treat `text` as the one-line summary and front-load the disambiguator (SocialOS prefixes the campaign name), because a mobile alert truncates from the right.
- ⚠️ **An alert that names an action without linking to it is a dead end.** SocialOS's v1 engagement notification was one line — who, what verb, link to the *post*. Every failure mode traced back to that shape: a workspace running several campaigns into one channel couldn't tell which campaign fired; "X commented on your post" linked to the post, dropping the reader into a hundred-comment thread with no way to find X's comment; and there was nothing to click. The fix isn't more copy, it's carrying the context that already exists in the DB: quote the engagement text inline (`Prospect.engagementContent` — already stored, just never sent), state the campaign, state the step the workflow runs next, and end with link buttons. **Link buttons (`type: "button"` + `url`) need no Slack app configuration** — no Interactivity Request URL, no signing-secret round trip — so an actionable message costs nothing beyond the block layout. Escape `&`, `<`, `>` in anything a prospect wrote before it reaches mrkdwn; an unescaped `&` in a headline eats the rest of the line.
- **LinkedIn has a per-comment permalink; use it.** `https://www.linkedin.com/feed/update/urn:li:activity:<activityId>?commentUrn=<enc>&dashCommentUrn=<enc>`, where the params are `urn:li:comment:(activity:<activityId>,<commentId>)` and `urn:li:fsd_comment:(<commentId>,urn:li:activity:<activityId>)` percent-encoded with `(`/`)` as `%28`/`%29` (LinkedIn encodes them; `encodeURIComponent` doesn't). Both params are needed — which one scrolls depends on which feed the viewer's session lands on. `buildCommentPermalink`/`extractCommentId` in `lib/anysite.ts`; stored on `Prospect.engagementUrl`. **Anysite's `/linkedin/post/comments` is not documented to return a comment urn** and the key varies where it does, so `normalizeComment` walks an alias list and everything downstream falls back to the post URL — but the miss is *logged* (bounded per process), not swallowed, per the matched/unmatched rule in the Anysite section. Guard hard against accepting an *activity* urn as a comment id: it builds a confident link to a comment that doesn't exist, which is worse than the fallback.
- Reading channels: paginate with cursors, bound page counts, and filter noise subtypes carefully — a blanket `if (msg.subtype) continue` silently drops file shares and thread broadcasts (Portal lesson).
- OAuth `state`: HMAC-signed payload, verified with `timingSafeEqual`; upsert installs so re-install refreshes the token.
- The Events request URL is verified at app-creation time — deploy the endpoint (answering challenges) *before* configuring the app.
- **Throughline's Slack app** (`src/lib/slack-app.ts`, setup `docs/slack-app-setup.md`): per-BRAND OAuth installs of one operator-owned app (`SLACK_CLIENT_ID/SECRET` env; credentials-not-flags — settings card shows a setup notice when unset). Tokens on `Organization.slack*`, connect flow mirrors HubSpot's (signed `oauth-state` CSRF guard, provider `"slack"`). It does TWO things. (1) Outbound-reply alerts (`slack-reply-alert.ts`, fan-out leg of the Smartlead webhook) to the brand's chosen channel — fired even/especially when no HubSpot task could be created, silent on `duplicate` so a chatty thread doesn't re-ping, and silent on an AUTO-REPLY (out of office / left the company / bounce — see the Smartlead auto-reply note), which never reaches this leg at all. Channel saves are VERIFIED (conversations.join + a test chat.postMessage) so "saved" means deliverable, not row-written; a reconnect into a DIFFERENT workspace clears the stored channel id (it points nowhere there). (2) **The GTM Partner over Slack** (`src/lib/assistant/slack-runner.ts` + `/api/webhooks/slack`): @mentions, DMs, and follow-up replies inside a thread the bot is already in run the SAME `runPartnerTurn` engine with the SAME full tool registry, core system prompt (`assistant/partner-prompt.ts` — shared with the chat route precisely so surfaces can't drift), approve gate (a "yes" in the thread executes the pinned proposal — the deterministic path, not a Slack bypass), and per-turn `appChatTurn` credits. Slack users are NOT ContentOS users: `userId` is null in the tool ctx and threads live in `SlackAssistantThread` (transcript + pendingAction per Slack thread; DMs are one rolling thread `"dm"`). Events endpoint follows the fleet Slack contract above: signing-secret HMAC (`SLACK_SIGNING_SECRET`, third credential — reply alerts work without it, the partner's ears don't), url_verification, fast-200 + detached processing (a partner turn blows Slack's 3s retry deadline), bot_id/self filtering in `parseSlackEvent`, claim-first dedupe on `event_id` (`SlackEventReceipt`, P2002 = already handled). ⚠️ **`app_mentions:read` alone makes the bot look broken in the exact conversation it just started**: nobody re-@mentions a bot on every line of a thread they're already having with it, and Slack delivers NO event for an unmentioned message without `channels:history`/`groups:history` + `message.channels`/`message.groups` — so there is nothing to parse and nothing to log; it is silent by construction. Those scopes are now requested, which means EVERY message in every channel the bot sits in hits the endpoint: a plain message is answered only when it is a reply inside a thread with an existing `SlackAssistantThread` row (checked BEFORE the receipt claim, so channel chatter writes no rows), and an @mention inside a thread — which arrives TWICE, as `app_mention` and as `message.channels` under two different event_ids that `event_id` dedupe cannot relate — is dropped on the message leg via `isMentionTwin` against `slackBotUserId`. Scope additions only bind after each install RECONNECTS. ⚠️ **The partner's memory of a thread was its OWN transcript only**, so a human replying to a reply-ALERT — the single most likely thing to ask about, and a message the app itself posted before any conversation existed — was answered by a model that could not see it, and asked the user to paste back the message on their screen. The first turn in a channel thread now reads it via `conversations.replies` (`fetchSlackThreadMessages`) and seeds `threadContextBlock` into the system prompt, authorship-tagged so the model knows the alert is something IT said; later turns don't need it because every subsequent thread message is itself a turn. Best-effort: a not-yet-reconnected install throws `missing_scope` here and still answers, contextless. **Brand resolution is (team, channel), never team alone** — an agency connects ONE workspace to many brands, so: alert-channel match → that brand; single brand on the team → it; several → ask for disambiguation, never guess (answering would ground in and mutate the wrong customer's workspace). Trust model: workspace reach = brand authority (the Linear/GitHub-app boundary) — documented in the setup guide, decided by whoever connects the workspace. Keep `SLACK_BOT_SCOPES` and the manifest's scope list in sync — the authorize URL sends the code list and Slack rejects undeclared scopes; scope additions require a reconnect per install. This module is distinct from `slack.ts` (internal #sales incoming webhook) — don't merge them; one is a customer surface, the other an internal ping.

### Web Push (Throughline — `src/lib/push.ts`, `public/sw.js`)
- Not a vendor: the browser's own push services (FCM, Mozilla, Apple) reached through the `web-push` library and a self-generated VAPID key pair (`npx web-push generate-vapid-keys`). Credentials-not-flags: with `VAPID_*` unset the Activity screen shows an operator setup notice and nothing is ever sent.
- Subscriptions are per BROWSER, keyed on the push service's `endpoint` (globally unique, so it is the table's unique key and a re-subscribe upserts). Rows live in `PushSubscription`, bound to a user, cascade-deleted with them.
- ⚠️ **Only 404/410 means "gone"** — prune the row on those and nothing else. A 429 or 5xx is the push service having a bad afternoon; deleting on it silently unsubscribes the user's phone and nobody finds out until they miss something.
- ⚠️ **`web-push` has NO default socket timeout.** The fan-out is awaited inside `createNotification`, so pass `timeout` (we use 5s) or a wedged endpoint holds a product request open.
- ⚠️ **The worker file is fetched cookie-less**, exactly like a PWA manifest — it must be in the proxy's public path set or `serviceWorker.register` gets the login redirect and push never arms, with no error anywhere a user would see.
- The SW has **no `fetch` handler by design**: one that caches can serve a stale deploy, and Throughline runs with version-skew protection unset.
- iOS: web push needs the PWA installed to the home screen, on 16.4+. `PushManager` simply does not exist in mobile Safari otherwise, so detect that case and say "add it to your home screen" rather than "unsupported".
- Payload is `{title, body, href, tag}`; `href` is validated as an internal `/dashboard` path resolving to a real capability (same gate as the partner's handoff chips) before it ever reaches a device. Same `tag` collapses rather than stacks on the lock screen.

### Microsoft Teams (Portal)
- Per-client **incoming webhook URL** stored on the client record — the URL is the credential (treat it as a secret). POST a legacy **MessageCard** (`@type: MessageCard`, `themeColor`, `potentialAction`/`OpenUri`).

### Gmail API (formerly Portal — Emily's mailbox; Emily retired Sept 2026, lessons kept)
- Google OAuth2 web-app flow; **narrow scopes by design**: `gmail.send` + `gmail.readonly` only. `access_type=offline` + `prompt=consent` to guarantee a refresh token; `hd=<domain>` + `login_hint` to pin the workspace.
- **Refresh token encrypted at rest** (AES-256-GCM).
- **Inbound via History-API polling with a persisted cursor, not Pub/Sub push** — Workspace domain-restricted-sharing policy blocks the Pub/Sub publisher grant push needs. Don't fight it; poll.
- OAuth footgun: the redirect URI must be **byte-identical** between the auth request and token exchange — compute it in exactly one place.

## 10. Cold email — Smartlead, Lemlist

### Smartlead
- Auth: long-lived full-access key as **`?api_key=` query param** (per-tenant, stored on the org/client record, not env). Base `https://server.smartlead.ai/api/v1`.
- **Agency accounts: ONE account, every customer a "client" inside it — so almost every read is account-wide and must be narrowed per brand.** How agencies actually run Smartlead is one account with a client per customer, which means each ContentOS brand carries the SAME api key and differs only by `Organization.smartleadClientId`. `client_id` on `POST /campaigns/create` scopes the campaign we create, but **`GET /email-accounts/` ignores clients entirely and returns every client's mailboxes** — unnarrowed, the campaign sending-account picker offered every customer's inboxes at once, unlabelled, with a source comment asserting the list "is already the right client's". It never was. Mailbox rows also carry the inbox's configured `signature` (HTML) — the one place in the stack a sender's signature already exists, so email designers pull it (`htmlSignatureToText`) instead of making the operator retype it. `listSmartleadEmailAccountsForClient` narrows on the `client_id` read BACK off each mailbox rather than trusting a filter query param, because a silently-ignored param is indistinguishable from a working one on this vendor (see the docs-drift lesson below) and the failure mode is offering another customer's inbox as a valid sender. When NO mailbox carries a `client_id` it degrades to the full list flagged `scope: "unfiltered"` and the UI says so — an empty picker would read as "this customer has no mailboxes" instead of "we couldn't tell them apart". `GET /client/` lists the account's clients (`listSmartleadClients`) so the operator picks a customer by NAME; the id is not discoverable from inside ContentOS and a mistyped one silently re-scopes a brand. `Organization.smartleadClientName` caches that name for display only, never for resolution.
- **Use `/campaigns/{id}/analytics` for aggregates** — the older `/statistics` endpoint returns paginated *lead-level* rows, not totals (burned the Portal).
- Response shapes are unstable (array of per-step stats to sum, or wrapped in `data`/`statistics`/`stats`, or flat) — parse defensively and keep per-endpoint diagnostics (`fetchSmartleadCampaignStatsWithDiag` pattern: record status/type/keys/preview per attempted endpoint).
- Pushing sequences: `POST /campaigns/{id}/sequences` **replaces** all steps — naturally idempotent for re-pushes. Personalized 1:1 sends via campaign-scoped lead custom-field merge keys. Agency accounts scope by `client_id`. **The per-step variants array key is `seq_variants`, NOT `variants`** — a `variants` key is rejected with `400 "sequences[0].variants is not allowed"`. This matches the GET response shape (`seq_variants`) our stats parser reads. Each variant is `{ subject, email_body, variant_label }`; `email_body` is HTML. `variant_distribution_type` must be **`MANUAL_EQUAL`** (not `MANUALLY_EQUAL`, which 406s with "Unsupported value"). The three distribution modes map to the UI's A/B options: `MANUAL_EQUAL` (equal split), `MANUAL_PERCENTAGE` (explicit per-variant %), `AI_EQUAL` (AI-optimized).
- **⚠️ The published Smartlead docs are STALE and self-contradictory on this endpoint — the live API is the only ground truth.** The help-center "Full API Documentation" copy-paste example (helpcenter.smartlead.ai/en/articles/125) literally shows `variants` + `variant_distribution_type:"MANUALLY_EQUAL"` — the EXACT two values the live server rejects (400 then 406). The `save-campaign-sequence` reference page's own overview contradicts its own example and says use `seq_variants`. Original code was copied from the stale example, which is why it 400'd/406'd in prod. **Lesson: when a live 4xx names a field, pull the WHOLE payload schema and reconcile every field against the actual API response in one pass — don't fix the one field the error names and redeploy, and don't trust the docs over a live rejection.** A real end-to-end push against a live key is the only thing that fully closes a sequence-schema change; the docs can't.
- **`GET /campaigns/` is account-wide on an agency key**, exactly like `/email-accounts/`: it returns every client's campaigns. `listSmartleadCampaignsForClient` narrows on the `client_id` read back off each campaign (never a filter query param this vendor may silently ignore) and degrades to the full list flagged `scope: "unfiltered"` when no campaign carries the field — same contract as the mailbox picker, pinned in `smartlead-client-scoping.test.ts`.
- **A campaign created via the API has NO sending inboxes assigned.** `GET /campaigns/{id}/email-accounts` reads what's assigned (`listSmartleadCampaignEmailAccounts` — rows sometimes nest under `email_account`); `POST /campaigns/{id}/email-accounts` assigns (`assignSmartleadEmailAccounts`, which no-ops on an empty list, so "clear all" is not expressible). Unassigned means Smartlead decides, which on an agency account may not be the brand's own mailboxes — any surface that creates campaigns must offer the assignment picker (the events delivery panel does). ⚠️ **In practice "Smartlead decides" can mean NOBODY sends: a live delivery campaign with zero assigned inboxes kept scheduling triggers forever and executed none of them — every lead "Overdue", every trigger "0 of N mailboxes used", no error anywhere.** `ensureSmartleadSendingInboxes` is the self-heal: when a campaign has none assigned it assigns the brand's own inboxes (healthy preferred), refusing only on an agency account whose mailbox list could not be narrowed to the brand's client (`scope: "unfiltered"` — auto-assigning there could put another customer's inboxes on the campaign). It runs on every event registration (`deliverViaSmartlead`) and continuously from the delivery sweeper (below); pinned in `smartlead-sending-inboxes.test.ts`.
- **Starting a campaign is gated on BOTH a schedule AND ≥1 lead** — Smartlead's "Review and Launch" stays disabled until each is set, and the API mirrors it. Schedule: `POST /campaigns/{id}/schedule` (`setSmartleadCampaignSchedule` — `timezone`, `days_of_the_week`, `start_hour`/`end_hour`, `min_time_btw_emails`, `max_new_leads_per_day`, optional `schedule_start_time`). Run status: `POST /campaigns/{id}/status` with `{ status: "START" | "PAUSED" | "STOPPED" }` (`setSmartleadCampaignStatus` / `startSmartleadCampaign`; START is idempotent). ⚠️ **The `days_of_the_week` integer encoding is NOT trustworthy from the docs — verify against a live key** (we default to `[1,2,3,4,5]` for weekdays); same lesson as the sequence-schema gotcha above. Verified live: the payload we send is correct as sent.

- **A lead carries only the fields `buildLead()` sets, so those are the ONLY merge tokens a templated body can use**: `{{first_name}}`, `{{last_name}}`, `{{company_name}}`, `{{job_title}}` (`SMARTLEAD_MERGE_TOKENS` in `lib/smartlead.ts` is the list, and it lives next to the builder so the two can't drift). Nothing pushes CRM properties across, so a HubSpot property name in braces is not a merge field: it goes out as literal braces to every recipient, with no error anywhere. This was a live near-miss — the GTM Partner invented `{{contact.<hubspot property>}}` for a 288-person medtech sequence — so both the partner's email tools and `read_page_personalization` quote the array rather than reasoning about it. ⚠️ The corollary for personalization talk: in `standard` delivery the drafted words go out verbatim, so "every email opens with their first name" is true only if the copy carries the token. The 1:1 rewrite is the other mode (`plan.outbound.deliveryMode === "personalized"`), and `outboundDeliveryMode()` defaults to `standard`.
- **A reply cannot be made to end a campaign from the flow graph.** SocialOS exits a replier from the remaining LinkedIn touches on the forwarded event, and the HubSpot follow-up task is automatic — but emails 2..n are the Smartlead sequence's own steps (one enrollment per contact, see the note below), and nothing in the graph or in this codebase stops them. So stopping the emails is a Smartlead SETTING, which `setSmartleadStopOnReply` now writes at campaign-create time (`POST /campaigns/{id}/settings`, `stop_lead_settings: REPLY_TO_AN_EMAIL`) on both writers — the bulk push and the SocialOS provisioner. ⚠️ **Create time only**: changing it on an existing campaign would override a deliberate operator choice in the Smartlead UI. ⚠️ **A 200 is not proof** (the standing lesson for this vendor), so the write is READ BACK off `GET /campaigns/{id}` and the outcome is recorded on `outboundRefs.smartlead.stopOnReply` as `confirmed` / `unconfirmed` / `failed` with a detail line — `read_campaign_emails` reports it, and a campaign pushed BEFORE this shipped carries no value, which reads as "unknown", never "off". The field name and enum value came from the vendor docs and want confirming against a live key. Any surface that reports on an `email_replied` branch must not imply it ends the campaign.
- **Per-step gaps come from the campaign FLOW, not a constant.** `saveSmartleadSequence` hardcoded `delay_in_days: 3` for every step after the first, which silently overrode every wait a user drew on the canvas: a live 288-contact sequence deliberately paced 2 / 5 / 7 days sent flat 3-day and no surface said otherwise. Nothing else persists a cadence (the plan has no field; the HubSpot nurture route takes one uniform gap from its own request body), so the delay nodes between `send_email` steps ARE the record of intended pacing — `emailCadenceFromFlow` (lib/campaign-flow.ts) walks the graph from the trigger and banks the delay reaching each email step, shortest path wins on a branch, step 1 forced to 0 (Smartlead fires it on enrollment), a sub-day gap floored at 1 day (Smartlead reads 0 as "send with the previous step"). Both writers pass it: the bulk push and the SocialOS provisioner. ⚠️ **A contact is handed to the email sequence ONCE** — `enrollContactInEmail` claims one slot per (campaign, email) — so on a LinkedIn-orchestrated flow only the FIRST `send_email` node a contact reaches enrolls them and Smartlead's own step delays pace emails 2..n; later `send_email` nodes do not send anything themselves. `/api/socialos/send-email` reads the node's `emailIndex` and answers `{ status, emailIndex }` so the cases are distinguishable: `enrolled` (entered the sequence at this node), `in_sequence` (already in it from an earlier node, Smartlead sends this email on its cadence), `already_enrolled` (a repeat of the entry node), `email_not_found` (index past the sequence), plus `no_email` / `email_unavailable` / `campaign_not_found`, all 200s. A contact whose FIRST email node is a later index still starts at Smartlead step 1 (Smartlead cannot start a lead mid-sequence); that is logged. Anything that describes a flow must therefore not imply each email node fires its own send.
- **A campaign's personalized-page URL is a real merge field** (`{{personalized_page_url}}`, `PERSONALIZED_PAGE_FIELD`): when the campaign holds a PERSONALIZED-access content piece among its assets, `resolveLeadContexts` gives each lead its own URL from that page's `personalizedLayout.contactSlugs` map (`lib/campaign-personalized-page.ts`). It rides the shared lead resolution, NOT the individual upload sites, because the push, the message test and the background 1:1 rewrite all re-resolve and re-upsert leads — a field attached in one of them would be dropped by the next. The slug map is the only source (a slug is issued at distribution and kept forever, so it is exactly the set of people the page can serve), and a recipient with no issued slug gets NO field rather than a link that 404s.

#### Getting a campaign out of Draft (the "why aren't my emails sending" trap)

**Two different paths load leads, and EACH must own the schedule and the start for the campaigns it loads.** Getting this wrong does not error anywhere: the campaign sits in `DRAFTED`, fully configured, sending nothing, until a human asks why.

- **LinkedIn-orchestrated campaigns never bulk-load leads** (they drip in one-per-contact as the flow reaches an email step via `enrollContactInEmail`), so launch can't start them (0 leads). The SocialOS programmer sets the schedule at provision time (`ensureSmartleadCampaign`) and the campaign starts on the first drip-in lead.
- **Email-only campaigns are bulk-loaded** by `runSmartleadPush`, which now also schedules and starts them. ⚠️ **This did not exist**, and there was exactly ONE `startSmartleadCampaign` call site in the whole codebase (the drip path). A real 665-contact campaign was bulk-loadable, launch-gated correctly, and still sent nothing for twelve days. If you add another way to get leads into a Smartlead campaign, it owns the schedule + start too, or it inherits this bug. The paths that comply today: the bulk push, its 1:1 personalization job, the SocialOS drip, and **event registrations** (`deliverViaSmartlead` in `src/lib/event-delivery.ts` starts a still-DRAFTED campaign after its first lead lands, setting the default schedule if none is stored; PAUSED/STOPPED is an operator's deliberate state and is never overridden). The event delivery picker sets the TRANSACTIONAL schedule on campaigns it creates (`EVENT_DELIVERY_CAMPAIGN_SCHEDULE`: every day, 00:00-23:59 — the agenda promise is "in a few minutes", and the 9-5 outreach default held a real registrant's email overnight), and `deliverViaSmartlead` re-asserts that window on EVERY registration (owner directive 2026-08-24) — an event campaign's send window is owned by code, and a narrower window set in Smartlead's editor is deliberately overwritten on the next registration. ⚠️ **Point-in-time enforcement was not enough: every one of those triggers (a registration, a sequence save, a button click) can simply fail to happen** — the live UNBOUND campaign sat a full day on the 9-5 default with zero inboxes because registrations were failing upstream of delivery. `sweepSmartleadDeliveryCampaigns` (`src/lib/event-delivery-sweeper.ts`, piggybacked on the `process-event-jobs` cron, throttled to one sweep per 30 min per replica) now re-asserts the 24/7 schedule, assigns sending inboxes when a campaign has none, and starts still-DRAFTED campaigns for every door with a Smartlead delivery target on a current event — continuously, with no operator action.
- **The provisioner and the push are not interchangeable owners.** `ensureSmartleadCampaign` provisions LEADLESS on the assumption a drip will fill it, so it must never run for a plan without LinkedIn touchpoints, and never before the SocialOS campaign it depends on exists. Both were true once, and a campaign fell between the paths: the programmer's recorded `campaignId` made the bulk push look already-pushed, while no drip existed to fill it. The refs fingerprint tells the two writers apart — `runSmartleadPush` always writes `leadsAdded` + `stepsCopy`, the programmer never does (see `scripts/inspect-smartlead-refs.ts`).
- ⚠️ **A 200 from `/schedule` or `/status` is not proof the campaign is running.** Verify by reading the campaign back: `GET /campaigns/{id}` → `scheduler_cron_value` (NULL until a schedule actually landed) and `status` (`DRAFTED` until it leaves Draft) — `getSmartleadCampaign` / `smartleadCampaignLeftDraft`. The original bug was a fire-and-forget `setSmartleadCampaignSchedule(...).catch(warn)` whose own comment said a campaign can't leave Draft without a schedule; in production `scheduler_cron_value` was `null` and re-POSTing the IDENTICAL payload returned `200 {"ok":true}`, so the call had simply never landed. **A schedule failure must be recorded (`outboundRefs.smartlead.scheduleError` / `scheduledAt`) and logged at `error`, not warned and forgotten.**
- **But never let the read-back become a new reason not to send.** A failed/unparseable `GET` means "couldn't verify", so fall back to what START reported; only a POSITIVE read of `DRAFTED` downgrades the outcome. Same for our own failed `/schedule` call: still attempt START, because the campaign may already carry a schedule from provisioning or from the operator.
- **A personalized push must NOT start at push time.** Leads are uploaded with BASE copy and rewritten 1:1 by a background job, so starting at push sends the draft. The start belongs on the job reaching COMPLETED (`startCampaignAfterPersonalization`); a failed run leaves the campaign in Draft with its leads intact, which is the safe direction. TEST_SLICE runs are excluded — the message test drives its own campaign.
- **`outboundRefs.smartlead.started` must survive a re-push.** The refs writer rebuilds that object from scratch, so the flag has to be carried forward explicitly or every push re-STARTs — which also resumes a campaign the operator deliberately paused. For the same reason, treat any status other than `DRAFTED` (including `PAUSED`/`STOPPED`) as "already left Draft" and do not re-START it.
- One decision predicate (`shouldStartSmartleadAfterBulkLoad`) and one effectful starter (`ensureSmartleadCampaignStarted`) are shared by all three callers (push, rewrite job, drip). A second copy of "set the schedule, then flip the status" is how one path silently stops starting, or starts a campaign another path is already driving.
- Reconcile campaign status nightly (paused/stopped/deleted upstream); surface 404s as an "invalid" state on the source record for admin remediation.
- Webhooks: HMAC-SHA256 hex (`x-smartlead-signature`/`x-signature`) + freshness + dedup + fast-200/async.
  - ⚠️ **A self-authenticating inbound endpoint must ALSO be exempted from the auth proxy (`src/proxy.ts` publicPaths), or it is dead on arrival with zero errors anywhere.** The Smartlead webhook shipped 2026-07-14 without the exemption: every event 307'd to `/login`, Smartlead treated the redirect as delivery, every handler test passed, and nothing logged — the reverse leg simply didn't exist in prod until an unauthenticated `curl` against the live URL exposed it (2026-08-06, while wiring Slack events, which hit the same wall on day one). Same audit found `/api/socialos/send-email`+`/engagements` and `/api/memory/webhooks` bounced too. `src/__tests__/proxy-webhook-reachability.test.ts` now pins reachability through the real proxy for every such path — add new ones there. **The handler's own tests cannot catch this class**; only a probe through the deployed proxy (or the reachability suite) can.
  - ⚠️ **EVERY path that provisions a Smartlead campaign must register the reverse-leg webhook, or the whole reply loop is silently dead for its campaigns.** The registration originally lived only on the email-only bulk push; the SocialOS provisioner (`ensureSmartleadCampaign`) skipped it, so LinkedIn-orchestrated campaigns had no HubSpot reply task, no Slack alert, AND their own `email_replied` graph branches never fired (SocialOS learns about email events only through this webhook) — replies didn't even stop LinkedIn touches. Both writers register now; `scripts/backfill-smartlead-webhooks.ts` re-registers already-live campaigns (idempotent: Smartlead upserts on campaign+name). If you add a third provisioning path, it owns registration too — same rule as the schedule+start ownership above, same failure shape: nothing errors, the campaign just goes quiet.
  - **Reverse leg (email → HubSpot + SocialOS):** register per campaign with `POST /webhook/create` (body `{ name, webhook_url, association_type:"campaign", email_campaign_id, event_type_map:{EMAIL_OPEN,EMAIL_LINK_CLICK,EMAIL_REPLY:true} }` — see `registerSmartleadWebhook`, fired best-effort on the outbound push). Smartlead POSTs to `/api/webhooks/smartlead/<orgToken>` (the token both routes + authenticates — `Organization.smartleadWebhookToken`, unique). Payloads vary per event: `to_email`/`lead_email`, `campaign_id` (number or string), and `time_opened`/`time_clicked`/`time_replied` (+ `preview_text` on replies) — parse defensively (`normalizeSmartleadEvent`). `processSmartleadEvent` resolves the campaign by `outboundRefs.smartlead.campaignId` and fans out. **HubSpot:** a reply → native incoming-email engagement (`logHubSpotIncomingEmail`, `INCOMING_EMAIL` on the `emails` object — shows in the contact's email thread with the reply body) **plus a follow-up TASK on the contact's owner** (`createReplyFollowupTask` → `createCallTask({ownerId})` + `associateTaskWithContact`, carrying the reply preview; no contact owner → the org's configured fallback owner, else unassigned — see the task-assignment note below). Recording a reply and getting a human to answer it are different jobs — the engagement alone left "tell me when someone replies" with nowhere to live, and the campaign-flow canvas can't cover it because an email-only graph is never programmed into SocialOS, so its `email_replied` branch never fires. ⚠️ **Task creation is not idempotent and the trigger is a retried webhook on a thread the prospect can keep replying to**, so the `EmailReplyFollowup` row is claimed FIRST and a P2002 means "already tasked" (the `EmailedContact` claim-first precedent) — one task per prospect per campaign. The claim is released when we learn no task was created (no HubSpot token, contact not in HubSpot) so a later reply can retry, and deliberately NOT released when `createCallTask` throws: it may have committed, and a duplicate in someone's queue is worse than one missed retry. A click → a note; an open → nothing (timeline noise). **OR**, when custom timeline events are configured (`HUBSPOT_APP_ID` + `HUBSPOT_TIMELINE_TEMPLATE_EMAIL_*` template ids + the `timeline` scope), EVERY event incl. opens becomes a branded HubSpot timeline event (`hubspot-timeline.ts` → `POST /crm/v3/timeline/events`, OAuth-token-only, appId-less path; templates are a one-time dev-key setup, `POST /crm/v3/timeline/{appId}/event-templates`). The `timeline` scope is requested by the OAuth connect ONLY when `HUBSPOT_APP_ID` is set (else it'd break every connect — the app must mark it Required first). **SocialOS:** every event is forwarded (`notifyEmailEvent` → the `email_opened`/`email_replied` graph nodes; a reply also exits the prospect from LinkedIn touches). Ack 200 fast for anything unactionable (bad token/event/campaign) so Smartlead doesn't retry a permanent condition.
  - ⚠️ **AN AUTO-REPLY ARRIVES ON THE SAME `EMAIL_REPLY` EVENT AS A REAL ANSWER.** Out-of-office responders, "I no longer work here" notices and bounce reports were fanned out as replies: a Slack ping to the whole channel and a HubSpot task on a rep for every vacation notice in EMEA (2026-08-07 — the trigger was a French OOO and a NextRoll role-change notice, minutes apart). `detectAutoReply` (`src/lib/auto-reply-detect.ts`) classifies at normalize time, where the raw payload still has headers and the reply body; `normalizeSmartleadEvent` attaches the verdict as `autoReply` on replies only. When it fires the fan-out keeps the RECORD legs (HubSpot engagement/timeline event, Salesforce activity — relabelled "Automatic reply from campaign email" so a rep scanning the timeline doesn't read it as engagement) and drops every leg that costs attention or changes behavior: no follow-up task, no Slack alert, and **no SocialOS forward** — `email_replied` would exit a live prospect from their LinkedIn touches on the strength of a vacation notice. It also claims NO `EmailReplyFollowup` row, so the prospect's real answer next week still creates the task. Three tiers, biased hard toward NOT filtering because the error costs are asymmetric (a missed auto-reply is noise; a filtered real reply is a lost deal): STRONG = machine on its face (RFC 3834 `Auto-Submitted`, `X-Autoreply`, null `Return-Path`, a `mailer-daemon`/`no-reply` sender, an "Automatic reply:" subject, a bounce report, "no longer work at"); PRESENCE = the away phrase alone ("out of the office", "hors du bureau"), which needs corroboration (a return date, a stand-in contact) because humans write it too; VETO = first-person intent ("can we", "call me", "I'm interested") overrides every CONTENT signal but not headers/sender/bounce codes. Patterns are multilingual and written WITHOUT diacritics — text is NFD-folded before matching, so an accented pattern can never match. Read the reply body from `preview_text`/`reply_body`/`reply_message.*`, and the sender ONLY from fields that mean "who answered" (`reply_from_email`, `reply_message.from`) — **never `from_email`, which is OUR sending mailbox**: a client sending from `noreply@` would have every reply classified as a robot. The webhook ack carries `autoReply: {kind, reason}` so an over-eager filter is visible without digging through logs.
- **SocialOS lifecycle emails (Build 9) use Smoke Signals' OWN key** (env `SMARTLEAD_API_KEY`, not per-tenant) and exactly one mailbox (`SMARTLEAD_ONBOARDING_MAILBOX_ID`); `src/lib/smartlead.ts` is the transport. Placement refuses any campaign whose `GET /campaigns/{id}/email-accounts` is not exactly that mailbox, so a cold-outreach inbox can never send onboarding email. Everything is behind `LIFECYCLE_EMAILS_ENABLED=true` (dry run otherwise).
- Endpoints verified 2026-09 (api.smartlead.ai/api-reference): add leads `POST /campaigns/{id}/leads` `{lead_list (≤400), settings}`; lead by email `GET /leads/?email=` answers `{}` when unknown; pause `POST /campaigns/{id}/leads/{lead_id}/pause` (keeps history; `DELETE .../leads/{lead_id}` deletes the lead outright when it's in no other campaign); campaign status uses `START`/`PAUSED`/`STOPPED` (not `ACTIVE`); schedule body is wrapped in `schedule`; webhook create is `POST /webhook/create` (singular) with `association_type` + `event_type_map`. Moving one person across campaigns needs `ignore_duplicate_leads_in_other_campaign: true` on the add, or Smartlead silently skips them.
- ⚠️ **Webhook payloads come in two documented families**: flat (`event_type`, `to_email`/`lead_email`, `preview_text`/`reply_body`, event names `EMAIL_REPLY`/`EMAIL_OPEN`/`EMAIL_LINK_CLICK`/`LEAD_UNSUBSCRIBED`) and nested (`event`, `lead.email`, `reply.body`, names `EMAIL_REPLIED`/`EMAIL_OPENED`/`EMAIL_CLICKED`/`EMAIL_UNSUBSCRIBED`). Normalize both (`normalizeSmartleadEvent`). Smartlead can't add custom headers to a webhook, so a shared secret on the URL query is the practical auth; a user-level webhook also delivers cold-outreach campaigns, so filter by campaign id. `preview_text` is plain text: don't run it through an HTML stripper (it eats `<anything>`).
- Plain-text campaigns can't track opens (no pixel); link clicks still track. The unsubscribe placeholder in a body is `%unsubscribe-text%`, rendered from the campaign's `unsubscribe_text` setting.

#### Task assignment (who a Throughline-created HubSpot task goes to)

Four paths create HubSpot tasks — email-reply follow-ups (`smartlead-webhook.ts`), LinkedIn-engagement follow-ups (`socialos-engagement.ts`), the cold call-task push (`campaigns/[id]/outbound/hubspot/tasks`), and always-on enrollment (`campaign-auto-enroll.ts`). All four now resolve the owner through **one** helper, `resolveTaskOwnerId` (`src/lib/hubspot-task-assignment.ts`): the CONTACT's owner always wins, then the workspace's configured fallback (one chosen HubSpot user, or a round-robin across several), then unassigned. Config is org-wide (`Organization.hubspotTaskAssignment`, set in Settings → Integrations) with an optional per-campaign override (`Campaign.hubspotTaskAssignment`, on the Launch stage).

- ⚠️ **The two cold paths previously passed no `ownerId` at all** — every task they created was unassigned, contact owner or not. If you add a fifth task path, route it through `resolveTaskOwnerId` or it will silently inherit that bug.
- **Round robin is STICKY PER PROSPECT.** The rotation picks a prospect's owner once (`HubSpotProspectOwner`, unique on `(scopeKey, identityKey)` where identityKey is the lowercased email); every later task for that person reuses it. One prospect generates several tasks over a campaign's life — reply follow-up, LinkedIn-engagement follow-up, cold call task — and splitting them across three reps means three people each holding part of one conversation. New prospects still spread evenly because the FIRST assignment comes off the rotation. A remembered owner who has left the roster triggers a re-assignment (and the row is updated, not re-decided per task). The unique index doubles as the concurrency guard: two simultaneous tasks for one prospect resolve to the first writer's owner.
- **Rotation itself must be atomic.** The busiest caller is a webhook, so rotation state lives in `HubSpotAssignmentCursor` and is claimed with a single `INSERT ... ON CONFLICT DO UPDATE SET position = position + 1 RETURNING position`. A counter on a JSON column would lose updates under concurrent replies. Verified: 40 concurrent claims across 4 owners → exactly 10 each. An overriding campaign rotates on its OWN scope key (`<orgId>:<campaignId>`) so it doesn't interleave with the org's.
- **Pass the prospect's email to `resolveTaskOwnerId` or you lose stickiness** — it silently degrades to raw rotation, which scatters one person's tasks. This is why `getHubSpotContactOwners` returns `email` alongside `ownerId`: the two contact-ID-based callers have no email otherwise.
- The owner index is `ownerIds[(position - 1) % ownerIds.length]`, so **editing the roster re-slices the rotation** instead of needing a cursor reset.
- **Batch the owner lookup.** For callers holding contact IDs, `getHubSpotContactOwnerIds` is one `batch/read` per 100 contacts — do not look owners up per task. But call `resolveTaskOwnerId` PER TASK (with `preloaded` config), or a round-robin puts the whole push on one person.
- **Listing owners needs `crm.objects.owners.read`, requested as an OPTIONAL scope** (`task-assignment` in `hubspot-scopes.ts`), because tokens freeze their scopes at issue time and a required scope would 403 every existing install. A 403 from `listHubSpotOwners` is therefore a NORMAL state for an older connection — it returns `{ error }` telling the user to reconnect, and task creation is unaffected.
- A config whose mode needs owners but has none coerces to `null` (unconfigured) rather than being stored as a setting that assigns nobody — that silent-nobody outcome is the bug the feature exists to fix.

## 11. Stripe — billing

Three implementations: ContentOS (`src/lib/stripe.ts` + credits engine), SocialOS, DealOS (`lib/billing.js`). Practices that matter:

- **Webhooks are at-least-once → handlers MUST be idempotent.** Claim `event.id` in a unique-keyed table before processing; a P2002/unique violation means already handled; delete the claim on handler failure so Stripe's retry can re-run (ContentOS SEC-017 fix — a double-granted-credits bug).
- Webhook routes need the **raw body** (`express.raw` / equivalent) for `stripe.webhooks.constructEvent`.
- Events to handle: `checkout.session.completed`, `invoice.paid` (**skip `billing_reason: subscription_create`** to avoid double-counting the first invoice), `customer.subscription.updated/deleted`, `invoice.payment_failed`.
- **Money mutations need DB-level atomicity** — read-check-then-write credit grants and deductions race under concurrency (double-spend). Use unique claims / row locks / atomic `updateMany` guards.
- Bound credit grants (positive integer, sane max) — never trust a quantity from metadata unchecked, and re-bind webhook metadata org IDs to the paying customer.
- Keep legacy plan slugs as aliases when renaming tiers — in-flight webhooks reference old slugs.
- SDK version quirks are real (v20: subscription at `invoice.parent.subscription_details`) — pin and note the version.
- Lazy-init the client (`getStripe()`) so builds/boots don't crash when unconfigured.
- Patterns in production: quantity-based subscription for credit units (ContentOS Agency tier), inline `price_data` for bundles (pricing changes ship as code), `setup_future_usage: 'off_session'` to save cards, usage-tier pricing derived from measured COGS (DealOS: tiers priced for ~90% gross margin against Claude costs — and meter EVERY vendor, not just the LLM, or margins are fiction).
- **Renewal deals in our own HubSpot (Throughline).** The billing webhook mirrors every active subscription as an OPEN deal in a dedicated "Renewals" pipeline in Smoke Signals' own portal: close date = the subscription's `current_period_end` (Stripe's clock, never a computed anniversary), likelihood = stage probability (monthly 90% / annual 85%), `dealtype=existingbusiness`. `invoice.paid` with `billing_reason=subscription_cycle` closes the open deal Won and opens the next; `customer.subscription.deleted` closes it Lost. Idempotent via a `renewal_period_key` custom property; fire-and-forget so a HubSpot outage never fails the webhook; no-ops without `SMOKESIGNALS_HUBSPOT_TOKEN`. ⚠️ **Basil API note (SDK v22):** `current_period_end` is on the subscription ITEM (`sub.items.data[0].current_period_end`), not the subscription, and the invoice's subscription is at `invoice.parent.subscription_details.subscription`. Lifecycle in `src/lib/renewal-deals.ts`, I/O in `src/lib/renewal-deals-sync.ts`, runbook `docs/stripe-renewal-deals.md` (adds the `invoice.paid` webhook event + deal scopes).
- **Annual = a second Stripe Price + a persisted interval, front-loading the year's credits.** Throughline offers a yearly agreement (pay for 10 months, get 12 — "two months free", 16.6% off) on the fixed self-serve tiers. Each tier carries a separate `interval=year` Price (`STRIPE_PRICE_*_ANNUAL`) alongside the monthly one; `TIER_PRICES[tier].annualPriceId` and the `interval` param on `/api/billing/checkout` pick which. The webhook's `tierFromPriceId` maps BOTH Prices back to the same tier, and `intervalFromPriceId` records the cadence on `Agency.billingInterval`. That column drives the credit grant: `grantMonthlyForAgency` → `planGrantForInterval` grants a MONTHLY agency one month on a 30-day period, but an ANNUAL agency the **whole year up front** (12 × the monthly allotment) on a 365-day period — so the daily `grant-monthly-credits` cron only rolls an annual agency once a year and re-grants the next full year at renewal (one grant path, both cadences). Set the interval BEFORE the signup grant, and reset it to `monthly` on cancellation (else a canceled→FREE agency front-loads a "year" of free credits). Keep the `annual` cents in `TIER_PRICES` equal to `annualPriceCents(monthly)` AND equal to the real yearly Stripe Price. Agency (quantity-based, adjustable anytime) stays monthly-only.
- **A failed invoice is a THIRD account state, not a suspension and not a failed top-up (Throughline).** Keep `Agency.suspendedAt` (staff kill-switch, whole dashboard redirects to a notice page, recovery via support), `Agency.autoTopUpFailedAt` (a failed OVERAGE charge on a healthy subscription) and `Agency.delinquentSince` (a failed SUBSCRIPTION invoice) strictly apart: they set and clear independently and each does something different. Delinquency is set from `invoice.payment_failed` and from `customer.subscription.updated` when status becomes `past_due`/`unpaid`, and cleared by `invoice.paid` (**every** `billing_reason`, `subscription_create` included — that skip exists to stop double-COUNTING an invoice, and clearing a state counts nothing) and by a subscription back to `active`. Handle the billing-health branch OUTSIDE the tier-mirroring `if (customerId && tier)`: a past_due can arrive on a Price you can't map, and "we couldn't resolve the tier" must never mean "we ignored the failed payment". Stamp it with a `WHERE delinquentSince IS NULL` claim so the two events for one failure can neither restart the grace clock nor double the notice email. Effects, all derived from that one timestamp (`src/lib/billing-delinquency.ts`): every credit charge refuses with a distinct `delinquent` status, the off-session auto top-up is never attempted (**charging a card that just failed its invoice is exactly wrong** — it declines again, or worse it clears and you have sold credits to an account whose work is paused), the dashboard stays fully reachable behind a pay-to-unlock banner, and after 14 days the org's PUBLIC pages 404. ⚠️ **A public-page cutoff is outward-facing** — it breaks links the CUSTOMER already sent their prospects — so: one gate in `src/proxy.ts` (the only point that runs ahead of the ISR cache AND that a newly-added public route cannot miss), a bare `no-store` 404 that never leaks billing status to a prospect, no cached verdict so paying restores every page on the next request, and **fail-open on any error** (404ing a paid-up customer is far worse than serving a delinquent one another minute). A credit-bundle purchase must NOT clear it: buying credits does not settle a subscription invoice.

### Cloudflare (ContentOS)
- **Cloudflare for SaaS** custom hostnames + a router Worker: the SaaS fallback-origin preserves the original Host header which Railway can't route — a Worker + Origin Rule rewrites Host to the canonical domain while the original rides in `x-forwarded-host` for tenant resolution.
- Make ALL Cloudflare ops idempotent (check-before-create); PATCH custom hostnames to re-trigger the slow verifier.
- **The zone APEX cannot be a custom hostname of its own zone.** Ask the custom-hostnames API for `smokesignals.ai` and Cloudflare answers `success:false` with the message `Internal Server Error` — no code, no reason (observed 2026-08-04 in prod). Subdomains of our zone are NOT affected: `insights.smokesignals.ai` has been an active custom hostname since 2026-04-02. So `isZoneApex()` — not "is it in our zone" — is the correct test, and the apex takes its own path: the zone already resolves it and the zone certificate already covers it, so its **Worker route IS the registration** (no custom hostname, no DNS records to ask the operator for, `APEX_PROVIDER_ID` as the stand-in provider id).
- **Never ask any customer to CNAME their root domain.** A CNAME can't coexist with the SOA/NS records a zone apex carries (RFC 1034), so providers reject it — and a customer serving their WHOLE site here starts at the root. `isApexHostname()` (`src/lib/domain-dns.ts`) asks DNS instead of counting labels: only a zone apex answers a SOA query in the ANSWER section, which gets `example.co.uk` and delegated subdomain zones right without a public-suffix list. Apexes get A records to the proxy's addresses (plus an ALIAS/ANAME note, which survives our IPs changing); everything else keeps the CNAME. `verifyDomainDnsResolves` already accepts either, so verification needed no change. Build the records with `buildRoutingRecords()` — never hand-roll a routing record, or one code path will keep telling root-domain customers to do the impossible.
- **An apex's "verified" can only be answered by Worker-route existence.** Every hostname in the zone resolves to the same Cloudflare anycast IPs, so `verifyDomainDnsResolves` finds an A-record match and reports success whether or not anything is wired up. Check the route (`hasWorkerRoute`), and delete the route on teardown (`deleteWorkerRoute`) or the hostname keeps serving us after its row is gone.
- **Verify custom domains on a SCHEDULE, not only when someone opens the settings page.** DNS moves without telling us — a registrar transfer, a record "cleaned up" by whoever inherited the zone, an expiry — and the customer's site goes dark behind a badge that still reads Active. `cron-verify-domains` re-resolves every hostname hourly and alerts on the working→broken transition (once, not every run; a resolver error is not a transition and never downgrades a live domain). Several breaking in one run is a signal about US, not them: root-domain customers pin our proxy's anycast addresses as A records, so if those move every apex customer breaks at once — that case mails staff rather than sending the whole blast radius to go check their own DNS.
- **A site needs both `www` and the apex registered, but only one canonical home.** An unregistered hostname doesn't answer at all, and serving identical pages on both splits inbound links. `OrgDomain.redirectToHostname` makes the second one a 308 to the same path on the first (`lib/host-redirect.ts`, applied in `src/proxy.ts`). Only `www.*` is consulted there — widening it to arbitrary aliases costs a DB lookup on every custom-hostname request, so it should be a deliberate change.
- Never surface `errors[0].message` alone — Cloudflare puts the actionable reason in the numeric `code` and the `error_chain`. Log the whole envelope plus the HTTP status (`describeCloudflareErrors` in `src/lib/cloudflare.ts`).
- **R2** via S3 SDK (`region: "auto"`, endpoint `https://{account}.r2.cloudflarestorage.com`): all-or-nothing config gate with inline-data-URL fallback; persist `r2://bucket/key` scheme; best-effort deletes (an orphan key beats a 500); R2↔Workers egress is free. Sanitize user filenames before using them in keys.

## 14. Cross-cutting engineering rules (the distilled lessons)

These recur across every repo. Follow them for ANY new integration:

1. **One transport module per vendor.** Every call goes through a single shared client so fixes (sanitizers, retries, instrumentation) land once. The SocialOS surrogate bug — patched at 2 of 8 call sites — is the cautionary tale.
2. **Config-gate optional integrations**: `isXConfigured()` → clean no-op / typed-only mode / fallback behavior / operator setup notice. Never crash on a missing key; never let an optional integration's failure break a core flow. Integration secrets are credentials, not feature flags.
3. **Structured outcomes, not thrown vendor errors**: return `{data, outcome/status}`; never leak vendor names or raw errors to end users.
4. **Retry only what can succeed**: 429/5xx/timeouts/network with exponential backoff + jitter, honoring `Retry-After` (ContentOS drops `timeouts` from this list for paid non-idempotent POSTs — see the client-side TIMEOUT sub-rule below). **Never retry other 4xx** — they fail identically. Distinguish per-minute limits (backoff) from daily caps (pause the endpoint, fail fast). Circuit-break repeating single-error storms.
   - ⚠️ **A client-side TIMEOUT on a paid non-idempotent POST is not retryable.** Our `AbortError` says nothing about what the vendor did: it may have completed and billed the work, so re-firing buys it twice. Throughline treats a timeout as terminal on every paid POST (Parallel, Perplexity, OpenAI, Gemini, cloro) while still retrying genuine connection-level failures and 429/5xx *responses*; free idempotent GETs (result polls) keep their retry. cloro renders a live SERP behind a 90s timeout, so this was a real double-buy.
   - **Meter the attempt, not just the success.** Metering only on success makes exactly this waste invisible: the timed-out call writes no UsageEvent, so the spend dashboard undercounts by the retry leakage. Throughline writes a UsageEvent at the flat COGS estimate with `metadata.timedOut: true`, and `parallel-spend.ts` surfaces that as a separate `timedOut` line rather than folding it into confirmed spend.
5. **Rate-limit client-side, before the wire.** Token bucket per provider; if the key is shared across replicas, add a Postgres-backed distributed limiter that is **fail-open** (a DB hiccup must never gate outbound calls). Serialize the bucket check so `Promise.all` bursts can't all pass at once. In-memory limiters do not coordinate across replicas.
6. **Never cache failures.** Cache successes with TTLs and genuine misses with short negative-cache sentinels; only set `cacheable` flags when the result is trustworthy.
   - **Key a cache by the ENTITY, not the tenant, when the payload is raw public data** — that is what makes the fleet pay once per TTL window instead of once per customer. Throughline has three: `EnrichmentProfileCache` (LinkedIn profiles), **`ScrapeCache`** (`src/lib/scrape-cache.ts` — normalized URL → markdown, behind the shared `scrapeWebpage` chain; before it the same customer website was scraped independently by positioning assessment, offerings discovery, the AEO audit and site import), and **`GeoEngineAnswer`** (`(engine, promptHash, region, day, runIndex)` → one answer-engine response, so ten orgs tracking the same public prompt buy it once instead of ten times at ~$0.09/prompt/day).
   - **Share ONLY the raw provider payload.** Never a derived judgment — an AEO score, a positioning diagnosis, a sentiment read, share-of-voice. Sharing the bytes a vendor returns to anyone is safe; sharing a judgment leaks one customer's analysis into another's product. Both new caches carry that rule in their schema comments, and every per-org derived field is still computed per org from the shared payload.
   - **A cache hit must not be billed.** If enqueue-time charging can't see the cache, teach it to: Throughline's GEO enqueue pre-reads the shared answer table and omits the credit for samples that will be served free (and skips the charge call entirely when the whole batch is cache-served, rather than passing zero through it).
   - **Store the change signal, not just the payload.** `ScrapeCache.contentHash` lets a recurring job skip its expensive derive step when a page is byte-identical: the external AEO audit re-scrapes on its 28-day TTL but only re-runs the deterministic audit when the hash moved (`GeoPageAudit.contentHash`).
7. **Parse vendor responses defensively** — shapes drift across versions (Firecrawl, Anysite, Unipile, Gong, Smartlead, notetakers). Multi-alias field reads, depth-limited key hunts, normalize string-or-object values.
8. **Webhook hardening checklist**: raw-body capture → HMAC verify with `timingSafeEqual` (reject when the secret is unconfigured) → ±5-min timestamp freshness → dedup by event id (mark seen only after successful processing) → **respond 200 immediately, process async** → debounce bursty triggers through a durable queue → normalize event-name casing/synonyms.
9. **OAuth lifecycle**: proactive refresh with a buffer AND retry-once-on-401; refresh 4xx = revoked → clear state, prompt reconnect; HMAC-signed `state` with TTL; byte-identical redirect URIs computed in one place; scopes are frozen at consent (prefer optional scopes post-launch); keep the scope list in one module.
10. **Meter every paid call with tenant attribution at call time** (the Parallel.ai mandatory-meter pattern). Get the vendor's billing *unit* right (tokens vs credits vs per-account vs flat) — wrong units made one admin dashboard overstate COGS 10× and one credits system understate them. Measured usage beats hardcoded guesses.
11. **Money mutations are atomic and idempotent**: unique-claim tables for webhook events, unique keys on billable output rows, row-level guards on credit math.
12. **Security non-negotiables**: SSRF-safe fetch for user URLs; never bind `role`/`organizationId` from a client request body; centralize authz (per-route discipline fails at scale — ContentOS shipped 277 routes with no middleware); `sandbox="allow-scripts allow-same-origin"` on an iframe voids the sandbox; encrypt third-party tokens at rest (AES-256-GCM — known gap: DealOS stores HubSpot tokens plaintext); don't reuse one secret across crypto domains; scrub PII/keys from error telemetry.
13. **Fail loudly where it counts**: include vendor error bodies in thrown errors; `console.warn` on silent truncation/caps; alert (deduped) on auth/quota failures; heartbeat-monitor scheduled jobs (ledger table + staleness alerts) so "did it fire?" is one SQL query.
14. **Tenant isolation by construction**: every cache/query keyed by org/portal id as a required argument.
15. **Agentic safety** (the Portal's retired Emily agent was the reference design): default-off feature flags for anything with spend or outbound risk; no LLM reasoning in irreversible click-paths; in-flight assertions comparing intended vs actual before the commit step; idempotent-by-name writes for crash recovery; observe-mode rollouts.
16. **Meter the resource you actually buy, and meter it once — then check the other direction too.** The same audit that finds free things being charged will find costly things that aren't: SocialOS charged nothing for Firecrawl web-tech detection, which bills per scrape. When you do add such a charge, put it on the *paid* path only (cold cache miss), not on the lookup — a shared cache means most calls are free to serve and should be free to the customer.
17. **Meter the resource you actually buy, and meter it once.** Vendors bill in different shapes — per call, per credit, per token, per seat, flat. A usage-based price on an action whose vendor bills per *seat* double-charges the customer for a resource that has zero marginal cost, and the second charge is usually the biggest line item on the bill. SocialOS charged 10 credits per LinkedIn send while Unipile bills ~$5/mo per connected account and nothing per send — and the account was already billed at $50/mo. That was 24% of a referral run and ~60% of a Scale plan for a heavy sender, all against $0 of COGS. Check every metered action against the *vendor's* billing unit (PLATFORM §5 lists them) and drop the ones that don't map to a real marginal cost. Two implementation notes: a zero price must still pass the subscription/suspension gate (free to run ≠ allowed to run), and it must not write a zero-amount ledger row per action — SocialOS's `chargeCredits()`/`refundCredits()` do both.
18. **A fuzzy matcher needs a stopword list, not a length floor.** Two independent SocialOS bugs had the identical shape: every US location pair matched because "united"+"states" counted as distinctive tokens, and every company pair matched because "the" is exactly 3 characters and cleared the length filter, then supplied 50% overlap against any two-word name. Both produced confident, specific, wrong claims shown to users ("same location", "Both worked at The Nielsen Company"). Rules: (a) keep a **stopword set per entity type** — geo, school, company all need different ones; (b) require **ALL** of the shorter side's distinctive tokens, not a percentage — a 50% threshold means one shared filler word matches any two-token pair; (c) use **whole-word containment**, since substring matching makes "Meta" a match for "Metabase"; (d) bias toward misses — a missed match costs a UI chip, a false one asserts a relationship that doesn't exist.
19. **`content` is an ARRAY OF BLOCKS — never index it.** Enabling extended thinking (`output_config: { effort }`, or `thinking`) prepends a `thinking` block, so the assistant's text is no longer `content[0]`. SocialOS had 17 call sites checking `content[0].type === "text"` and returning "" otherwise; the day `output_config` was added to one writer, that writer failed on **every single call** — silently, because empty and failed were handled identically. Parse by **scanning for text blocks** (`lib/anthropic.ts` → `anthropicText`), and route every call site through one shared helper. Two riders: **thinking tokens come out of `max_tokens`**, so a budget sized for the answer alone returns a response with no text block at all; and a **4xx other than 429 is not retried**, so `if (!res.ok) return null` with no logging is a 100%-failure mode with nothing to diagnose from — log the status and body (`logAnthropicFailure`). A test that mocks the whole `@/lib/anthropic` module must `importActual` and stub only the network call, or it drops helpers added later and reads as a production failure.
20. **Never substitute a plausible placeholder for a failed generation.** When SocialOS's DM writer failed we wrote a generic "I came across what you're working on..." note, reasoning that the human reviews it anyway. They don't: it was visually identical to a real draft, sat in a list of 260 queued to auto-send, and would have gone out under a referral partner's name to someone they know. Leave the field NULL, refund the charge, and let the retry sweep pick it up — a self-healing gap beats permanent garbage. The tell that you have this bug: a fallback whose justification is "the user will edit it."
21. **A cache keyed on "has the config changed?" still has to expire.** Skipping expensive re-work when your own settings are unchanged is the right optimization, but the *subject* changes too. SocialOS reused a prospect's ICP grade whenever the filter fingerprint matched, with no TTL — so a prospect who failed at a ten-person shop and later became a VP at a target account kept their FAIL forever, which is precisely the lead the product exists to find. Two rules: (a) find a **free change signal** already in the payload you're processing — the engagement feed carries the person's current headline, so job-change detection costs nothing and fires the same day; (b) add a **time backstop** for what that signal can't see (acquisitions, headcount, tech adoption). And when the signal fires, invalidate every layer — the row-level copy AND the shared cache — or you detect the change and then re-decide against the same stale facts, which is worse than not detecting it.
22. **A terminal status is a data-loss bug waiting to happen.** If a row's state column gates whether anything will ever process it again (`WHERE send_status IS NULL`), then writing a failure into that column on a *transient* provider error destroys the work permanently. SocialOS marked a referral intro "failed" on any Unipile error; both the auto-sweep and the partner's manual retry skip non-null statuses, so one 500 killed that introduction forever — and the org had already been charged, with no refund path. Rules: separate "attempt failed" (retryable, bounded by an attempts counter) from "gave up" (terminal); **refund before you leave the failure path** when you charge before the call; and weigh the cost of giving up against how many chances you get — a referral partner acts once, as a favour, and never returns, so there is no second attempt to rely on. **This recurred, in a different table, four months later** — so audit for the pattern rather than fixing instances: `knowledge_base_sources.status` was set to `'failed'` on any refresh error while the scheduler sweep selected `status = 'active'`, so one transient Anysite error removed a customer's LinkedIn source from the rotation *permanently*. It sat dead for 93 days with a `next_index_at` 86 days in the past, and the stored error message promised the opposite ("We'll automatically try again on the next scheduled refresh"). The tell is structural and greppable: **a status column written on failure, and a worker query filtering on that same column.** If both exist, the failure is terminal whether you meant it or not. Sweep on `status NOT IN (<user-chosen stops>)` plus a bounded attempts counter, never on `status = 'active'`; and make an explicit user-facing Retry reset that counter, or a recovering row drops straight back out of the sweep.
23. **When you ghostwrite for a third party, never write a claim only they could verify.** Drafting in someone's voice is fine; drafting an assertion about their own life is not. SocialOS drafts a comment for a referral partner to leave on a connection's post, and the highest-converting thing that comment could say is "we use them, they fixed exactly this for us" — which we have no idea is true. Being onboarded to a referral program tells you someone *knows* the customer, never that they *bought* from them. The draft would be published on the open internet under a real person's real name to someone who knows them well enough to notice. "They can edit it before posting" is not a defence for handing someone a ready-to-paste lie, and it is the same excuse as rule 20's placeholder DM. Constrain the prompt to what the person can honestly say from the fact of the relationship alone (they know the team; they can make an introduction), state the ban concretely with the exact phrasings to avoid rather than as "be truthful", and keep the human in the loop as a *publisher* — we suggest, they post, we never post for them. Applies to any generated text that will carry a real person's byline: testimonials, endorsements, references, recommendations.
24. **Attribution decides money, so it matches on identity or not at all.** When several people can earn a share of the same fee, the matching step stops being a UI nicety and becomes the ledger. SocialOS credits a referral partner for commenting on a prospect's post, which means recognizing them among a hundred commenters — and the tempting fallback (the comment carries a display name, and we know the partner's name) is exactly the one to refuse: names are not unique, and there is no undo on a payout sent to the wrong person. Match on a normalized provider id or profile slug, and credit nobody when you can't. That constraint pushes work earlier: the identity has to be captured while you still have the person's session, which for a flow whose whole promise is "we disconnect immediately" means capturing it in the same pass that uses the session, not in a later sweep. Three riders. **Snapshot the money at the moment it is earned** — a live "fee amount" setting computed on read means editing it silently rewrites what people are already owed. **Split in the smallest unit and distribute the remainder deterministically** — $5,000 across three is not representable in dollars, per-share rounding overpays and per-share flooring quietly keeps the difference; the shares must sum to the total exactly, and the same input must produce the same split on a re-run. **Freeze the credit set when the money becomes real** — reopening a settled payout to add a late participant takes money back from people who were already told what they earned.
25. **Separate the list from the thing that polls it.** A list of people and a job that fetches their posts are different objects with different costs, and fusing them is how a product ends up with a standing spend nobody chose. SocialOS's audiences lived *inside* the Program that used them — a CSV pasted into `modeConfig`, a HubSpot list id — so a list could not be named, reused across Programs, inspected, or kept current without rebuilding the Program around it, and the only way to "have a list" was to start monitoring it. Splitting them made the expensive act explicit: an Audience holds people, has no schedule and spends nothing; pointing a Program at one is a separate click. Three things that follow. **A derived list needs a refresh that reconciles, not replaces** — delete-and-reinsert is simpler and destroys `addedAt`, which is the only column answering "what's new since I last looked". **Record refresh failures on the row**, because a list that has quietly stopped updating is indistinguishable from a small list. And **hand the list to the consumer in the shape it already accepts** (here, an `uploaded_list` Program's `resolvedProfiles`) rather than inventing a new mode: it needs no engine change and inherits the dormant-target backoff that makes a long list affordable.
26. **A stored score answers ONE question — asking a different one needs its own row.** A column like `icp_grade` reads as "how good is this person", but it is really "how good is this person against the filter that happened to be configured when we graded them". The moment a second surface wants the same people scored against a different filter, writing back to that column silently rewrites the first surface's answer — SocialOS came within one line of having an audience built against ICP B change which intros a referral partner was shown, because their campaign's grade against ICP A lived in the same field. The fix is a side table keyed `(subject, filter)`, with the original column left alone as the campaign's own answer, and a resolver that reads whichever applies. Three riders. **Never re-buy a settled answer**: a FAIL is an answer, so "needs scoring" must test for the ABSENCE of any row, not for a qualifying one, or the negative cases get re-graded forever. **Price the gap honestly and show both halves** — "4,200 already match, 6,800 unscored, ~N credits to check them" — because reporting only what qualifies looks misleadingly small and reporting only the cost looks misleadingly scary, and the customer needs both to decide. **Price the PIPELINE, not the item**: SocialOS's scoring path is a cheap gate (~0.5 credits) and an expensive tail (~8 — fit review, post fetch, engagement checks, brief) that only contacts clearing the gate reach, so a flat per-contact quote is wrong in both directions — several times over for a narrow ICP, and, far worse, UNDER for a broad one. Estimate the pass rate from the customer's own history (this filter's results first, then these accounts', then a documented default), lift an observed rate where the thing you can measure is downstream of the thing that drives cost, and show which basis you used so the number is checkable rather than magic. **Consent is per-question**: changing the filter in the picker must reset the "yes, spend it" toggle, since the number they agreed to was for the filter they were looking at.
27. **Where a product meters usage, forecast the spend before the user commits it** (SocialOS `lib/credit-forecast.ts` + `components/credits/credit-forecast-panel.tsx` are the reference). A config screen that can silently drain a balance needs an estimate sitting next to the controls, not a support ticket afterwards. Five rules make the difference between a forecast people trust and one they learn to ignore:
    - **Read the live price table; never restate prices.** A re-pricing PR must not be able to leave the forecast quoting stale numbers.
    - **Model the full cost of a choice, not the line item.** The cheap-to-fetch option is often the expensive one: LinkedIn reactions cost a third of comments per post and are still ~74% of a typical program, because they bring ~40 people per post and each carries a lookup and an AI grade. Summing unit prices gives exactly the wrong advice.
    - **Don't overstate, and sanity-check the output against a real run before shipping it.** Model whatever the system already dedupes or caches — across repeat runs *and* within one. SocialOS got this wrong twice over, compounding to ~5×: it re-charged per-person work every run (the engine skips anyone already graded), and it billed that work per raw ENGAGEMENT when prospects are keyed per person per org and the same human reacting to twenty posts is one paid lookup, ever. A forecast 5× high is not conservative, it's broken — it reads as "this feature is unaffordable" and the honest advice underneath never gets read. **Bill against the entity your storage is keyed on, not against the events you observed.**
    - **Calibrate from the tenant's own history** where it exists, and widen the band when it doesn't. Always print the assumptions; always show a range.
    - **Every tip names a number and a control on the screen in front of the user**, and prices the suggested change by re-forecasting it. Generic advice is worse than silence — it trains people to skip the box that also holds "you can't afford this."

28. **A backoff must be able to observe the evidence that clears it.** Polling every target on every run is the obvious cost to cut, and skipping the quiet ones is the obvious way to cut it — but a backoff is a *state machine with an exit*, and the exit only works if the reduced check can still see the thing that proves the target is active. SocialOS shipped both halves of one cost PR in one commit: an incremental lookback (`postedAfter` = the previous run's start, so a daily program asks for one day of posts) and a dormant-target backoff (a target quiet for 30 days is re-checked weekly instead of daily). Each is correct alone. Together, a target deferred for a week was re-checked with the *run's* one-day window, so it could not see the six days it had been away — it found nothing, stayed dormant, and was deferred again. Dormancy was self-fulfilling: nothing could climb out, and monitored lists decayed to zero pickup over a few weeks. It compounded with a second conflation, **"never seen posting" read as "gone quiet"**: a null `lastPostFoundAt` counted as dormant outright, so one empty first check wrote a target off before there was anything like 30 days of evidence, and the list started decaying on day one instead of day thirty. Rules. **A per-target skip needs a per-target window** — anchor the catch-up to when *that target* was last actually fetched, not to when the run last happened, and cap it so a long pause can't re-mine history. **An absent observation is not a negative one**; give it a separate anchor (a `first_checked_at`) and a grace period before any inference. **Trace the exit path explicitly**: write down what has to be true for a backed-off row to come back, then confirm the reduced check can actually observe it — if the answer depends on the target acting inside a window the backoff itself narrowed, the state is terminal, which is rule 22 wearing different clothes. And the failure is silent by construction: an all-deferred run makes **no API calls, spends nothing, finishes in milliseconds and completes green with zero results**, which reads in the UI exactly like "we looked and your audience was quiet". A cheap, fast, successful run is not automatically good news — **distinguish "found nothing" from "looked for nothing" in the run log**, or the stall is invisible until a customer says it has been weeks.

29. **A setting with no screen behind it is an off switch, not a feature.** Shipping the API and deferring the UI is a normal trade — but the moment a *config option* depends on a screen that doesn't exist, that option stops meaning what it says. SocialOS's referral listening notify step had `requireApproval`, which parked alerts at `status = "pending", statusReason = "awaiting_approval"` awaiting a human decision. The list endpoint and the approve/decline endpoint both existed and both worked; nothing rendered them. So turning the setting on silently held every alert forever, and looked from the outside exactly like a program that had found nothing. Three tells to check before calling an API-only feature shipped. **Does any option gate on a human action?** If yes, that option is unusable, and it should be either hidden, rejected at write time, or built with its screen — not left as a checkbox that stops the pipeline. **Can the customer answer the question the feature exists to answer?** An attribution ledger that computes a $1,250 share is not delivered until someone can see the comment that earned it; the arithmetic being right in the database is not the deliverable. **Is a failure recorded somewhere nobody reads?** `lastRefreshError` was written on every failed refresh and read by nothing, so a list that had been failing nightly for weeks was indistinguishable from one that was simply small. Grep for columns written on a failure path and never selected by a route — each one is a silent outage with a paper trail nobody is holding.

30. **A "create" affordance that navigates away from the thing it creates is a missing feature wearing a button.** SocialOS shipped Audiences as a real object with its own page, list, and API — and both buttons on that page linked to the Program wizard, because that is where the one builder happened to have been written. The object existed; the way to make one lived somewhere else, so the page could only ever show an empty state to anyone who had not already been through the wizard. The user's report was exact: "I don't understand the point of this tab if both buttons just take me to the program creation page." Two rules fall out. **Build the creator where the object lives**, and let other surfaces embed it — the same component took an optional "hand me the saved record" callback and served both callers, which is a smaller change than it looks and the wizard kept working unchanged. And **a first source is not the shape of the feature**: audiences supported exactly one derivation (referral networks) because that was the use case that prompted them, which quietly answered "what is an audience" with "a referral thing". The second source — people the org's own listening had already found — needed no schema change, only a collector behind the same dispatch and the same normalized member key, so a person both sources contain is one member. If a feature's source list has exactly one entry and its refresh sweep names that entry in a WHERE clause, both are load-bearing guesses about a plural.

31. **One counter cannot name two relationships, and two counters on different clocks read as a bug.** A SocialOS listening run showed "0 Posts / 530 Engagers" for an hour on a program configured to watch **posts only** — a mode that performs no engagement fan-out whatsoever. Neither number was a lie about the data; both were lies about what they were called. `engagers_found` was incremented for every prospect `processPost` captured, and that includes the post's own AUTHOR, so the tile labelled Engagers was counting people who had written posts, not engaged with them — and counting them **once per post rather than once per person**, because a user-posts fetch returns up to 5 posts per contact and every one names the same author. One contact with five recent posts was five "engagers", five prospect upserts (four of them losing a unique-constraint race, which is what the repeated `P2002` warnings for a single name seconds apart actually were), and five ICP evaluations. Meanwhile `posts_found` was written **once, at the end of the whole scan** — the live increment existed but sat inside the `voc_analysis` branch — so the honest number was invisible for the entire time the run was working and then appeared complete. Three rules. **Name the relationship, not the bucket**: if a counter's label would be wrong for any configuration the product allows, it is two counters (`authors_found` + `engagers_found`), and the UI should hide the one that is structurally zero rather than show a permanently-blank column. **Count the entity your storage is keyed on** — prospects are unique per person per org, so per-person is the only tally that can ever reconcile with the rows, and a per-event tally will always over-report by the fan-out factor. **Every long-running job's progress counters must tick on the same clock**: a metric written only in the terminal summary, sitting next to metrics that increment live, is indistinguishable from a stalled pipeline — and the increment doubles as the heartbeat a stale-run sweeper reads. Don't back-fill a split like this: nothing on the old rows records which share was which, and a zero meaning "predates the split" is honest where a guess is not.
32. **A serial loop over independent network work is a wall-clock bug even when every call is correct.** SocialOS's HubSpot-segment scan walked contacts strictly one at a time — one Anysite posts scrape, then per-post DB writes and CRM round-trips — measuring ~6s per contact, so a few hundred contacts took about an hour with the process idle for nearly all of it. `runBounded` (`lib/bounded-concurrency.ts`) already existed for exactly this and had been adopted only by referral scoring. Two things to get right when converting one: the credit check must gate **starting** work rather than abandon paid-for in-flight items (`shouldStop`), and the concurrency ceiling is **not** your own throughput — it is the tightest limit any provider in the loop body imposes, shared with every other job in the process. Here Anysite's own bucket (180/min, per-process) was never the constraint; HubSpot's search limit was, which is why the observed 429s came from the CRM and not the scraper. Pick the limit from the tightest downstream, leave headroom for the rest of the fleet, and make it per-tenant overridable rather than a constant.
33. **For a handler whose failure mode is silence, the log line IS the observable behaviour — and a log that can't tell "expected" from "broken" is worse than none.** Two defects in SocialOS's Unipile webhook, neither of which changed a single routing decision, both of which made a working handler look broken for months. One printed `event=undefined` on the majority of traffic because the log read a different field than the router did — a log line that duplicates a value the code has already resolved will drift from it, so **log the resolved variable, never a re-read of the raw payload**, and log which field it came from. The other logged an expected category (referral partners, who by design have no `linkedin_accounts` row) with the same words as a genuinely lost mapping, on every event, so the volume itself destroyed the signal — and "8+ unknown accounts" read as a data-integrity incident when it was a naming problem. Three rules for skip-and-continue paths. **Classify before you log**: if a branch has more than one cause and one of them is normal, say which one, or the message is noise for the normal case and invisible for the abnormal one. **Match severity to actionability** — expected → `log`, orphaned → `warn`; if everything is the same level, nothing is. **Suppress steady-state conditions per key per process**, so a recurring fact costs one line rather than one per event and a deploy re-reports it. Keep the diagnostics in a `try/catch` that swallows: a failure to *explain* a skip must never change the response, or you've turned a log line into a webhook retry storm. And where a skip is genuinely unimplemented work rather than a no-op, say so in the message — partner LinkedIn events have nowhere to land (`referral_partner_contacts` tracks email replies only), which is a missing feature, not a lost write, and the log is the only place anyone will learn that.
34. **A step that fails and advances anyway needs a bounded retry, or one bad deploy silently eats a whole cohort.** SocialOS's campaign engine had exactly two ways to treat a step outcome: defer forever (credits, daily caps — external causes that self-clear) or record it and move the cursor on. `engage_failed` took the second path, so when the reaction call was broken — and it had been broken since the feature shipped — 412 of 412 enrollments recorded "Reaction failed" and advanced to "Next: in 2 days". No retry, no alert, no failed status, nothing for the sweeps to pick up; the only trace was a tooltip, and fixing the call did nothing for those rows because their engage node was already behind them. Both extremes are bugs: retrying forever is the infinite-deferral failure (lesson 22, and the no-Unipile-account sender), never retrying loses the work to any transient blip. **Retry a few times, count the attempts on the CURSOR rather than the row** (reset the counter when the cursor moves, or a later node inherits a spent budget), then give up and advance — a like is not worth stranding the DM behind it. Two design notes. **Distinguish "no work possible" from "work failed"**: a deleted post is not a transient error, so it skips immediately rather than burning attempts and reads on an answer that will not change. And **a fix to the call is not a fix to the rows** — a cohort that advanced past a step needs its cursor rewound deliberately (`scripts/retry-failed-engagements.ts`), which is safe only because the cursor sits ON the next node awaiting its time, so nothing already sent gets re-sent; keep public actions (comments under the customer's name on someone else's post) behind an explicit opt-in rather than replaying hundreds of them from a script.
35. **A hardcoded interval in a status tooltip goes stale the moment a second clock exists.** The campaigns detail page told every deferred row "It will retry in about an hour" while the engine actually used 1h for credits, 4h for a rolling invitation cap and 2h for a failed engagement. Render the scheduled timestamp the engine already stored (`nextStepAt`), never a restatement of the interval — the same rule as logging the resolved variable instead of re-reading the raw payload (lesson 32).
36. **Two surfaces that compute the same metric will disagree; the only fix is one definition both import.** SocialOS reported a 47% accept rate for a campaign on the campaigns list and 5.9% on that campaign's own detail page, over the same 17 invites. Four endpoints had each written their own predicates and no two agreed: `/api/campaigns` counted `connectionAcceptedAt != null` (minus soft-removed rows), `/api/campaigns/[id]` counted `connectionStatus = 'accepted'` (including them), the dashboard route required both, and the partner engagements route required the status. Every one was defensible in isolation. Three rules. **A denormalized counter is not a denominator**: `connectionsSentTotal` counts send ATTEMPTS (incremented per send, never decremented, double-counted on re-enrollment) and both pages divided a per-PROSPECT acceptance count into it — mixed units, and a rate that can exceed 100%. Numerator and denominator must count the same entity, which for a funnel is always the enrollment row. **Where two columns encode one fact, they will drift, and the drift is a bug upstream.** `connectionStatus` and `connectionAcceptedAt` were written together — until `is_connected` re-ran on an accepted enrollment, found the prospect in the sender's relations cache (which is exactly what an accepted invite produces) and overwrote the status with `already_connected`, silently deleting the acceptance from every metric keyed on the status while the timestamp stayed put. The report of a *reporting* discrepancy was really a report of data loss; when two surfaces disagree, find which one is wrong before you unify them, because unifying on the wrong one hides the defect permanently. A state that means "we never sent an invite" must not be writable over a state that means "the invite was accepted". **A rate with no denominator is null, not zero.** Rendering both as `—` made "messaged six people, none replied" indistinguishable from "sent nothing" on the list, while the detail page said `0.0% reply rate` for the same campaign — a third apparent discrepancy that was purely a formatting choice. Canonical predicates now live in `src/lib/campaign-metrics.ts` (pure, client-safe) with the Prisma aggregates in `src/server/services/campaign-metrics.ts`; every surface imports them, and the repair for the clobbered rows shipped as migration `20260904000000_repair_clobbered_acceptances`. **On an API you can't unify, add the right field rather than redefine the wrong one.** The partner engagements endpoints kept `connectionsSent` / `messagesSent` on the action counters — external consumers bind to them, and "how many sends did this campaign spend" is a real question — so a partner could still reach the mixed-unit pairing. The fix was additive: a `prospects*` family (`prospectsInvited`, `prospectsAccepted`, `prospectsMessaged`, `prospectsReplied`) plus `acceptRate` / `replyRate` computed server-side, always lifetime, so the correct rate is the easiest thing to read and nothing downstream has to pick the right denominator. Rates are deliberately NOT windowable: acceptances-in-window over invites-in-window are different cohorts (an invite from last month is accepted today) and yield rates above 100%. One test-hygiene note that cost a cycle: `tests/integration/campaigns-engagements.test.ts` stubbed its aggregates positionally with `mockResolvedValueOnce` chains, so adding one query to a route shifted every later stub onto the wrong bucket and the assertions went on passing against the wrong numbers. Where a route issues its queries in a `Promise.all`, the order is an implementation detail — dispatch mocks on the WHERE clause and throw on an unrecognized one.

37. **Expose a product to AI agents from ONE operations registry, not per-surface code.** SocialOS defines each operation once (`src/server/ops/`: zod input/output, risk class, scopes, handler over a shared service) and generates `/api/v1` + OpenAPI, the MCP tools and the CLI commands from it, so the three can't drift. Pull logic out of route handlers into services with an explicit `{ orgId, userId }` context first; the web route and the op then call the same code. See SocialOS `docs/mcp-cli-plan.md`.
38. **Anything an agent can do that spends money or acts on a third party needs a two-step, single-use confirmation.** First call returns a preview + an HMAC token bound to op, tenant, user, a hash of the exact input and a short expiry; the second call with the token executes; spending the token writes a row keyed by its jti so a retry or replay can't run twice; changed input gets a fresh preview. Tool descriptions and server instructions must tell the model to show the preview and wait. Audit previews and executions separately, and redact the token.
39. **MCP OAuth in practice: accept the client metadata real clients publish.** claude.ai's CIMD document declares extra grant types (`jwt-bearer`); requiring an exact grant list rejected it. Require only what you need (`authorization_code` included), bind access tokens to the resource (RFC 8707), rotate refresh tokens with reuse detection, and build discovery documents from configured `APP_URL`, never the request Host header.
40. **Auth checks belong in the service, not the route.** A route that only checks "signed in" is one refactor from a privilege escalation: SocialOS's team routes let any member make themselves admin, remove teammates and mail login links for months. Put role rules (admins only, never the last admin) where every caller goes through them, and test the member path explicitly.
